# 协调与派单

调度只由当前登记的协调者执行。执行者完成本职交付不是调度决定。

## 触发条件

出现下列任一情况时，协调者执行本文件，而不是在会话里口头分工：

- 整体目标已经登记，需要决定拆不拆、谁先做、谁等谁。
- 一份候选成果回来了，需要核验、采用或退回。
- 两个以上执行者可以同时开工，需要确认输入相同且输出不互相覆盖。
- 本轮必须结束，需要选明一种退出情形。

没有登记协调者时，先按 [roles.md](roles.md) 完成登记或更换，再派单。

## 步骤

1. 复述整体目标、范围外事项和本次选用的一种完成契约。契约定义见技能入口。
2. 列出候选工作块。同一个执行者能够看清、并且没有独立责任需要切开的，合并成一个任务。
3. 对每个仍准备派出的任务，确认拆分理由是独立责任、上下文隔离、专业复核、并行收益中的哪一项。一项都没有，就不要派。
4. 写下开工依赖。依赖未满足的任务只登记，不派发。
5. 为每个可派任务填写 [templates.md](templates.md) 的任务说明。七项语义都要落到任务说明里，不能留在协调者的隐含上下文中。字段名可以按宿主调整。
6. 把任务说明和只读输入版本交给执行者，并写明返回入口。
7. 收回结果后分开记录执行情况、质量结论和接受决定。
8. 指定核验人对照原始证据检查。通过后写采用记录：选用的版本、核验人、时间或事件标识。采用只表示后续任务可以引用这个版本，不表示业务批准，也不表示可以合并、部署或发布。
9. 若后续任务依赖该版本，把采用记录写进后续任务的输入依据，再派发那些依赖已经满足的任务。
10. 选择本轮退出情形，写明下一责任人和第一个未完成动作。

涉及软件质量时，在第 4 步确认下一动作所需的需求、设计、权限和运行条件，在第 8 步核验结论与证据的对应关系；具体见 [evidence-and-change.md](evidence-and-change.md)。已有效完成的工作可以引用原版本，不为填满阶段清单重做。某项依赖未满足时，只暂停用到它的任务，其他获授权的独立工作仍可安排。

## 派单必须写清的语义

| 内容 | 必须回答 |
|---|---|
| 任务关联 | 属于哪个整体目标，当前协调者是谁，结果回到哪里 |
| 目标与范围 | 要解决什么，不包含什么 |
| 输入依据 | 读哪些资料、准确版本是什么、哪些必须读正文 |
| 允许动作 | 哪些可读、可改、可执行，哪些还要另行确认 |
| 依赖 | 开始前哪些条件必须已经成立 |
| 交付物 | 交出什么，放在哪里，用什么识别版本 |
| 完成条件 | 哪些检查必须完成；负面结论算不算有效交付 |
| 返回与接续 | 怎样通知协调者；失败或受阻时怎样报告 |

## 并行

只有同时满足以下三点才并行派发：

- 各任务能独立做完。
- 只读输入的版本一致。
- 可写输出的位置互不覆盖。

并行数量由宿主和任务安排决定。本 skill 不另做资源调度。

并行时的隔离：

- 每个执行者只写自己的成果，不抢写同一份结论或公共索引。
- 采用、合并决定和下游输入由协调者串行处理。
- 代码任务使用仓库规范已经允许的隔离分支、工作区或补丁。本 skill 不规定分支名字。
- 代码交接写下准确提交和必要路径。只给可变分支名视为交接未完成。
- 多个任务共用基础材料时，依赖写成显式只读版本。不同任务的可写产物不能拿来混用。
- 权限域不同的资料，不因为属于同一次协作就打进同一个包。
- 独立容器之间不能假设本地目录互通。本地多个 Agent 共享磁盘，也不能因此省略版本和责任。

分布式角色委派和单个运行里的本地子 Agent 是两种组织方式。当前适配声明支持哪一种，见 [platform-adaptation.md](platform-adaptation.md)。没有声明，就不要从一种换成另一种。

## 交接物

- 任务说明，每个派出的任务一份。
- 不拆分记录：合并进哪个任务，理由是什么。
- 采用记录：版本、核验依据、是否已经进入下游输入。
- 本轮退出记录：四种情形之一，加下一责任人。

简单任务不要为了凑齐模板而复制多份空报告。没有派发的专业角色，不写空的角色报告。

## 完成标准

- 每个未结束任务都有执行责任、固定输入、一种契约和返回入口。
- 未满足依赖的任务没有被派发出去。
- 并行任务的输出位置两两不重叠。
- 后续任务引用的是已采用版本，不是未核验候选。
- 退出记录能指出下一手是谁、做什么、怎样算做成。
