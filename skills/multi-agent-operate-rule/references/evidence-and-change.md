# 证据的适用范围

本页供协调者派单、执行者交付和复核者检查软件质量时使用。沿用已有角色和完成契约；把必要记录放进现有成果即可，不要求另建质量岗位、固定开发阶段或新增审批。

## 下一动作需要证明什么

先把下一动作写成一个可检查的问题：预期行为的来源是否明确，输入版本是否可读，是否允许执行，结果要怎样观察。阶段名称和检查深度由任务决定；风险来自可能影响的行为、共享依赖、数据、权限和恢复成本，不能仅按改动行数判断。

规则含糊时，由协调者组织负责需求或设计的人澄清。现有实现只能说明当前行为，不能替代使用方的目标。纯工程调查不必虚构业务需求；使用已授权的问题和约定的调查范围。只暂停答案依赖缺口的动作，能独立交付的部分继续。

## 一条结论配一组可回读记录

按 [templates.md](templates.md#证据清单) 的证据清单，将需要交付的结论和原始检查记录对应起来。预期应来自有效规则、设计或其他独立依据；不能仅根据被测实现生成一份相同的预期，再宣称验证通过。

构建成功、调用成功或任务状态变化，只支持其实际观察到的事实。证明输出正确，还需要检查与目标相关的结果和断言。没有执行、环境不可用或版本对不上时，保留缺口和接手人。某条结论已有充分证据，也不能代替其他尚未检查的结论。

## 换了对象，先重新说明证据用途

新代码、输入规则、测试材料、配置或运行环境形成新基线时，协调者先记录变化，并沿需求、实现和验证之间的关系找受影响的结论。共享依赖的影响不局限于当前文件；关联尚未查明时，相关结论先留作待核。

旧检查记录保留原来的对象和结果。要在新任务里引用它，写明仍然成立的前提和可复用的具体结论；发生变化的部分另补验证。不能把旧版本的通过记录改签为新版本通过。已派出的任务继续绑定原输入，需要调整则明确修订任务说明和版本。

例如，虚构书摘工具 Paperlane 的标题键生成器被修改，书摘和检索都使用它。旧报告验证的是旧生成器：需求解释仍可作为来源，但新实现对两处消费者的影响要核查。若另有一个仅检查静态帮助文案的结果，确认它不依赖生成器后，可以引用原记录，不必重做整次协作。

## 先确定矛盾在哪里，再安排返工

成员交回问题时先列观察、依据和仍未知的部分；解释原因时指出能区分不同解释的下一项检查。协调者据此安排责任，不把现象直接当作根因：

- 实际输出违反有效规则，由对应实现者修复，并补相关自测和约定复核。
- 用例或夹具与有效规则冲突，先由负责验证的人核实来源并修订材料；不能为了绿色结果弱化正确预期。
- 正确版本或关键观察缺失，先补相应记录，暂不认定实现错误。工具恢复后还须核对业务行为。
- 规则本身无法支持明确预期，回到负责该规则的人，由协调者汇集必要决定；原因仍不清楚时安排定向调查。

多处问题可以分别交办。只修复一个问题，不等于其余结论已经成立；更换了验证材料，也要说明哪些旧结果需要重新检查。涉及未知外部副作用或重复尝试时，继续遵守 [recovery-and-reconciliation.md](recovery-and-reconciliation.md)。

## 公开依据

本页的协作记录方式和 Paperlane 示例为本技能自行编写，不表示获得下列机构认证，也不把其专用标准整体施加于每个任务。

- NASA [SWE-052 Bidirectional Traceability](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695427/SWE-052%2B-%2BBidirectional%2BTraceability) 将需求、设计、实现和验证之间的关联用于完整性核查与变更影响分析。
- NASA [SWE-191 Software Regression Testing](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695526/SWE-191%2B-%2BSoftware%2BRegression%2BTesting) 说明软件变化后的回归验证及依据影响选择检查范围的考虑。
- Google SRE 的 [Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/) 介绍根据观察提出假设、再通过检查区分原因的方法；这里用于说明为何返工前要核实问题来源。
