# 角色与职责

角色表示责任和判断视角。它不要求换一个模型，也不要求单独的服务器。人员可以兼任，但兼任必须写在任务说明里。要求独立复核的环节，作者不能复核自己的成果来充当独立意见。

每个角色按下述触发条件进入，做完步骤，交出交接物，并用完成标准自检。越出边界的事项交给协调者，不自行改总目标。明确的紧急停止要求要立刻遵守并报告，不能为了等协调者而继续危险操作。

对外确认只由登记的协调者组织。其他角色可以提出问题和建议，不能各自向决定人发一套彼此不知情的确认。

## 发起方

触发条件：有人提出整体目标，或获授权的工具代为提交目标。

步骤：

1. 写出要达成的结果、已知约束和希望接收结果的入口。
2. 指出必须阅读的输入及其版本。版本未知时标明未知，不要叫执行者去找“最新的”。
3. 需要自己作决定时，只在协调者后来写明的范围和版本上作决定。

交接物：目标说明、输入版本、接收入口。

完成标准：协调者能把目标、范围外事项和输入版本登记进持久记录。工具生成的意见保持为工具意见，不写成人工批准。

边界：发起方可以是人，也可以是获授权工具。工具意见不会自动变成决定人的批准。

## 协调者

触发条件：整体任务需要分工、处理依赖、组织确认、汇总或接续。

步骤：

1. 登记自己为当前协调者，写明生效范围和返回入口。
2. 确认范围、范围外事项和一种完成契约。
3. 固定输入版本，并按 [coordination-and-dispatch.md](coordination-and-dispatch.md) 决定最小任务组合。
4. 派发依赖已满足的任务，收回后把执行情况、质量结论和接受决定分开记录。
5. 组织核验。需要独立复核时指定作者以外的复核者。
6. 需要人决定时，按 [human-decision.md](human-decision.md) 发出请求并结束本轮。
7. 约定交付齐备后汇总，提请最终接受。不把协作结束写成合并、部署或发布许可。

交接物：任务说明、采用记录、确认请求或最终汇总。

完成标准：每个未结束事项都有下一责任人、第一个动作、前提和成功判断。

边界：不替专业角色下专业结论，不默认代替决定人接受最终结果。协调者可以在简单任务里兼任一部分执行，但任务说明必须写明兼任了哪一段。

更换协调者时：

1. 写出原协调者停止调度的范围、新协调者、生效时点和第一个未完成动作。
2. 把这份交接写入持久记录。
3. 新协调者读完该记录后再做调度决定。

完成标准：调度决定的记录者与登记协调者一致。两个人同时改派或同时采用，视为调度未完成，先停下来报告冲突。

## 执行者

触发条件：收到一份任务说明，其中派单语义齐全，输入版本可读取。

步骤：

1. 只读取任务说明点名的版本。打不开就按 [recovery-and-reconciliation.md](recovery-and-reconciliation.md) 停止依赖步骤并报告缺口，不要换成最新稿、旧缓存或其他任务的材料。
2. 用自己的话写下本职范围和完成条件。与任务说明冲突时交给协调者，不自行扩大范围。
3. 在允许动作内规划、执行和验证。需要专业技能时，只用任务说明点名的技能，并仍按本文件交还结果。
4. 按契约形成交付：调查契约交出报告即可，实现契约必须有代码版本和自测证据，整改契约必须有通过证据。
5. 按 [handoff-and-fixed-input.md](handoff-and-fixed-input.md) 发布候选和交接记录。成果尚未被采用时标明候选。
6. 失败、受阻或需要人决定时，向登记的返回入口报告问题、已核对状态和恢复位置。

交接物：候选成果、交接记录、证据和缺口。不能继续时改为阻塞报告。

完成标准：契约要求的检查有结果；若契约允许，负面结论也是有效交付。没有任务说明授权的外部写入没有发生。

边界：不增加任务说明以外的外部操作，不修改整体目标，不向决定人另开确认入口。

## 独立复核者

触发条件：协调者指定某一环节独立复核，且复核者不是该成果的作者。

步骤：

1. 读取任务说明、需求依据和成果的指定版本。先确认读到的版本，再开始检查。
2. 按需求和原始证据检查。作者自述、会话摘要和“已完成”标记都不是检查证据。
3. 列出问题，并给出复核结论。结论至少分开执行情况和质量结论。
4. 把复核记录交回协调者。是否采用由协调者写入采用记录，复核者不直接改下游输入。

交接物：指向被核版本的复核记录。

完成标准：每条结论能指回具体需求依据和原始证据。作者自评没有被标成独立复核。

边界：不替决定人作接受决定，不改写执行者的成果正文来“顺便修好”。

## 决定人

触发条件：协调者发出一份绑定版本和批准范围的人工决定请求。

步骤：

1. 只回答请求里列出的问题。
2. 写明接受、拒绝或要求修改，以及这条意见覆盖的版本和范围。
3. 把意见留在请求约定的通道里。不要只在别的会话里口头告诉某个执行者。

交接物：能核验的原始意见，包括决定人、通道和所针对的版本。

完成标准：批准范围可以被另一个协调运行原样读到，并且不能解释成其他阶段或其他权限的许可。

边界：一次笼统的同意不能同时覆盖不同权限或不同阶段。决定人可以和发起方是同一个人，身份仍按这次请求里的范围生效。

## 专业角色

触发条件：软件工程任务里出现需要单独承担责任的需求分析、架构、前端、后端、代码审查或测试等工作，并且第 2 步的拆分理由成立。

步骤：

1. 协调者在任务说明里写上允许使用的专业技能名称和适用场景。
2. 该执行者用对应专业技能完成本职规划和核验。
3. 接单、报告、交接和接续仍按本 skill。专业技能不改变协作规则，也不证明操作已经获准。

交接物：与执行者相同。

完成标准：专业结论附有该专业技能要求的证据，协作字段仍然齐全。

边界：没有对应的公开专业技能时，任务说明只写责任，不虚构技能名。本 skill 不内置这些专业能力。
