# Multi-Agent Operate Rule

## 用途与边界

本 skill 在需要多 Agent 协同时使用。它规定怎样把一个有明确目标的任务拆开、交给独立上下文中的执行者，并让交接、复核、人工决定和中断恢复都能顺着持久材料继续。它不负责模型如何推理，也不实现调度平台。

适合：

- 目标需要分给不同执行者，或要换模型、开发工具、运行实例后继续；
- 成果必须按固定输入版本交接，而不能靠主会话记忆；
- 需要独立复核、并行产出，或调用结果不确定时先对账；
- 人工决定必须写明对象、版本和恢复入口。

不适合：

- 一个执行者已经能独立看清并做完的任务；
- 实现任务队列、进程保活、后台轮询、消息系统、分布式锁、额度、计费或密钥管理；
- 代替需求分析、架构、实现、代码审查或测试等专业技能；
- 因为工具可见，或因为协作过程结束，就视为已获访问授权、合并、部署或发布批准。

遇到不适用请求时，简短说明边界，不要为了使用本 skill 强行拆分。

## 本地环境依赖

本 skill 只依赖 Markdown，没有固定 CLI、MCP、外部服务、凭据或运行时依赖。

任务身份、执行环境、交接存储、代码制品和人工通道由宿主提供。某项能力不存在时，按 [references/platform-adaptation.md](references/platform-adaptation.md) 改成可解释的人工交接，或停止依赖该能力的步骤。不要编造已派单、已送达或已批准。

## 开工条件

进入协作流程前，持久记录里必须已经写明：

1. 整体目标、不包含的事项，以及只选一种的完成契约。
2. 当前协调者、生效范围和返回入口。
3. 可按版本读取的输入。不能用“最新文件”或可变分支名充当依据。
4. 允许执行的动作、仍要另行确认的动作、开工依赖和交付位置。

缺任何一项时，先补登记。不要派发依赖缺口的任务。

同一整体任务同时只有一个登记协调者可以做调度决定。调度决定包括分工、改派、采用版本、把成果纳入下游输入、结束或暂停整体任务。更换协调者时，先把责任、生效范围和第一个未完成动作写入持久记录，新协调者再开始调度。宿主不能保证调度写入串行时，改为同一时刻只允许一个协调运行写入调度决定，或明确报告做不到。不要声称提示词本身能消除竞争。

完成契约三选一：

| 契约 | 完成标准 | 不能当成完成 |
|---|---|---|
| 调查或报告交付 | 约定检查已经做完，并交出有效报告；结论可以是发现问题 | 报告写完等于被调查对象通过 |
| 实现并自测 | 授权范围内的改动已经落地，并交出准确代码版本和约定自测证据 | 只提交一份实现建议 |
| 整改至满足标准 | 整改和复核都已完成，并有约定的通过证据 | 第一轮只发现问题 |

选定契约后，不要同时要求“交出报告即可”和“必须解决所有问题”。主任务的最终验收不要拆成每一个子任务都等人批准。

## 基本流程

登记的协调者按下面的顺序推进。步骤表示逻辑上的下一手，不表示本 skill 能创建事件、维持后台进程或自动唤醒执行者。宿主没有可靠触发时，必须写明由谁人工启动下一轮。

1. **确认范围。** 读取发起方给出的目标和约束，写明范围、范围外和完成契约。  
   交接物：任务登记。完成标准：没读过主会话的人能复述要做什么、不做什么、做到什么程度算完。
2. **决定是否拆分。** 一个执行者能完成的，保持不拆。只有独立责任、上下文隔离、专业复核或并行收益至少一项成立时，才增加执行者。  
   交接物：任务清单，包含不拆分的任务及理由。完成标准：每个任务只有一个执行责任，没有为了凑齐角色而拆单。
3. **固定输入并派单。** 按 [references/coordination-and-dispatch.md](references/coordination-and-dispatch.md) 写全派单语义，绑定输入版本，只派依赖已经满足的任务。  
   交接物：任务说明。完成标准：执行者只靠任务说明和指定版本就能开工。
4. **执行并交出候选，或报告卡住的位置。** 执行者在授权动作内规划、执行和验证，发布候选成果；不能继续时报告问题、已核对的状态和恢复位置。  
   交接物：候选成果和交接记录，或阻塞报告。完成标准：成果能按版本读取，或阻塞写明责任人、恢复条件和当前未知项。
5. **核验后再采用。** 协调者或指定的独立复核者对照需求和原始证据核验。核验通过后，才把该版本写入后续任务的输入。需要返工时，保留原版本，回到第 3 步另写任务说明。后续任务还依赖这份成果时，用已采用版本派发那些任务。约定交付已经齐备时，进入第 8 步。  
   交接物：核验记录和采用决定。完成标准：采用指向一个具体版本；为了读取候选而先改成已采用，视为未完成。
6. **需要人决定时结束本轮。** 发出绑在具体版本和批准范围上的确认请求，写明暂停哪些动作、哪些工作仍可继续、反馈后从哪里恢复。然后停止本轮执行。  
   交接物：人工决定请求。完成标准：决定人能看出自己决定什么；记录里没有把“将继续”写成已经自动接续。
7. **新的一轮先核对再继续。** 平台事件或登记的人启动新的协调运行后，先读持久记录，核对原始反馈、版本，以及这条意见是否已经处理。有效且还要继续时，回到第 3 步；这条反馈改变了输入时，先固定新基线，并标出受影响的既有结论。有效且已经满足结束条件时，进入第 8 步。反馈与本等待无关时，维持原等待。仍然不够决定时，重新发出确认请求。  
   交接物：反馈核验记录。完成标准：同一次成果不重复采用，同一个后续任务不重复派发，转述不代替原始批准。
8. **齐备后提请最终接受。** 汇总成果、风险和验收依据，按登记方式请决定人接受。接受则记下依据并结束整体任务。要求修改则保留被退回的版本，回到第 3 步安排剩余工作。拒绝或终止则保留已有成果，按停止范围结束或暂停相关工作。  
   交接物：汇总和接受记录。完成标准：结束依据能回溯到版本和决定人。协作结束不表示允许合并、部署或发布。

分支：

- 现有授权内能处理的范围冲突：协调者改写任务说明，回到第 3 步。专业成员不另开确认入口。
- 现有授权不能决定：转入第 6 步。
- 恢复条件还不成立：保存恢复检查点，登记具体阻塞，不派发依赖它的任务。
- 旧版本上的决定：不放行范围已经变化的新版本。
- 任务已取消或被替代：核对停止范围，保留已完成成果，处理仍挂着的等待。旧事件到达时不重新开工。

每一次执行退出前，必须落入一种可解释情形：约定交付已经完成；等待有明确对象和接续入口；阻塞和恢复条件都具体；或已经获授权停止。只写“待后续处理”而没有责任人，视为这一轮没有完成。

## 角色入口

协调者和执行者使用同一份核心规则。专业差异写在角色说明和独立专业技能里，不把整份协议复制进每个角色提示。

最小角色、兼任、专业角色扩展和更换协调者的步骤见 [references/roles.md](references/roles.md)。每个角色都按触发条件、步骤、交接物和完成标准执行。

技能已被加载，只说明可以阅读这套规则。读写、执行和外部操作是否获准，另看任务说明里的允许动作。看不到对应授权，就不执行该动作。

收回成果时分开写三个结论，不用一个“成功”代替：

- **执行情况**：约定工作是否做完，哪些失败、跳过或没有执行。
- **质量结论**：结果是否满足要求，证据是否足够，还剩什么风险。
- **接受决定**：谁依据哪个版本接受、拒绝或要求修改。

宿主如何把这三项映射到自己的状态字段，由适配说明解释。不要为了统一而给所有平台强加同一套状态机。

`evals/evals.json` 和 `evals/trigger-evals.json` 用来复核触发条件和异常边界。执行具体任务时不要把这些场景逐条重跑一遍。

引用文件缺失时，说明安装不完整，不要凭空补写规则。
