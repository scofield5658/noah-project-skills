# 前端技术方案编写

## 适用范围与项目上下文

用于用户指定项目的前端技术方案，不根据技能安装目录推断业务项目。

- 从用户请求、当前工作区及项目说明确认系统、仓库、业务入口和技术栈。
- 项目别名只使用当前用户明确提供或项目资料能够证明的映射，不预置任何业务系统清单。
- 项目未知时可先整理草案和缺口；影响方案方向的系统、入口、契约未确定前不能定稿。
- 只有代码审查或纯后端实现需求时，转用对应能力，不强套前端模板。

## 核心约定

使用本技能时，始终遵守以下要求：

- 最终交付优先是中文 Markdown 前端技术方案，并遵循 `assets/frontend-technical-solution-template.md`。
- 仅保留必要的技术缩写、路由、接口路径、代码标识、配置键、Mermaid 语法和专有名词；正文解释必须使用中文。
- 在定稿前，必须围绕方案和用户反复讨论，持续收敛缺口，不能静默补全关键决策。
- 对页面入口、改动范围、牵涉范围、字段清洗与转换、前后端契约、验收方式、验收用例等高风险信息，必须持续确认。
- 方案必须包含 `附录 D. AI 实施约束与验证闭环`，确保后续 AI 按方案实施。
- 方案头部必须登记 `常规设计使用工具和模型`；若由人工整理而非 AI 生成，也要写明 `人工整理 / 不适用`，不得留空。
- 正文与附录的**章节标题出现顺序**必须与 `assets/frontend-technical-solution-template.md` 自上而下完全一致（详见下文「章节骨架与固定顺序」）；会话草案与落盘文件同一标准。
- 只要本地存在已起草的 Markdown 方案文件，更新后必须运行遗漏检查。
- 方案已具备可读完整草案（落盘或会话中已完整展开）后，定稿前必须经过对抗式评审：由外部 Agent（Codex MCP、Claude CLI、Codex CLI、Cursor CLI 或本地 Subagent）以怀疑立场独立审查方案，最多迭代 5 轮直到通过；评审记录必须登记实际使用的评审工具和评审模型；所有评审运行时均不可用时保持 `draft/unreviewed` 状态，不得宣称已定稿。
- 本技能用于方案起草、补全和检查，不用于代码评审。

### 章节骨架与固定顺序（强制）

与模板编排一致指：**同级与跨级的 Markdown 标题在文中首次出现的先后顺序**与模板相同，而不是仅「章节都存在」。

- **大章顺序固定**：`## 一、需求背景` → `## 二、改动范围与牵涉范围` → `## 三、详细方案设计` → `## 四、实施安排与风险` → `## 五、验收与发布` → `## 附录`（若撰写 `## 附录` 标题）。不得为阅读方便重排（例如把验收提前、把附录插到第四节之前）。
- **各章内小节顺序固定**：例如「三」下须为 `3.1` → `3.2` → … → `3.5`，编号不得颠倒或交叉穿插。
- **附录内顺序固定**：`### A. 方案自检` → `### B. 评审记录` → `### C. 参考资料` → `### D. AI 实施约束与验证闭环`；其下 `#### D.1 AI 实施原则` 须在 `#### D.2 实施步骤与验证闭环` 之前。
- **可选小节 4.3**：若撰写 `### 4.3 监控、埋点与兼容性（如适用）`，须紧接在 `### 4.2 风险与回滚` 之后、`## 五、验收与发布` 之前；不适用则保留该小节标题并写简短「不适用」说明，**不得挪到其他大章前后**。
- **起草习惯**：优先按模板顺序自上而下填空，避免先写附录再回头补第二节这类需整体调序的写法。
- **与遗漏检查的关系**：落盘后 `scripts/audit_frontend_solution.py` 会校验上述顺序；顺序错误视为 **P1** 级问题，须在定稿前修正。
- **canonical 顺序的唯一来源**：脚本启动时从 `assets/frontend-technical-solution-template.md` 解析 `##/###/####` 标题得到 canonical 顺序；未来调整章节顺序或新增章节，**只需修改模板**，脚本自动对齐；只有当一个章节需要从"必需"调整为"可选/容器"时，才需要同步修改脚本中的 `OPTIONAL_BUT_EXPECTED_SET` / `NON_REQUIRED_STRUCTURAL` / `P0_HEADINGS` 分类集合。

## 资源

- 模板：`assets/frontend-technical-solution-template.md`
- 讨论与自检清单：`references/frontend-solution-checklist.md`
- 遗漏检查脚本：`scripts/audit_frontend_solution.py`
- 对抗式评审提示词模板：`assets/adversarial-prompts.md`
- 评审运行时适配器参考：`references/review-runtime-adapters.md`

这些文件是本技能的运行基础。若模板、引用文件或脚本缺失，先说明 skill 安装不完整，不要凭空补模板结构或评审规则。

可按需参考当前仓库已有前端规范：

- 当前项目自身的前端架构和编码规范。
- 若已安装 `frontend-code-review`，可按需读取其前端规则；未安装时不阻塞方案起草。

可按需协同其他 skill：

- 下列 skill 仅作为可选协同能力，不是当前 skill 的前置依赖。
- 若当前环境存在对应 skill，且用户诉求与其触发条件匹配，则按需协同使用。
- 若对应 skill 不存在、不可读、不可触发，或用户未要求走该路径，不得阻塞当前 skill 的主流程；应回到当前 skill 的主目标，结合用户诉求、现有上下文和通用工程经验继续完成交付。

- `writing-plans`：当用户要求把前端方案进一步拆成可执行实施计划时使用。
- `brainstorming`：当需求仍模糊、需要先比较交互路径、模块边界或实现框架时使用。
- `humanizer-zh`：当用户明确希望优化中文修辞、版式表达或减轻 AI 写作痕迹时使用。

## 执行流程

### 1. 先确认项目上下文

确认当前任务对应的系统、仓库、前端入口与技术栈：

- 优先读取当前项目说明、依赖声明、相邻页面和用户给出的需求。
- 无法确认的项目事实进入缺口表；不沿用其他项目的别名、组件库、分层或接口。
- 有足够需求时可以起草，P0 缺口未确认前保持草案。

### 2. 信息收集

围绕模板收集事实，并识别缺口。优先关注以下内容：

- 所属系统、所属功能入口（路由、页面名称、菜单入口、tab 场景）。
- 改动范围：业务布局组件、业务专用组件、业务通用组件、通用 UI 组件、通用工具函数。
- 牵涉范围：是否影响其他页面、组件、流程、共享能力、上下游契约。
- 改动内容：页面结构、组件拆分、项目现有视图/服务/数据转换分层、状态管理、表单联动、异常态、前后端交互。
- 字段清洗与转换：字段来源、展示值、存储值、请求体、响应体、提供方、消费方、类型定义、兼容策略。
- 复用评估：是否已有项目能力可复用；若不复用，为什么需要在当前模块内新增实现。
- 验收方式与验收用例：是否用 `chrome-devtools`、自动化脚本、单元测试、手工冒烟等。
- 发布、回滚、监控、埋点、兼容性、灰度观察。
- 常规设计使用的工具和模型，例如 `Codex / gpt-5.4`、`Cursor / Claude Sonnet`、`人工整理 / 不适用`；该登记会影响后续对抗式评审运行时选择。

如果用户给的信息过于模糊，先提一轮紧凑的 P0 问题，不要一次把模板所有字段都问完。

### 3. 缺口讨论

讨论时维护可见的缺口表：

```markdown
## 信息缺口

| 优先级 | 模板位置 | 需要确认的问题 | 当前处理 |
|--------|----------|----------------|----------|
| P0 | 2.2 牵涉范围 | 改动是否影响其他模块尚未确认 | 等待用户确认 |
```

缺口处理规则：

- P0：会影响方案方向、范围评估、前后端契约、验收、发布或回滚；除非用户明确接受某个假设，否则不能定稿。
- P1：会影响实现细节、测试完整性、监控或协作排期；可先带假设起草，但下一轮必须请用户确认。
- P2：不影响核心方案闭环；可以写明不适用或待评审补充。

追问以每轮 3-5 个为宜，优先提具体、可回答的问题。

### 4. 起草方案

当用户要求产出方案时：

- 默认先在会话中给出 Markdown 草案。
- 若用户要求落盘但未给目录，优先检查当前项目是否存在 `.planning/` 或 `.background/`。
- 若存在，则写入对应目录，文件名使用 `YYYYMMDD-{taskTopic}.md`。
- 若两者都不存在，则保持会话输出，不自动创建目录。

起草规则：

- 保留模板主章节：需求背景、改动范围与牵涉范围、详细方案设计、实施安排与风险、验收与发布、附录；且**章节与小节标题顺序须与模板一致**（见「章节骨架与固定顺序」）。
- 文档头部必须填写 `常规设计使用工具和模型`；如果方案由当前会话起草，记录当前主要设计工具和模型；如果用户提供既有方案且无法确认，写明 `用户既有方案 / 模型未确认` 并作为 P1 缺口提示用户补充。
- 方案必须明确写出所属系统、功能入口、改动范围、牵涉范围、改动内容、验收方式、验收用例。
- 涉及表单联动、字段清洗、字段转换、前后端通信时，必须写清字段来源、转换规则、类型定义、提供方、消费方和兼容策略。
- 必须评估能否复用现有项目能力，避免重复造轮子。
- 若因后续演进方向明显偏离现有公共能力而需要模块内新实现，方案中必须说明边界，并要求补充必要代码注释。
- 交互复杂时优先使用 Mermaid 图表达页面流程、状态流转或数据流。
- 对不适用章节，不要直接删除；补一段简短的不适用说明。

### 5. 与用户复审

每次完成较大草稿或修订后：

- 简要说明本轮修改内容。
- 暴露仍未解决的 P0/P1 缺口。
- 优先追问牵涉范围、字段转换与契约、验收方式和验收用例中的高风险点。
- 只要还有 P0 缺口，就不要宣称方案已可评审。

### 6. 对抗式评审

在方案基本成形、P0 缺口已收敛、且方案已具备完整可读草案（落盘 Markdown 或会话中已完整展开）后，执行对抗式评审。由外部 Agent 以怀疑立场独立审查方案，最多迭代 5 轮直到通过。

读取 `assets/adversarial-prompts.md` 获取完整的 XML 评审提示词模板。读取 `references/review-runtime-adapters.md` 了解各评审运行时的调用差异。

对抗式评审依赖的外部 CLI / MCP / Subagent 都是增强能力，不是起草草案的前置条件。所有评审运行时都必须只读：不得修改方案文件、不得发布 Wiki、不得上传附件、不得执行代码生成或格式化。所有外部评审运行时均不可用时，方案保持 `draft/unreviewed`，不得宣称已定稿。

#### 6.1 选择评审运行时

先读取方案头部的 `常规设计使用工具和模型`，评审运行时选择必须遵守以下规则：

- 优先选择与常规设计不同的工具或模型，以增加对抗性和中立性。
- 若存在多个 CLI / MCP 候选，必须避开常规设计已使用的工具和模型；例如常规设计使用 Codex，则优先选择 Claude CLI、Cursor CLI 或其他不同模型。
- 若本地环境只有一个 CLI 工具可用，或所有可用外部工具都与常规设计相同，可使用本地 Subagent 兜底，但必须在评审记录中标注对抗性弱化原因。

按以下优先级检测可用的评审运行时，并结合上述差异化规则选择：

- **优先级 1 — Codex MCP**：检查当前会话是否包含 `mcp__codex__codex` 工具。
- **优先级 2 — Claude CLI**：执行 `command -v claude`；返回路径只代表已安装，还须通过下述能力检查。
- **优先级 3 — Codex CLI**：执行 `command -v codex`；返回路径只代表已安装，还须通过下述能力检查。
- **优先级 4 — Cursor CLI**：执行 `command -v agent`；返回路径只代表已安装，还须通过下述能力检查。
- **优先级 5 — 本地 Subagent**：仅当当前运行时确实提供并允许使用子代理工具时可用；否则记录不可用，不假定所有客户端都有该能力。

能力检查必须覆盖已安装版本、参数兼容性、有效工具权限、模型可用性与认证状态。只读模式不能替代外部工具权限隔离，提示词也不能替代运行时限制。参数不支持、认证失败或无法确认权限时，记录原因并尝试下一运行时；全部不可用则保持 `draft/unreviewed`。不得自动安装、升级、登录或改动用户全局配置。命令解析成功仅证明参数可接受，只有实际返回有效裁定才算完成评审。

执行任一评审运行时前，必须再次确认只读边界：评审者只能读取方案和相关上下文，不能修改文件、运行格式化、发布 Wiki、上传附件或执行任何会改变仓库/外部系统状态的动作。CLI 错误可能包含提示词或敏感内容，仅保留脱敏摘要；不把原始 stderr 写入共享临时文件。

#### 6.2 执行评审

使用 `assets/adversarial-prompts.md` 中的「方案评审提示词」构建 prompt。

**方案内容传递：**
- 方案已落盘 → Codex MCP 可传文件路径，Claude CLI、Codex CLI、Cursor CLI 与本地 Subagent 必须内联全文。
- 方案仅在会话中 → 所有运行时统一内联全文。

**调用参考：**

```
# Codex MCP
mcp__codex__codex(
  prompt: "<XML评审提示词>\n\n方案文件路径：<文件路径> 或 方案全文：\n<Markdown 全文>",
  sandbox: "read-only",
  model: "<当前账户可用且满足差异化要求的模型>",
  approval-policy: "never"
)

# Cursor CLI
cat <<'PROMPT_EOF' | agent --mode ask --print --output-format text
<XML评审提示词>

<方案全文内联>
PROMPT_EOF

# Claude CLI
cat <<'PROMPT_EOF' | claude --bare --print --tools "" --disallowedTools "mcp__*" --strict-mcp-config --mcp-config '{"mcpServers":{}}'
<XML评审提示词>

<方案全文内联>
PROMPT_EOF

# Codex CLI
cat <<'PROMPT_EOF' | codex --ask-for-approval never exec --sandbox read-only --ignore-user-config --ignore-rules --ephemeral -
<XML评审提示词>

<方案全文内联>
PROMPT_EOF

# 本地 Subagent
Agent(
  description: "对抗式评审前端技术方案",
  prompt: "<XML评审提示词（含 additional_constraints）>\n\n<方案全文内联>",
  subagent_type: "general-purpose"
)
```

向用户展示评审结果原文，不改写。

评审完成后，必须在方案 `### B. 评审记录` 中登记：

- `评审工具`：实际使用的运行时，例如 `Codex MCP`、`Claude CLI`、`Codex CLI`、`Cursor CLI`、`本地 Subagent`。
- `评审模型`：实际模型名称；若 CLI 未暴露模型，写明 `CLI 默认模型（未暴露）`。
- 若评审工具或模型未能与常规设计区分，必须在 `待解决事项` 或同一行备注中说明原因，例如 `本地仅检测到 agent CLI，改用本地 Subagent 兜底，对抗性弱化`。

#### 6.3 处理裁定

严格解析评审结果：

- 评审输出的**最后一个非空行**必须是且仅是 `VERDICT: APPROVED` 或 `VERDICT: REVISE`。
- 文本中存在多个 VERDICT 行（正文引用、示例、代码块不算） → 解析失败。
- 未找到 verdict → 解析失败。
- 存在 high/critical finding 但 verdict 为 APPROVED → 视为矛盾，按 REVISE 处理并记录为评审异常。
- 解析失败时最多重试 1 次（要求评审者重新输出裁定），仍失败则切换运行时或阻断。

**评审运行时失败处理：** 超时、非零退出码、空输出、无 verdict、网络错误 → 视为当前运行时不可用，按优先级降级下一个运行时重试。所有评审运行时（含本地 Subagent）均失败时，方案保持 `draft/unreviewed`，明确告知用户"未通过对抗式评审，不可作为最终方案"，不得触发最终化或发布。

裁定处理：

- **VERDICT: APPROVED** → 评审通过，检查是否触发变更门禁（6.5），否则进入遗漏检查。
- **VERDICT: REVISE** → 基于发现修复方案，再重新提交评审。
- 解析失败 → 要求评审者重新给出裁定。

#### 6.4 迭代修复循环

最多 5 轮。每轮：

1. 基于评审发现修复方案。
2. 向用户简述本轮修改内容。
3. 重新提交评审。

维护评审问题台账：

```markdown
| Finding ID | 严重程度 | 问题描述 | 处理方式 | 修改位置 | 复审结果 |
|------------|----------|----------|----------|----------|----------|
| F1 | high | 牵涉范围未说明共享组件调用方 | 补充 2.2 牵涉范围条目 | 二 2.2 | 已通过 |
```

后续轮次的 prompt 必须包含修复说明和台账：

```
我已根据你的反馈进行了修复。以下是修复内容：
<修复列表>

评审问题台账：
<台账表格>

请以相同的对抗式立场重新评审。重点关注：
1. 修复是否真正解决了报告的问题
2. 修复是否引入了新问题

以 VERDICT: APPROVED 或 VERDICT: REVISE 结束。
```

Codex MCP 后续轮次使用 `mcp__codex__codex-reply(threadId, prompt)` 恢复会话；Claude CLI、Codex CLI、Cursor CLI 和本地 Subagent 在 prompt 中附带评审历史摘要。

**失败出口：**

- 达到 5 轮仍有 high/critical 未关闭 → 阻断最终化，向用户报告未解决问题。
- high/critical 全部关闭但仍有 medium 未关闭 → 所有未关闭 medium finding 必须落入方案「4.2 风险与回滚」，并在输出中请用户确认"接受残余风险"后才能继续最终化；未确认时保持 draft 状态。

#### 6.5 变更门禁

对抗式评审通过后，检查本轮修复是否触及以下领域：

- 所属系统 / 功能入口
- 改动范围或牵涉范围
- view / service / translator 分层落点
- 前后端契约、字段转换或类型定义
- 表单联动或关键异常态
- 验收方式或验收用例
- 发布 / 回滚 / 兼容性策略
- 假设与约束

如涉及以上任一领域 → 生成变更摘要，回到阶段 5（与用户复审）。纯文字修正或格式修正可直接进入遗漏检查。

### 7. 遗漏检查

当方案已写入本地 Markdown 文件后，运行：

```bash
python3 <skill-dir>/scripts/audit_frontend_solution.py <solution-file.md>
```

然后：

- 修复所有能基于当前上下文解决的 P0/P1 问题。
- 重新运行，直到没有可修复的 P0/P1。
- 把剩余问题和需要用户确认的假设明确告诉用户。
- 该脚本只依赖 Python 3.8+ 标准库；如果 `python3 --version` 不满足要求，或脚本无法运行，改用 `references/frontend-solution-checklist.md` 手工自检，并说明缺口。

仅在会话中输出草案时，可以先不跑脚本，但必须继续显式暴露 P0/P1 缺口。

### 8. Wiki / Confluence 与静态资源

本技能不绑定固定 Wiki 上传脚本。只有用户明确要求时，才按当前环境可用能力选择路径：

- 优先评估当前环境可用的 MCP 服务、已有 skill 或其他工具。
- 若环境缺少可用发布能力，回退为会话输出或本地 Markdown 文件。

静态资源转换规则：

- Mermaid：先用 `command -v mmdc` 检测本地 Mermaid CLI；可用时再导出静态图，不可用时保留 Mermaid 源码并说明缺口，不改走在线服务。
- 其他文档或图片转换：先评估本地 Python / Node / npm / npx 工具链与现成脚本；若缺失，只给推荐安装方向。

环境探测示例：

```bash
command -v mmdc
command -v python3
command -v node
command -v npx
```

如果当前环境能探测到这些命令，可以把它们视为优先候选能力，但执行前仍应重新确认。

### 9. 执行计划协同

当用户要求把前端技术方案继续下钻为执行计划时：

- 先确认技术方案的 P0 缺口已收敛，至少达到可实施状态。
- 若当前环境可用且适合协同，则再协同 `writing-plans`，把方案拆成更细的实施任务、验证步骤和交付顺序；若不可用，则由当前 skill 按用户目标先完成可交付的执行拆解草案。
- 如果执行计划正文需要进一步压缩 AI 痕迹或优化中文表达，且当前环境可用、用户也有此诉求，可在定稿前再协同 `humanizer-zh`；否则保持当前 skill 直接交付。
- 如果执行计划阶段仍发现方案本身存在结构性歧义，应先回到当前 skill 或在当前环境可用时协同 `brainstorming` 收敛问题，不要直接带着歧义往下分解任务。

## 输出要求

创建或更新方案后的最终回复应包含：

- 输出位置：会话 / 文件路径。
- 确认技术方案为中文 Markdown。
- 遗漏检查结果；若未运行脚本，要说明原因。
- 对抗式评审结果摘要（常规设计使用工具和模型、使用的评审运行时、评审模型、轮数、最终裁定、残余风险处理）；若因草案未成形或所有评审运行时均不可用而未执行评审，必须说明原因并保持 `draft/unreviewed`。
- 仍需用户确认的问题，如有。
- 说明保持简洁，技术方案正文才是主要交付物。

## 完整使用示例

概述：把前端需求整理为可实施、可验收的中文技术方案。

输入：库存管理系统 `inventory-web`，Vue 页面新增仓库筛选，空仓库编码的后端语义尚未确认。

输出：按随包模板产生中文草案，明确入口、组件及转换范围，把空值语义列为 P0；保留字段契约、验收与回滚章节。用户确认契约后补齐方案，落盘则运行审计脚本；独立评审能力不可用时标记 `draft/unreviewed`，不将草案标为定稿。
