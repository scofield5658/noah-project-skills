# 前端技术方案讨论与自检清单

基于 `assets/frontend-technical-solution-template.md` 起草、讨论或审查前端技术方案时使用本清单。

- 各结构标题在正文中的**出现顺序**须与模板自上而下完全一致（含「五」之后 `## 附录`、附录内 A→B→C→D、D.1→D.2；可选 `### 4.3` 仅允许在 4.2 与「五」之间）。落盘后可由 `scripts/audit_frontend_solution.py` 校验顺序。

## 缺口分级

| 等级 | 含义 | 处理方式 |
|------|------|----------|
| P0 | 会影响方案方向、影响面评估、前后端契约、验收、发布或回滚的缺口 | 必须追问；若继续写，必须得到用户认可的明确假设 |
| P1 | 会影响实现细节、测试完整性、监控或协作排期的缺口 | 可先按假设起草，但下一轮必须请用户确认 |
| P2 | 不影响当前方案闭环的补充信息 | 可标注不适用或待评审补充 |

## 首轮必问 P0

只询问缺失的问题。用户已经说明或本地上下文已有的内容，不要重复追问。

| 模板位置 | 必须确认的问题 |
|----------|----------------|
| 1.1 所属系统 | 当前是哪个系统、仓库和业务域？别名是否有用户说明或当前项目资料支持，是否已经确认实际入口？ |
| 1.2 所属功能入口 | 路由、页面名称、菜单 / tab / 弹窗入口分别是什么？ |
| 2.1 改动范围 | 是否涉及业务布局组件、业务专用组件、业务通用组件、通用 UI 组件、通用工具函数？ |
| 2.2 牵涉范围 | 是否影响其他页面、共享组件、公共能力、上下游契约？ |
| 3.3 / 3.4 改动内容 | 是否涉及表单联动、字段清洗、字段转换、前后端通信、类型定义变更？ |
| 2.3 复用评估 | 当前项目是否已有可复用能力？若不复用，原因是什么？ |
| 5.1 / 5.2 验收 | 验收用什么工具做？关键交互、契约和回归场景有哪些？ |
| 文档头部 / B. 评审记录 | 常规设计使用了什么工具和模型？对抗式评审是否使用不同工具或模型？若无法不同，原因是什么？ |

## 分章节检查要点

### 一、需求背景

- 所属系统必须能定位到系统、仓库、业务域与技术栈。
- 功能入口必须写清路由、页面名称、菜单或 tab 入口，以及是否存在多 tab / 弹窗 / 抽屉语境。
- 需求背景与目标不能只写“优化体验”，要写清当前问题、用户场景与本次目标。
- 边界与影响必须明确包含范围、不包含范围、兼容性要求和性能 / 体验要求。

### 二、改动范围与牵涉范围

- 改动范围五类必须逐项判断，不能笼统写“前端页面改动”。
- 牵涉范围必须说明是否影响其他模块；如果影响，要写清对象、内容、风险等级和回归点。
- 必须显式评估当前项目已有能力是否可复用，避免重复造轮子。
- 若决定新增实现，要说明边界、偏离原因，以及哪些关键逻辑需要代码注释。

### 三、详细方案设计

- 页面结构与交互流程应覆盖主路径、联动路径、异常态和返回路径。
- 方案应按 view / service / translator 分层落地，避免把转换逻辑、请求逻辑、页面逻辑混在一起。
- 改动内容必须落到具体组件、逻辑、状态和交互变化。
- 涉及字段联动、字段清洗、字段转换、前后端通信时，必须区分展示值、状态值、请求字段、响应字段、提供方和消费方。
- 对表单联动，明确谁驱动谁、什么时候清空、什么时候回填、异常时如何处理。
- 对前后端契约，明确类型定义、默认值、兼容字段和兜底规则。

### 四、实施安排与风险

- 每个实施步骤都应映射到需求或风险，并限定允许修改范围。
- 风险不只写描述，还必须有预防措施和回滚或止损方式。
- 若涉及监控、埋点、兼容性，至少说明是否适用与观察点。

### 五、验收与发布

- 验收方式必须明确是否使用 `chrome-devtools`、自动化脚本、单元测试或手工冒烟。
- 交互联动验收用例必须覆盖前置条件、主流程、联动场景和后续影响场景。
- 前后端通信验收用例必须覆盖字段存在性、类型一致性、提供方 / 消费方呼应关系。
- 工具函数或 translator 若承载明显逻辑，应在当前项目既有测试框架下补必要单元测试。
- 不要为普通 UI 改动强行设计过量测试。

## AI 实施约束检查

附录 D 至少要覆盖：

- 显式假设与追问
- 最小可行实现
- 变更可追溯
- 外科手术式实施
- 每步带验证
- 先复现后修复

并确保 `实施步骤与验证闭环` 表中至少包含：

- 步骤
- 对应需求 / 风险
- 实施动作
- 允许修改范围
- 验证方式
- 完成标准

## 最终自检问题

在宣布方案完成前，逐项回答：

- 当前方案是否明确所属系统、仓库和前端入口？
- 如果用户使用系统或入口别名，是否已按当前项目资料确认映射，而非沿用其他项目约定？
- 所属系统、所属功能入口、改动范围、牵涉范围是否完整？
- 是否已经明确说明哪些模块会被影响、哪些不会？
- 是否已经评估项目现有能力能否复用？
- 若有字段联动、字段清洗、字段转换、前后端通信，相关规则是否闭环？
- 验收方式是否真实可执行，而不是只写笼统的“测试通过”？
- 验收用例是否覆盖关键交互、回归点和前后端契约？
- 若涉及工具函数或 translator，是否提供了必要但不过度的单测要求？
- 文档头部是否登记常规设计使用工具和模型？
- 对抗式评审记录是否登记评审工具和评审模型，且尽量不同于常规设计侧？
- 最终 Markdown 是否已移除占位符、未确认标记和英文说明段落？
