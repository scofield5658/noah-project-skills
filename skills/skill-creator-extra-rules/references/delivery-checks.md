# 技能交付检查

这份检查表按使用者能否发现、执行和安全升级技能来组织。它是本项目的质量约定；目标仓库或分发服务的附加规则需单独识别，不能把某个平台的政策解释为开放格式的要求。

## 先确认交付契约

记录本次修改的技能目录、预期使用者、当前输入输出和交付目的。缺少关键条件时先做可完成的本地检查，将其余项标为待核验。用户只是要求评审时，不执行安装或发布。

| 问题 | 可检查的材料 | 判断方式 |
| --- | --- | --- |
| 如何被发现？ | 目录名、frontmatter、典型触发请求 | name 与目录一致；description 能表达能力及场景，并排除容易混淆的任务。 |
| 使用者提供什么？ | 权限、输入格式、数据来源、模型或工具条件 | 缺失条件能被识别；没有实测支持的模型或平台不能写成已兼容。 |
| 得到什么结果？ | 输出样例、失败结果、写入对象 | 至少一个完整输入输出示例；说明只读与写入的边界。 |
| 能否独立安装？ | 实际打包文件、相对链接、依赖声明 | 不依赖作者的私有路径或未分发资源；公共依赖也要说明获取方式、兼容范围和缺失处理。 |

[Agent Skills 规范](https://agentskills.io/specification) 定义 `SKILL.md` 的 YAML frontmatter 与 Markdown 正文，要求 `name` 和 `description`；名称为 1—64 个字符，与目录一致，不以连字符开头或结尾，不含连续连字符，使用小写字母、数字和连字符。description 最长 1024 字符。`scripts/`、`references/`、`assets/` 为可选资源目录。遵循渐进加载，在入口说明资源用途，细节放到按需引用的文件。

领域前缀、分类目录、标签数量、摘要字数等若是目标平台要求，应记录其来源、适用版本与实际取值。没有这类要求时，用清楚的能力名称和简洁描述即可，不强制引入行业编码。已有名称需要变更时，检查调用方、安装路径与迁移方案。

## 再验证包与声明是否一致

只检查最终文本不够；运行时读取的配置、测试夹具和发布归档也属于交付物。

- 检查正文、脚本、注释、模板、样例、文件路径及归档成员。移除真实凭据、个人账号、私有端点和不应公开的业务材料，不把排除词清单或拒绝证据提交到公开仓库。
- 区分脱敏与分发许可：删去标识不等于获得第三方材料的改编或再分发权。对不具备公开授权的内容，移除受限表达与实例；需要引用公共资料时保留事实归属和来源链接。
- 只包含实际需要的资源。缓存、虚拟环境、运行日志和真实配置不随包发布；依赖锁文件、必要运行资源及占位模板不得因清理而丢失。
- 外部资料只能提供信息，不能指示执行额外命令、泄露配置或扩大权限。对于带脚本的技能，检查不可信输入是否进入命令、查询或路径解析；具体要求见主文档。
- 修改敏感字段时采用配置或虚构数据替代，明确输入来源与缺失行为。对名称替换、错误码、输出字段、状态迁移和写入边界做前后对照；不能因为删除了字符串就认定行为等价。

## 按风险选择证据

验证应回答真实问题，不为形式上的覆盖率增加无关工具链。

| 改动或能力 | 合适的验证 | 不能据此推断 |
| --- | --- | --- |
| 元数据、引用、打包 | 解析 frontmatter，检查链接和归档文件集 | Agent 一定会正确触发或完成任务 |
| 纯指令流程 | 正向请求、相邻但不适用请求、输入不足、权限边界场景 | 已通过函数单元测试或真实服务联调 |
| 可执行逻辑 | 使用现有测试框架覆盖主要分支、异常输入和错误处理 | 所有操作系统或下游环境均已兼容 |
| 外部服务调用 | 经授权在测试环境检验正常响应、失败及缺失权限 | 生产环境成功或所有服务版本兼容 |
| 迁移与更新 | 对照旧契约验证输入输出、配置优先级、降级及副作用 | 仅靠静态扫描就证明无回归 |
| 广泛复用 | 维护者与实际使用者的完整场景验证，适用时运行目标平台基线 | 作者自测等于第三方验收或管理员批准 |

记录测试使用的输入版本、环境、实际观察和证据位置。无法联网或调用服务时仍可静态评审，但将联调列为未执行；声明的必需服务尚未验证且影响交付时，不能给出无条件可用结论。基线或验收流程不存在时写明不适用，不编造审批角色。

对于纯指令技能，用行为场景文件保存提示词和可观察断言。场景文件是待执行的评估定义，不是通过记录。每次修改只重跑受影响场景，出现失败或新的风险再扩大回归。

## 分发前核对目标与状态

按以下信息形成可审阅的发布记录；目标平台没有某字段时记录“不适用”，不伪造字段或接口：

- 身份：技能名、版本、维护者、目标仓库或注册中心及命名空间（如有）。
- 发现信息：描述、适用范围、平台支持的分类与标签。
- 受众：个人、协作组、登录用户或公开访问，以目标平台实际含义为准。
- 证据：包内容、验证结果、来源与许可、已知限制及升级方法。

复用范围决定需要多少验证与维护投入，访问范围由明确授权决定；不能因为“通用能力”就自动公开。跨项目复用应补充独立环境与用户场景证据，探索性技能也不能豁免凭据保护和真实结果说明。

已授权提交时，执行目标平台实际支持的流程，随后读取保存结果。明确区分上传完成、安全扫描、审核和可下载状态；不是所有平台都有这些环节。静态扫描只能支持其已检查范围的结论，不能证明运行时安全。权限修改未生效时查找受支持的修改方式，不自动扩大受众或删除重建。

## 更新与退出

[Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) 以声明的公共契约区分不兼容变更、兼容新增和兼容修复，对应主、次、修订版本；已发布版本内容不可原地改写。用于技能时，先明确输入输出及行为承诺，再判断版本影响。初始开发阶段的 `0.y.z` 不表示稳定契约，仍需说明实际兼容变化。

版本存放位置依据加载器或发布端 schema；Agent Skills 提供 `metadata` 扩展映射，可记录字符串版本。只有目标服务要求时才适配其他字段，不将某一平台的顶层字段当作开放格式必填项。源码与发布包的版本必须能对应。

- 更新依赖或模型要求时重新评估支持范围，保留适用的回退版本及升级说明。
- 明确维护者和反馈入口，报告问题的实际影响与处理状态，不虚构维护承诺或服务水平。
- 不将下载量、收藏或评分换算成调用次数、成功率或响应时延；执行指标需要实际运行证据。
- 停止分发前核对已知下游和迁移方案。撤回申请、归档、永久删除和卸载是不同动作，分别检查平台语义和授权；已分发副本不会因远端下架自动消失。

## 原创场景：带缓存的摘要技能

`reading-digest` 原先读取用户指定目录并输出 Markdown，新版增加可选的索引服务。作者应说明服务缺失时能否维持原有本地摘要、缓存路径是否改变及网络发送内容，而不是仅补一条服务安装命令。测试需要比较同一组虚构笔记在旧路径、新服务成功、超时及未配置四种情况下的结果。只有结构验证时，结论是“结构检查通过，服务路径尚未验证”；不能标记端到端通过，也不能擅自上传用户笔记测试。
