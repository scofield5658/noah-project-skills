# Skill Creator Extra Rules

本规范可独立使用，也可补充现有的技能编写流程；不依赖另一个 skill。目标是把 skill 依赖的本地环境描述清楚，让不同开发者在不同机器上运行时有一致预期，减少“作者本机可用、其他人不可用”的情况。

## 本地环境依赖

本技能只依赖 Markdown 指令和随附文本资料，无本地运行时依赖，不要求安装 CLI、MCP 或访问外部服务。评审对象的运行依赖应按下文单独核对；缺少其运行环境时仍可做静态评审，但不得宣称运行验证已通过。

公开改编授权见[授权与适用范围](references/publication.md)。

## 使用时机

创建、修改、迁移或评审 agent skill 时，只要存在以下任一情况，就应用本规范：

- 需要运行本地脚本、CLI 命令、MCP、浏览器自动化、数据库连接、文档平台、事项管理或其他外部服务接口。
- 需要 Python、Node.js、Java、Maven、Docker、Pandoc、Mermaid CLI、数据库客户端等本地程序。
- 需要第三方包、全局 npm 包、pip 包、浏览器插件、系统命令或特定 shell。
- 需要环境变量、本地配置文件、用户目录、仓库目录、缓存目录或输出目录。
- 示例命令中出现绝对路径、维护者个人目录、固定端口、固定服务地址或固定账号。

如果 skill 只依赖 Markdown 指令和仓库内普通文本资料，也要明确写出“无本地运行时依赖”。

普通业务功能开发、为当前机器安装软件或排查服务故障，没有技能编写或依赖评审目标时，不触发本规范。核对说明不等于获准安装软件或调用外部服务。

## 依赖分类口径

写依赖说明时先分类，避免把标准库和第三方依赖混在一起。

| 类型 | 是否算本地依赖风险 | 说明 |
| --- | --- | --- |
| Python 标准库 | 随运行时核对 | 如 `argparse`、`json`、`pathlib`、`re`、`subprocess`、`urllib`、`ssl`。只需声明 Python 版本。 |
| Python 第三方包 | 是 | 如 `requests`、`openpyxl`、`numpy`、`pandas`。必须声明安装方式或 requirements 文件。 |
| Node 内置模块 | 随运行时核对 | 如 `node:fs`、`node:path`。只需声明 Node.js 版本。 |
| npm / npx 包 | 是 | 如 `@mermaid-js/mermaid-cli`、数据库 MCP 包。必须声明包名、版本策略和验证命令。 |
| 系统 CLI | 是 | 如 `git`、`mvn`、`pandoc`、`docker`、`mmdc`、`curl`、`wget`。必须声明最低版本或可用性检查。 |
| 外部服务 / MCP | 是 | 如文档服务、事项管理、日志检索、数据库或 MCP 服务。必须声明工具名、权限、不可用时处理方式。 |
| 本地配置 / 凭据 | 是 | 如 `.env.local`、`config.properties`、token、密码。必须声明不入库和脱敏规则。 |

## SKILL.md 必备小节

凡存在本地运行时依赖的 skill，`SKILL.md` 应包含一个 `## 本地环境依赖` 或等价小节。建议使用下面结构：

```markdown
## 本地环境依赖

| 依赖 | 必选 | 版本 / 来源 | 用途 | 检查命令 | 缺失时处理 |
| --- | --- | --- | --- | --- | --- |
| Python | 是 | 3.10+ | 运行脚本 | `python3 --version` | 提示安装 Python，不继续执行脚本 |
| requests | 是 | 见 `requirements.txt` | 调用文档 API | `python3 -c "import requests"` | 在项目虚拟环境按依赖文件安装 |
| pandoc | 否 | 3.x 推荐 | Word 转 Markdown | `pandoc --version` | 跳过 Word 转换，提示用户安装 |
```

如果依赖较多，可以把安装细节放到 `INSTALL.md`、`references/setup.md` 或脚本 README 中，但 `SKILL.md` 必须能告诉使用者：依赖是什么、为什么需要、怎么检查、缺失时去哪看。

**跨平台 Python 命令声明**：凡涉及 Python 脚本的 skill，应在 `## 本地环境依赖` 或等价小节中加一行声明：

```markdown
**Python 命令**：先检查项目约定和可用解释器；macOS/Linux 通常使用 `python3`，Windows 可使用已验证的 `py -3` 或 `python`。虚拟环境优先使用其解释器。下文统一写 `python3`，应按实际环境替换并验证版本。
```

正文示例命令统一写 `python3`，不再在每个命令处分别标注。

## 版本与安装规范

1. 对语言运行时写清最低版本，根据实际使用的语法、API 和已验证环境确定，不将示例版本当作所有技能的统一最低版本。
2. 对第三方包优先提供仓库内依赖文件：
   - Python：`requirements.txt`、`pyproject.toml` 或明确的 `pip install ...`。
   - Node：`package.json`、锁文件或明确的项目内安装方式；确需全局安装时说明原因及影响。
3. 对 `npx -y`、`pip install git+...` 这类动态拉取命令，说明版本策略。能固定版本、tag 或 commit 时优先固定。
4. 对下载脚本、GitHub fork、二进制包、MCP 包等供应链依赖，说明来源、版本、校验或更新策略；不能固定版本时，要说明为什么以及风险边界。
5. 对平台相关依赖分别说明 macOS、Linux、Windows 的差异；不能跨平台时明确写出适用平台。
6. 示例命令不要写维护者个人路径。使用占位符或环境变量：
   - `<SKILLS_ROOT>` 表示技能集合根目录。
   - `<REPO_ROOT>` 表示目标业务仓库根。
   - `<SKILL_DIR>` 表示当前 skill 目录。
   - `SKILLS_ROOT`、`TARGET_REPO_PATH` 等环境变量必须解释含义和优先级。

## 配置与凭据规范

1. 真实凭据、token、密码、数据库连接串、个人账号配置不得提交到仓库。
2. 入库模板只保留 `*.env.example`、`*.example.json`、`config.example.properties` 等占位内容；真实本地配置应被忽略。
3. 配置位置由目标项目声明，可以是项目配置、用户配置或环境变量，不依赖维护者机器上的中央模板或加载脚本。
4. 项目已有共享配置模板时优先复用；引用随技能提供的模板应使用相对链接。外部配置必须说明来源、配置项、加载方式和缺失处理，不假定读者能访问私有目录。
5. `.gitignore` 只能防止新增误提交；如果真实配置已经被 Git 跟踪，必须指出泄露风险并给出停止跟踪、凭据轮换和必要的历史清理建议；实际轮换、历史重写等操作按授权范围单独执行。
6. 文档示例使用占位符，不使用真实 host、账号、库名、密码或内网服务地址，除非该地址是公开且无敏感性的固定系统入口。
7. 如果脚本会读取多个配置位置，写清优先级，例如：普通参数可采用命令行参数 > 环境变量 > 本地配置文件，并以实现为准；凭据遵循下述专用规则，不通过命令行传递。
8. 输出日志不得打印凭据原值；错误信息可以说明缺少哪个变量，但不要回显变量值。
9. 不推荐通过命令行参数传递密码、token 或 Basic `user:pass`，因为可能进入 shell 历史、进程列表或日志；优先使用环境变量、密钥管理或 MCP 凭据能力。
10. 若需要直连数据库或写入文档或事项管理服务，写明权限边界、只读/写入行为、是否需要用户确认。

## 命令执行与输入安全

配套脚本或示例命令只要会接收用户输入、Git ref、文件路径、URL、SQL、页面 ID 或分支名，就要说明输入边界并避免命令注入。

1. Python 脚本优先使用 `subprocess.run([...], shell=False)` 这类参数数组形式；不要把未可信输入拼进 `shell=True` 字符串。
2. Shell 脚本优先使用数组保存命令和参数；避免 `eval "$CMD"` 执行拼接命令。
3. 对 Git branch/ref、文件路径、URL、pageId、数据库名等关键输入做白名单、格式校验或工具自带校验。
4. 不要在命令字符串、日志或错误堆栈中拼接凭据。
5. 如果因为兼容性必须使用 shell 拼接，必须在文档中说明输入来源可信边界，并在脚本中集中转义或校验。

## 写入、高权限与外部系统操作

凡 skill 会修改外部系统、用户机器或共享资料，必须把确认点写在 `SKILL.md` 中，而不是只依赖脚本参数。已有授权覆盖明确目标和动作时，不机械重复索取确认；超出授权或范围不明时再确认。预览或 `--yes` 参数本身不构成授权。

1. 文档、事项、数据库、流水线或系统配置等写入操作，执行前确认目标系统、环境、URL、资源 ID 或名称、项目、分支、账号权限和影响范围。
2. 删除、覆盖、发布、上传附件、触发流水线、执行 DDL/DML、修改系统配置等操作，应提供 `--dry-run`、预览、`--yes` 或二次确认机制。
3. 高权限操作（如 `sudo`、系统包安装、全局 npm/pip 安装、修改桌面环境、修改 shell 全局配置、写用户级目录）必须说明适用平台、执行前备份、失败回滚和授权要求。
4. 对 HTTP + Basic auth、明文接口、命令行传密等传输风险，必须写清适用范围和替代方式；能使用 HTTPS 或 MCP 凭据能力时优先使用。
5. 当外部服务或 MCP 不可用时，不要自动改走未授权接口；应停止、降级为本地草稿，或明确要求用户补齐授权工具。

## 缺失与降级规范

每个必选依赖都要有缺失处理。不要让使用者只能看到底层 traceback。

- 可安装的依赖：给出安装命令或指向安装文档。
- 可替代的依赖：写清替代路径及结果差异。
- 不可替代的依赖：明确停止执行，并说明需要用户补齐什么。
- 外部服务或 MCP 不可用：不要自行改走未授权 HTTP 调用；先提示工具不可用和人工查询方式。
- 本地程序版本不满足：不要继续生成可能不一致的结果；先要求升级或切换兼容模式。

## 脚本自检要求

配套脚本应尽量在入口处做轻量自检：

1. 检查必需命令是否存在，如 `shutil.which("mmdc")`。
2. 检查第三方包是否可 import，并给出明确安装提示。
3. 检查关键环境变量是否存在，但不打印值。
4. 检查输入路径、输出目录、目标仓库根是否有效。
5. 对破坏性或写入型操作提供 `--dry-run`、`--yes` 或二次确认机制。
6. 对动态下载或外部包执行前打印包名和版本来源，避免用户无法判断实际运行内容。

## 创建或修改 skill 的检查清单

提交前逐项检查：

- `SKILL.md` 是否有本地环境依赖小节；无依赖时是否明确说明。
- 是否区分了标准库、第三方包、系统 CLI、MCP、外部服务和本地配置。
- 所有第三方包是否有安装方式和验证命令。
- `npx -y`、`pip install git+...`、下载脚本或外部二进制是否有版本/来源策略。
- 所有示例路径是否使用占位符，而不是个人绝对路径。
- 所有真实配置是否使用模板文件，真实本地文件是否被 `.gitignore` 覆盖。
- 已被 Git 跟踪的真实配置是否说明了停止跟踪、凭据轮换和历史清理。
- 写入、删除、上传、数据库访问等操作是否有权限边界和确认规则。
- 脚本中是否避免 `shell=True`、`eval` 或未校验输入拼接命令。
- 高权限或系统配置类操作是否有平台范围、备份/回滚和人工确认。
- 缺失依赖时是否有清晰的停止、安装或降级说明。
- 若 skill 依赖特定平台或网络访问，是否明确写出适用范围、授权和不可用时处理方式。

## 推荐输出格式

当评审一个 skill 的依赖完整性时，优先输出：

1. 结论：依赖说明是否闭环。
2. 缺失项：按本地程序、第三方包、配置凭据、外部服务分类。
3. 风险：可能导致哪些环境差异或执行失败。
4. 建议补充：应添加到 `SKILL.md` 或安装文档的具体内容。

当评审一批 skills 时，优先产出一张统一综合表，把安全隐患、本地依赖、依赖说明闭环、缺失降级和建议动作放在同一张表中；不要把“原审查表”和“规范覆盖性复核”拆成两个割裂结论。
