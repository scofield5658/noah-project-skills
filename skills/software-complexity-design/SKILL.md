# 软件复杂性与架构设计

## 定位

使用本技能时，你的目标是帮助用户完成目标系统技术架构层面的设计与评估，而不是进入代码级详细设计。架构设计不能停留在“列出哪些系统和文件要改”；它还要说明这些改动如何控制长期复杂性，使后续团队能更少地跨模块理解、更集中地修改、更可靠地识别影响范围。

目标系统来自用户当前请求与授权项目上下文，不预置任何业务系统的别名、模块或拓扑。

本技能重点回答：

- 业务链路从哪里开始，到哪里结束。
- 哪些外部系统、平台、目标系统模块参与。
- 每个关键节点的输入、输出、触发时点和责任边界是什么。
- 数据如何在模块间流动、落库、同步、被消费和被追溯。
- 关键流程如何保证幂等、可回退、可重跑、可补采、可重新加工。
- 需求中是否存在可借鉴的现有能力或机制，并和用户充分讨论后判断应复用、扩展还是新建。

判断设计质量时，同时检查三种复杂性症状：

| 症状 | 架构评审中的判断方式 |
|---|---|
| 多点修改（change amplification，原书常译“变更放大”） | 一个口径、流程或状态变化需要同步修改多少模块、接口、配置或人工规则。 |
| 理解负担（cognitive load，原书常译“认知负担”） | 一个开发者为了正确修改或排障，需要同时理解多少系统、概念、例外和时序。 |
| 隐藏影响点（unknown unknowns，常见直译“未知的未知”） | 修改前难以发现、容易遗漏的受影响位置，例如未记录的定时任务、状态判断或跨模块约定。 |

这些症状通常来自设计知识散落在多个模块、重要信息不清楚或不一致，以及特殊情况过多。复杂性是跨方案判断基线，不能只在单独章节中说明一次。

## 适用场景

当用户提出以下诉求时，优先使用本技能：

- 梳理目标系统技术架构、系统链路、模块边界、上下游关系。
- 评估新增业务场景：当具体功能逻辑或牵涉模块较多，至少覆盖跨服务、跨系统，或单模块内链路也相对冗长复杂，并可能带来较大范围改动时，使用本技能进行技术设计指导。
- 比较“复用或扩展现有机制”和“新建独立模块/合作开发/黑盒加工”等技术路线。
- 梳理跨模块数据流、数据同步平台/大数据平台同步、文件采集、外部系统上下场、日终/闭市流程。
- 输出面向领导或团队评审的架构设计概要、流程图、关键节点输入输出、风险和待确认项。
- 基于已有案例沉淀目标系统架构设计方法，识别可借鉴能力并论证是否适合复用。

模块和外部系统名称只用于初步导航，不能代替当前代码与需求证据。按 `references/project-baseline.md` 从当前项目采集基线，再以任务所用分支核对仓库、构建模块、代码包、启动/部署单元和业务责任方；只有需求、接口、配置、任务或用户确认能够证明参与关系时，才把系统放入当前架构图。

## 不适用场景

本技能不负责以下内容：

- Java 类、方法、Controller、Service、Mapper 的详细实现设计。
- DDL、表字段、索引、SQL、接口字段级契约。
- 单元测试、集成测试或 E2E 用例的详细编写。
- Confluence/Wiki 发布、Mermaid 渲染、附件上传。
- 代码修改和实施任务拆解。

这些阶段按用户请求由当前环境中可用的对应能力承接：前端方案可使用 `frontend-technical-solution-writer`，代码审查可使用 `frontend-code-review`；详细设计、开发、测试和 Wiki 发布按所在团队已授权的工具执行。它们不是本技能的必装依赖，缺失时仍可交付架构材料，不自行安装或发布。

架构阶段先确定模块边界、状态与数据所有权、恢复责任和候选接口行为，不能用 TDD 循环替代这些取舍。实现阶段若选择 TDD，由第三方 `test-driven-development` skill 承接；不采用 TDD 时，后续实施仍要给出相应验证证据。

## 用行为示例评估模块契约

用户希望以测试驱动开发（TDD）塑造边界时，架构阶段也应参与，不直接将问题转交实现阶段：

1. 从调用者可观察的业务结果出发，写出成功、不变量、错误、重复请求和恢复的行为示例，不展开字段或测试代码。
2. 检查表达一个行为需要准备多少内部状态、模拟多少组件、掌握多少调用顺序。mock 数量只是调查信号；区分真实外部依赖与内部编排泄露，不设机械数量阈值。
3. 比较候选契约：哪些规则和恢复步骤由责任模块封装，哪些输入、结果和错误必须暴露给调用方。用同一组行为示例验证候选，而不是把现有内部步骤逐一包装成接口。
4. 将示例反馈用于修正候选边界，并确认状态、数据和恢复责任；再由实现阶段执行红—绿—重构。行为测试应允许内部实现变化，避免绑定私有调用顺序。

这部分产物是可观察行为和边界取舍，不要求安装测试技能或编写测试代码。

## 本地环境依赖

本技能本身只依赖 Markdown，无本地运行时、CLI、MCP、外部服务或凭据依赖。

架构任务若涉及现有实现，优先读取用户指定的代码仓库。代码源以用户指定的 `<PROJECT_ROOT>`、仓库清单和授权范围为准；缺失时不要阻断概念设计，但必须把模块归属、调用链和存量行为标成证据缺口，不得用技能内的示例替代当前代码事实。若用户提供 Wiki、配置或其他材料，按对应读取技能及权限边界处理。

## 事实时效与证据规则

技能中的模块和外部系统名称用于帮助检索，不代表最新生产拓扑。每次涉及存量边界、复用或影响面时，按以下顺序核对：

1. 记录代码仓库、分支、提交号和核对日期。
2. 从当前技术栈的构建清单确认聚合模块，再检查运行入口、依赖、接口、任务和配置。Java 项目可用 POM、启动类和 Controller/Service 作为入口。
3. 区分“代码被某启动类扫描或依赖”和“业务责任由该模块持有”。例如 Spring 项目可能存在跨 package 的 `scanBasePackages`、`@ComponentScan` 和 Feign 扫描；这类加载关系不能直接证明业务责任方。
4. 用具体文件、类、任务或配置支撑职责判断。目录名、类名和历史方案只能作为搜索线索。
5. 将结论标成已确认事实、代码证据支持的判断、合理推断或待确认；代码与用户提供的生产事实冲突时，明确列出冲突并暂停涉及存量行为的决定。

只读取与当前问题直接相关的模块。不要为了“了解全貌”扫描整个仓库后输出一份很快过时的模块百科。

## 术语写法

关键技术概念第一次出现时，写成“直白中文理解（English original，必要时注明常见译法）”。后文使用直白中文，不单独堆放英文标签或容易误解的直译。统一术语见 `references/software-design-philosophy/source-and-method.md`。

例如：

- 隐藏影响点（unknown unknowns，常见直译“未知的未知”）。
- 简单接口封装大量能力（deep module，常见直译“深模块”）。
- 设计知识分散（information leakage），指同一设计知识散落在多个模块，不是安全意义上的数据泄漏。

代码标识、协议名和书中的英文术语原样保留，中文解释不能替代或改写这些标识。

## 面向读者的表达规则

架构输出不是读书笔记。默认读者没有读过《软件设计哲学》，也不应为了理解结论先掌握一套术语。

- 第一次使用专业概念时，写清对象、动作和影响。例如不要只写“稳定语义”，应说明“调用者能看到哪些输入、输出、错误和状态，哪些内部步骤不需要了解”。
- 标题、表头和图中短标签即使脱离上下文，也应能看懂。不要为了对仗或缩短篇幅省略“谁做什么、影响谁”。
- 避免单独使用“知识收拢”“理解成本外溢”“证据边界”“复杂性下沉”等抽象短语。需要表达这些意思时，直接写成“同一规则由一个模块维护”“调用者必须额外理解哪些内部步骤”“把事实、判断和待确认项分开”等可检查的陈述。
- 原书术语需要保留时，先使用自然中文，再在括号中标注英文原词。中文不能只做字面翻译。
- 面向团队宣贯、领导汇报或 PPT 时，可见文案只保留一项明确判断；案例条件、适用边界和来源放在同页说明或演讲稿中，但不能删除。
- 完成后逐项检查：不了解原书的工程师能否仅凭当前句子说明它指向的结构问题、判断方法和可能影响。不能则继续改写。

## 工作流

### 1. 先明确设计范围

先用 3 到 6 句话确认：

- 本次设计解决的业务问题。
- 本次链路的开始和结束位置。
- 本次只做架构设计，不进入详细设计。
- 哪些业务或模块明确不在范围内。
- 是否面向领导汇报、团队评审、后续开发拆解或知识库沉淀。

先应用 “Decide What Matters”：从需求中提炼 3 到 5 个真正决定架构的核心问题，并说明为什么重要。随后明确本次复杂性控制目标，例如减少跨模块修改点、降低调用方必须理解的状态、消除隐式依赖或隔离罕见分支。不要把所有事实赋予相同权重；重要约束必须出现在结论、边界或接口中心，不重要的实现细节应留到详细设计。

如果用户已经给出文档、Wiki、代码或会议纪要，先读取这些材料，再追问缺口。

### 2. 先沉淀基础输入和共同规则

在进入方案设计前，先把跨方案共用的事实单独整理出来，避免后续每个方案各说各话：

- 新增输入或新增业务场景是什么。
- 每类输入的业务源头、目标系统直接采集源头、中转平台、到达时点、刷新频率和补采方式。
- 进入目标系统后的用途，以及哪些模块消费。
- 基础业务规则、匹配规则、金额处理规则、账户口径、交易日/清算日口径。
- 哪些规则已确认，哪些只是生产样例落地前的待验证规则。
- 每项关键规则或数据口径由哪个系统或模块唯一持有，哪些消费者只需要看到稳定结果。
- 接口缺失值和默认值的来源、确认状态及权限边界。

对外部系统数据，必须区分“业务来源”和“目标系统直接采集来源”。例如业务来源可能是上游订单系统，但目标系统直接读取的是同步平台快照、文件或预处理结果表；分别标注业务生产者与本次读取来源。

### 3. 建立系统参与方清单

按三类列出参与方：

| 类型 | 内容 | 证据要求 |
|---|---|---|
| 外部系统/平台 | 按本次需求识别上游业务系统、客户端、管理端、同步平台、数据平台等实际参与方 | 接口、配置、任务、用户确认或正式文档 |
| 目标系统代码/运行单元 | 仓库、构建模块、代码包、启动单元、部署单元分别记录 | 根构建清单、模块构建配置、运行入口与实现 |
| 数据对象 | 订单、文件记录、快照、业务事件、处理结果、下游输出、对账数据等 | Entity/DTO、表或消息契约、生产数据口径 |

不要只写系统名。必须说明每个参与方在本链路中是数据生产者、消费者、加工者、编排者、状态维护者，还是展示/运营入口。

参与方清单还要标出关键规则的维护者，例如状态机、匹配口径、批次含义、回退规则和核心业务结果分别由谁唯一维护。若同一设计知识散落在多个模块，需要重复理解或同步修改，先标记为“设计知识分散（information leakage）”，再决定合并职责、统一跨模块输入输出和错误含义，还是保留现状并明确同步机制。不要仅按组织归属、技术层次或执行时序划分边界。

### 4. 梳理端到端主链路

按时间或业务阶段串起链路：

1. 外部输入或用户动作产生。
2. 数据进入目标系统或中转平台。
3. 数据在目标系统内部采集、加工、匹配、标准化或落库。
4. 核心业务模块消费数据。
5. 生成或更新业务结果。
6. 进入清算、估值、资金、闭市、上场或对账。
7. 处理异常、回退、重跑和补偿。

主链路要避免断点：如果设计从 T 日数据输入开始，且业务实际要到 T+1 上场或闭市检查才结束，文档也应覆盖到 T+1 收尾。

梳理主链路时同步标记复杂性热点：跨模块重复判断、依赖隐式时序、同一状态多处维护、调用方必须理解下游内部步骤、以及修改后难以枚举影响点。主链路图用于暴露这些问题，而不是证明链路“画完整了”就结束分析。

### 5. 按方案分别画图并写节点输入输出

不要为了套模板强行制造多套方案。只有当架构评估后发现存在真实不确定性，并且有两条或多条合理技术路线时，才输出多方案设计。

对影响边界、数据所有权、核心状态或长期演进的关键决策，先“至少比较两种设计（Design It Twice）”：构思两个实质不同的候选，再比较接口复杂度、内部设计知识能否封装、多点修改、理解负担和隐藏影响点。若约束使另一候选明显不可行，可记录被快速排除的候选及原因，不必为了形式扩写成完整方案。

一旦进入多方案设计，每个方案都必须形成相对完备、可独立评审的内容，不能只把推荐方案写细，把其他方案用一句话带过：

- 方案定位和适用前提。
- 方案架构图或多张流程图。
- 方案节点输入输出表。
- 责任模块和边界。
- 可借鉴的现有目标系统能力或机制。
- 本方案下的数据一致性、幂等、回退、重跑和监控方式。

不要把所有关键节点输入输出只放在一个“总表”里。总链路章节只保留共同输入和共同口径；方案章节内再分别列本方案的节点输入输出。这样读者评审单个方案时不需要来回翻页，也能避免两个方案的责任边界互相混淆。

如果最终只存在一条合理路线，也要说明为什么没有展开多方案，例如：存量架构约束已经确定、上下游接口只有一种可行接入方式、或其他路线会明显破坏既有边界。

### 6. 逐节点写清输入输出

每个关键节点都要用表格写清：

| 节点 | 输入 | 输出 | 仓库 / 构建模块 / 运行单元 / 业务责任方 | 触发方式/时点 | 说明 |
|---|---|---|---|---|---|

输入输出必须是可理解的数据对象，不要只写“处理数据”“调用接口”。例如：

- 输入：上游订单事件、库存快照、文件批次、标准化明细。
- 输出：标准化记录、候选匹配关系、业务处理请求、状态事件、下游输出批次。

如果需求中存在可借鉴的现有目标系统能力或机制，应补充模块或入口名称；但本技能只列架构参考，不展开代码级详细设计，也不能默认直接复用。

节点接口应让常见路径最简单：只暴露调用方作出正确决策所必需的信息，隐藏内部存储表示、重试编排和中间状态。判断是否做到“简单接口封装大量能力（deep module）”，要比较接口使用成本和它封装的有效能力，而不是只看参数或接口数量。

“常见路径最简单”不等于研发可以替业务决定默认结果。技术保护值可由服务根据容量和稳定性设置；如果会截断数据、改变用户看到的结果或影响业务时效，也要进入需求确认。业务日期、机构和范围必须由产品需求明确，且只有权威来源唯一时才能自动取得，否则显式传入或报错。权限始终服从授权策略。

### 7. 设计模块分工和边界

优先按规则由谁维护、模块能稳定提供什么能力来划分边界，使每项重要设计知识尽可能只由一个模块掌握。模块应做到“简单接口封装足够多的能力（deep module，原书直译‘深模块’）”；每一层都应把底层细节转换成上层可以直接使用的结果，避免多层使用同一模型和参数机械透传。

先区分仓库、构建模块、代码包、启动/部署单元、业务能力责任方。Java 项目分别可对应 Maven 模块、Java package 和 Spring 启动单元；其他栈使用实际组织方式。这些层次不一定一一对应，不能把运行时加载关系等同于业务职责。

本次模块基线按 `references/project-baseline.md` 采集。最终归属根据状态责任方、写入点、调用方向和运行配置判断；客户端、运营和管理入口也要通过真实接口与页面链路区分，不能凭模块或系统名称推断。

如果方案引入独立模块或合作开发边界，图和文字必须说明：

- 输入如何进入独立模块。
- 独立模块负责和不负责哪些结果。
- 目标系统核心模块如何消费这些结果。
- 数据交互采用数据同步平台、数据库同步、消息、服务 API 还是运营页面触发。
- API 的查询、控制和批量传输边界是否有容量与时效依据；跨服务大量查询是否需要消费侧本地数据，及其一致性代价。

对大批量明细，比较批量同步、消息、结果表与 API 的吞吐、时效、一致性和恢复成本。若收尾窗口依赖跨服务分页，必须给出容量和故障恢复证据；不能预设目标系统已有某种同步平台，也不能只因技术名称排除可行路径。

边界评审时主动识别以下危险信号：

- 按处理时序拆分（Temporal Decomposition）：按采集、加工、校验等执行先后拆分，但每层都依赖同一业务知识。
- 纯透传层（Pass-Through Method）：中间模块只把相同参数传给下一层，没有提供新的抽象。
- 设计知识分散（Information Leakage）：调用方仍需理解服务内部表结构、状态映射或恢复步骤。
- 低收益模块（Shallow Module，原书直译“浅模块”）：新增契约、部署和一致性成本，接近甚至超过它隐藏的能力。

发现危险信号只表示需要继续调查，不能脱离兼容性、性能、权限和存量稳定性直接判错或强制合并。

### 8. 数据流管理与一致性设计

架构设计中必须考虑：

- 批次号、业务日期（交易日、清算日等）、版本、来源系统、原始记录号。
- 标准化数据与原始数据的关系。
- 数据生产者与消费者是否数据库 schema 隔离。
- 跨模块数据是否通过数据同步平台同步，还是通过 API 查询。
- 消费侧是否需要读标、处理状态、关联登记或统一统计口径。
- 同一批数据被多个核心节点读取时，如何保证读取的是同一份加工结果。
- 数据变化后如何重新加工，已消费数据如何回退或重新关联。
- 同一数据格式、批次含义、状态转换和统计口径是否分别由一个明确模块维护，避免多个消费者复制实现。

不要把“数据已加工完成”直接等同于“业务已处理完成”。加工结果、核心消费状态、合约/事件/清算/资金结果通常应分层管理。

数据分层的目标不是增加层数，而是隔离容易变化的底层表示，由一个责任方维护口径，让上层只依赖明确的业务结果。若每层仍要求上层理解相同字段和状态，说明只是形式分层，没有降低理解负担。

### 9. 幂等、回退、重跑与异常恢复

关键流程图必须体现幂等和恢复设计，至少覆盖：

- 重复采集：同一来源、同一批次、同一原始记录如何去重。
- 重复加工：仅未发布且未被消费的临时结果可按明确策略覆盖；已发布或已消费的结果必须保留，修正时生成关联的新版本。
- 重复消费：核心模块二次读取同一加工结果时如何避免重复簿记、重复清算、重复上场。
- 回退：业务回退时，哪些状态由核心模块维护，哪些状态需要通知前置加工模块。
- 重跑：回退后从哪个节点重跑，使用原批次、修正批次还是新批次。
- 补采/补加工：上游迟到、缺失、修正后如何重新进入链路。
- 异常阻断：哪些异常阻断闭市或上场，哪些只进入监控待办。

恢复顺序必须清晰，不能把重新加工、回退、补偿和重试当成同一操作：

1. 固定输入版本、规则版本与旧结果，明确已消费范围及责任方；重新加工生成可追溯的新结果版本，不覆盖已发布或已消费的历史。
2. 先判断已发生的副作用。责任范围内可逆的状态按契约回退；跨系统或不可逆副作用采用可审计的前向补偿，例如关联原通知的更正通知。若无法安全补偿，阻断并转人工处置，不宣称已恢复。
3. 输入与副作用处置明确后，才从已知检查点按指定批次和版本重试，落实幂等、防重复消费及最终对账；不能简单重放全部原业务。
4. 迟到、缺失或修正输入需保留来源标识、原业务时间、应到与实到时间、补采批次和去重规则，并明确是否重开已收尾流程、由谁批准及如何对账。

接口或操作级幂等还要区分三类请求，不能笼统写成“重复请求返回成功”：

- 同一幂等标识且参数相同，通常是同一请求重试：复用首次结果或返回当前处理中状态，业务副作用不得再次发生。
- 同一幂等标识但参数不同：返回幂等冲突，不得复用首次结果。
- 使用新标识重复提交同一业务：这是新的重复业务，按产品需求和业务唯一性规则提示“已经提交”或返回业务冲突，不能伪装成一次新的成功处理。

只有当操作契约本来就定义为“确保达到某个目标状态”时，目标已经达到才可以作为正常结果，例如清理临时状态时对象本来就不存在。真正无法达到目标状态，或出现资金、订单、权限、核心状态和数据一致性冲突时仍要报错。可统一恢复的复杂性由最了解规则的模块处理，避免所有调用方重复捕获并忽略同一异常。

如果流程图较复杂，拆成多张图：主链路图、模块交互图、回退重跑图。不要为了塞进一张图而牺牲准确性。

### 10. 闭市、上场、对账等收尾环节

当需求涉及日终、闭市、上场、对账或其他收尾环节时，要单独写清：

- 收尾流程从哪个节点开始，以哪个结果作为通过条件。
- 闭市或调度节点只检查状态，还是会执行明细加工。
- 哪些异常阻断收尾，哪些进入人工待办。
- 如果需要重跑，回到哪个节点，使用哪个批次或版本。
- T+1 或后续日期的数据输出由哪个模块发起，输出内容是什么。

原则上，不建议把大批量明细加工放到闭市检查节点现场执行。闭市更适合接入批次状态、结果状态、异常汇总和核心业务结果。

这是“由最合适的责任模块集中处理复杂性（Pull Complexity Downwards）”的具体应用：与采集、加工、校验相关的问题应由对应责任模块在收尾前解决一次，闭市节点只观察影响收尾决策的状态。责任模块不能借此吸收与自身职责无关的业务策略。

### 11. 数据质量监控备忘

在架构设计阶段先形成监控备忘，即使规则还没完全确认，也要提示后续需要落地：

- 输入批次是否缺失或延迟。
- 关键字段是否缺失、重复或无法匹配。
- 数据版本、读取标记、交易日/清算日口径是否一致。
- 金额、数量、比例等结果是否守恒或可追溯。
- 核心业务结果是否缺失。
- 上场、通知、对账、闭市状态是否一致。

监控项要写清检查对象、检查口径和处理建议，不能只写“增加监控”。

监控设计应让重要事实容易找到：核心批次、阻断状态、业务结果和责任方必须可快速定位；低价值细节应聚合或按需展开。若异常只能通过跨多个系统拼接日志才能判断，应视为理解负担和隐藏影响点风险。

### 12. 方案对比与案例论证

当存在多条技术路线时，按以下维度对比：

| 维度 | 方案一 | 方案二 |
|---|---|---|
| 数据加工位置 |  |  |
| 核心模块改动范围 |  |  |
| 上下游交互方式 |  |  |
| 闭市/上场接入方式 |  |  |
| 回退重跑复杂度 |  |  |
| 数据一致性风险 |  |  |
| 外部协作或供应商可见性 |  |  |
| 后续扩展性 |  |  |
| 多点修改：一个变化涉及多少位置 |  |  |
| 理解负担：正确修改需要掌握多少信息 |  |  |
| 隐藏影响点：是否存在事前难以发现的遗漏 |  |  |

案例论证要说明需求中哪些部分可借鉴现有目标系统链路或机制，并分别评估复用、扩展和新建的代价。是否复用不能由 Agent 单方面默认决定；当复用会影响模块边界、数据口径、闭市链路、性能、回退重跑或后续扩展时，必须和用户充分讨论并记录最终选择。结论中要区分已确认事实、可借鉴参考、推荐方案、放弃方案和待确认项。

方案比较不能只统计改动文件、服务数量或短期工期。还要说明每个方案消除了哪些复杂性、保留并封装了哪些复杂性、把哪些复杂性转嫁给了调用方，以及未来相邻需求需要理解和修改什么。最小闭环改动不等于最小 diff；优先选择在当前范围内稳定、可回退，同时不会持续放大长期维护成本的方案。

存量系统性能优化先用当前基线定位主要瓶颈，改后同条件复测并设置撤回条件。新架构或容量设计则写清性能目标、容量假设、原型或压测计划和验收标准；两类场景都不能只凭直觉引入缓存、并发或特殊分支。

### 13. 收敛关键改动点和推进顺序

架构文档最后先按模块列出关键改动、存量影响、风险、待确认项、推进顺序和后续承接阶段。涉及存量演进时，从近期真实变更记录选取痛点，选择一个可独立验证的最小切片；没有历史证据时列为待验证假设，不能编造收益。明确旧契约兼容期、新旧状态的唯一写入责任、观测指标、切换条件和撤回路径。切流开关不等于数据或副作用可回退。用下一次真实相邻变更复核修改位置、理解负担与遗漏是否减少，再决定扩大范围，避免一次性重写。

评审收尾形成与这些章节互相引用的五项结论：

1. 变更影响：涉及哪些消费者、触发入口、状态、配置、权限及恢复路径，有哪些遗漏待核验。
2. 规则所有权：列出必须一致的不变量、口径与状态，明确唯一维护、解释并负责的模块。
3. 行为契约：调用者必须知道哪些输入、结果、错误和状态，用哪些行为示例验证，哪些内部细节由模块处理。
4. 恢复闭环：输入与规则版本、结果版本、已消费范围、回退或补偿、重试顺序及最终对账是否明确。
5. 演进验证：最小切片、兼容期、观测指标、撤回条件和下一次真实变更的验证安排；不涉及存量迁移时说明不适用，并列出当前验证证据与缺口。

三项复杂性问题用于暴露成本，不要求机械得到“一处、很少、全部”的答案；按当前需求风险选择检查项。

- 需要将原则或书中案例转成目标系统架构评审问题时，读取 `references/software-design-philosophy-integration.md`。
- 需要核对当前仓库结构、模块标识和已知边界风险时，按 `references/project-baseline.md` 采集任务时的实际代码与配置证据。

完成前按 `references/architecture-checklist.md` 做一次自检，重点确认：

- 架构图是否体现所属模块和整体时序。
- 关键节点是否都有输入输出。
- 外部系统和目标系统模块边界是否清晰。
- 存量边界是否有当前分支、提交号和具体代码或配置证据，是否区分构建模块、运行单元与业务责任方。
- 数据流、读标、批次、版本、状态、回退、重跑是否覆盖。
- 是否避免进入代码级详细设计。
- 是否形成变更影响、规则所有权、行为契约、恢复闭环和演进验证五项结论，并说明多点修改、理解负担和隐藏影响点如何处理。

最终回复给用户时，优先说明：

- 结论。
- 已完成的架构梳理内容。
- 仍需业务或技术同事确认的事项。
- 后续可交给哪个技能继续细化为技术方案、Wiki 或实施文档。

对外表述时，不得仅凭本 skill 断言某项检查已经成为目标系统团队规范；需要时先核对团队实际采用情况。

## 完整使用示例

概述：以复杂性控制方法评估软件架构、模块责任和恢复路径。

输入：库存系统新增供应商到货文件，可以由库存模块直接加工，也可以独立预处理后同步；现有代码不可访问。

输出：先列输入、批次与共同规则，分别比较两条实质可行路线；每条路线提供节点输入输出、状态责任、重复请求与参数冲突处理、回退重跑和容量验证计划。模块归属标为待核验，不能把示例当当前拓扑。结尾按第 13 节说明变更影响、规则所有权、行为契约、恢复闭环和演进验证；不进入类/SQL 详细实现，也不宣称具备上线条件。
