# Software Complexity Design

## 用途与边界

本 skill 用于需要跨越模块、运行单元或系统边界的设计判断。它关注未来变化是否集中、使用者需要理解多少内部信息，以及影响点能否被可靠发现。

适合：

- 确定数据、状态、规则和恢复责任；
- 比较服务边界或数据流方案；
- 设计幂等、回退、重跑、补偿和收尾；
- 评审细粒度接口、透传层和隐式时序；
- 用 TDD 的行为示例反推稳定契约与边界；
- 规划大型项目的渐进式架构演进和变更复杂度控制；
- 编写软件复杂性评审指南。

不适合：

- 类、方法、字段、SQL 或 CRUD 的详细设计；
- 边界已确定后的普通测试实现和代码拆解；
- 单元测试或代码编写；
- 文档发布和外部系统写入。

遇到不适用请求时，简短说明边界，不强行执行完整流程。

## 本地环境依赖

本 skill 只依赖 Markdown，没有固定 CLI、MCP、外部服务、凭据或运行时依赖。

判断存量事实需要用户提供或授权访问代码、配置和正式文档。材料不足时可以提出候选设计，但必须把存量职责和行为列为证据缺口。

## 复杂度雷达

| 雷达维度 | 可观察问题 |
|---|---|
| 变更传播范围 | 一个决定会同步触达哪些代码、配置、契约、监控和操作入口？其中哪些入口事前无法直接发现？ |
| 决策信息负担 | 修改者为了作出一个正确决定，必须临时掌握多少状态、时序、系统和例外？ |
| 恢复确定性 | 失败或数据修正后，能否明确选择补采、重新加工、回退、补偿和重跑，并证明最终一致？ |
| 演进摩擦 | 新场景是否持续增加特例，还是可以通过可观测、可撤回的小切面逐步演进？ |

“变更传播范围”综合观察 change amplification 与 unknown unknowns；“决策信息负担”借鉴 cognitive load。英文短术语只用于来源识别，评审必须落到当前系统可观察事实。

## 四遍评审法

四遍分别回答：我们知道什么、变化会穿过哪里、谁应承担什么、如何证明设计可运行。

### 第一遍：建立决定与证据账本

先写一张决定卡：

| 项目 | 内容 |
|---|---|
| 目标结果 | 本次设计最终要保证什么 |
| 链路边界 | 从哪个输入或动作开始，到哪个业务结果结束 |
| 关键决定 | 3–5 个会改变边界、正确性或长期成本的问题 |
| 范围外 | 本轮不进入的实现细节和相邻流程 |
| 读者 | 谁评审、谁实施、谁运营 |

涉及现有实现时，建立证据账本：

| 结论 | 仓库 | 构建模块 | 代码包 | 运行/部署单元 | 业务责任方 | 分支/提交/工作区状态/日期 | 证据 | 等级 |
|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  | 代码 / 配置 / 文档 / 用户确认 | 事实 / 判断 / 推断 / 待确认 |

规则：

- 记录未提交差异，避免把工作区行为错误归因到当前提交。
- 包扫描、依赖和目录名只能帮助导航，不能证明业务所有权。
- 职责判断要落到状态写入点、数据模型、契约、任务配置和调用方向。
- 证据冲突时保留各自来源，暂停依赖该事实的决定。
- 只调查当前决定需要的范围，不建立系统百科。

### 第二遍：做变化演练

选择一个当前需求和一个可能的相邻变化，分别沿链路演练：

1. 输入如何产生、接入和标识；
2. 哪些地方解释格式、规则或状态；
3. 核心结果在哪里形成；
4. 哪些消费者和后台入口会受到影响；
5. 日终、交付、对账或其他收尾如何完成；
6. 失败后从哪里恢复。

为每次演练记录：

| 变化 | 修改位置 | 必须理解的信息 | 可能漏掉的入口 | 恢复路径 |
|---|---|---|---|---|
|  |  |  |  |  |

这一步的产物是复杂性热点，而不是漂亮的流程图。重点寻找重复解释、隐式时序、多处状态和只能依靠个人经验发现的影响点。

### 第三遍：设计责任与契约

为重要知识指定维护者：

| 知识或结果 | 唯一维护者 | 稳定输出 | 调用者必须知道 | 模块内部封装 |
|---|---|---|---|---|
| 数据格式/版本 |  |  |  |  |
| 状态机/不变量 |  |  |  |  |
| 匹配或计算口径 |  |  |  |  |
| 幂等与恢复语义 |  |  |  |  |
| 核心业务结果 |  |  |  |  |

每个关键节点还要写明具体输入、输出、触发方式和责任方。不要用“处理数据”代替契约。

边界评审问题：

- 接口成本是否小于它封装的有效能力？
- 中间层是否只转发相同参数、模型和错误？
- 是否按执行顺序拆分，却让每层理解同一规则？
- 调用者是否仍需了解内部表、状态映射或恢复步骤？
- 通用机制是否混入具体场景策略？

危险信号只触发调查。不要脱离存量兼容、容量、权限和团队责任机械合并或拆分。

### 第四遍：比较候选并设计证明

关键决定至少构思两个实质候选。候选可以在边界、数据所有权或恢复责任上不同；不要为了数量制造伪方案。

按同一维度比较：

| 维度 | 候选 A | 候选 B |
|---|---|---|
| 恢复闭环与最终对账 |  |  |
| 演进切面、兼容与撤回 |  |  |
| 契约意图、错误与测试负担 |  |  |
| 变化传播范围与遗漏风险 |  |  |
| 知识权威与决策信息负担 |  |  |
| 权限、性能和存量兼容 |  |  |
| 运维与收尾 |  |  |

约束已排除的候选，只记录排除原因。

为推荐方案设计证明：

- **一致性**：来源、批次、版本、业务日期、读标和消费状态；
- **幂等**：同键同参重试复用结果，同键异参冲突，新键重复业务按唯一性规则处理；
- **恢复**：谁发起回退，谁维护状态，重跑使用哪个批次或版本；
- **监控**：检查对象、口径、阻断条件、处理动作和责任方；
- **收尾**：通过条件、待办、下游交付和重新进入链路的入口；
- **性能**：存量场景使用基线、复测和撤回条件；新场景使用目标、容量假设和验收计划。

迟到、缺失和修正数据必须形成闭环：

1. **补采**处理原始输入迟到或缺失：保留来源标识和原业务时间，记录应到/实到差异、补采批次、去重键，以及是否需要重开收尾。
2. **重新加工**处理输入修正或规则变化：绑定输入版本与规则版本，生成可追溯的新结果版本，不直接覆盖已经发布或消费的结果。
3. **已消费结果处置**先判断下游副作用：
   - 可逆且仍由当前责任方控制时，执行回退，恢复到明确前态；
   - 已跨系统或不可原地撤销时，执行补偿，产生可审计的前向修正；
   - 输入和副作用已处置、检查点明确后，再从指定批次或版本重跑。
4. 补偿、回退和重跑不能互相替代。文档必须说明执行顺序、状态维护者、已消费范围、重复执行保护和最终对账方式。

不要无证据预加缓存、并发或特殊分支。真正无法完成、权限、核心状态和一致性冲突必须保持显式失败。

## TDD 与架构演进的使用方式

### TDD 设计

TDD 在本 skill 中用于澄清行为，不替代边界决策：

1. 先写调用者可观察的行为示例、不变量、错误和恢复结果；
2. 用测试前置条件和 mock 数量识别调用方被迫理解的内部知识；
3. 比较不同契约如何减少测试编排和状态泄漏；
4. 确认数据、状态、规则和恢复责任后，再进入实现级红绿重构；
5. 外部行为测试固定稳定契约，内部测试允许实现演进。

如果测试必须复现多个模块的内部顺序，先回到第三遍重新设计责任与契约，而不是继续增加测试夹具。

### 大型项目演进

演进任务从真实变化历史出发：

- 选取最近的相邻需求、缺陷或恢复事件，记录修改位置和遗漏点；
- 找到频繁变化但由多处解释的知识；
- 选择一个可独立验证的切面收拢责任或统一契约；
- 为旧路径提供兼容期、观测指标和撤回条件；
- 用下一次真实变化的修改数量、理解成本和遗漏率验证收益；
- 只有证据支持时才扩大到下一切面。

这是一条渐进路线，不是一次性重写许可。

## 五控制面交付门禁

交付前逐项过门：

| 门禁 | 必须具备的证据 |
|---|---|
| 变化面 | 当前需求与相邻变化均完成演练；修改位置、消费者、触发入口和可能遗漏点可枚举 |
| 知识面 | 数据、规则、状态和恢复语义的权威解释者有证据；冲突责任已关闭或明确列为阻塞 |
| 契约面 | 调用者意图、结果、错误、权限和版本可由行为示例验证；外部测试不依赖内部编排 |
| 恢复面 | 迟到/缺失、规则修正和已消费结果都有补采、重新加工、回退/补偿、重跑与对账顺序 |
| 演进面 | 最小迁移切面、旧路径兼容、观测指标、撤回条件和下一次真实变化的验收方式已定义 |

五项均有证据后，才能给出推荐方向、适用前提和推进顺序。任一门禁依赖推断时，明确阻塞决定或给出补证据动作，不用完整文档掩盖缺口。
