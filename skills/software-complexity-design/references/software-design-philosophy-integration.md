# 软件设计哲学在目标系统架构设计中的应用

本文把 John Ousterhout《A Philosophy of Software Design》的原则转化为目标系统架构设计动作。它不是独立的理论章节；使用时应回到 `SKILL.md` 对应步骤、输出模板和检查清单中完成判断。

## 1. 应用目标

架构设计的目标不只是证明需求可以实现，还要控制开发者完成未来正确变更所需掌握的信息量。评审时持续检查三种复杂性症状：

| 症状 | 目标系统架构表现 | 设计目标 |
|---|---|---|
| 多点修改（change amplification，原书常译“变更放大”） | 一个口径或状态变化需要同时修改多个模块、同步任务、监控规则和人工流程 | 由一个责任模块维护规则，并统一跨模块输入、输出和错误含义 |
| 理解负担（cognitive load，原书常译“认知负担”） | 修改或排障必须同时理解多套状态、内部表结构、隐式时序和罕见配置 | 简化常见路径，由合适模块封装必要复杂性 |
| 隐藏影响点（unknown unknowns，常见直译“未知的未知”） | 修改前不知道某个依赖或影响点存在，因此不会主动检查 | 让重要约束明确、集中、可追溯 |

依赖、设计知识分散（information leakage）、重要信息不清楚或不一致，以及特殊情况累积，是上述症状的常见成因。

## 2. 原则到工作流的映射

| 目标系统架构步骤 | 主要原则 | 必须形成的设计判断 |
|---|---|---|
| 明确范围 | Decide What Matters | 哪 3–5 个问题真正决定边界、正确性和长期成本；哪些细节留到详细设计 |
| 沉淀输入与共同规则 | 设计知识封装（Information Hiding） | 关键口径由谁唯一维护；消费者需要哪些结果和错误信息，哪些内部步骤不应暴露 |
| 建立参与方清单 | Knowledge Ownership | 状态机、匹配口径、批次语义、回退规则和核心结果分别由谁负责 |
| 梳理主链路 | Complexity Symptoms | 哪些节点造成多点修改、上下文跨越或影响点不可发现 |
| 形成候选方案 | Design It Twice | 是否存在实质不同的边界或数据所有权方案；为何选择或排除 |
| 写节点输入输出 | 简单接口封装大量能力（Deep Modules）/ 让常见用法最简单（Common Case Simple） | 接口是否封装足够能力；常见调用是否无须理解内部步骤和罕见选项；默认值是否有技术规则、产品约定或权威上下文依据 |
| 设计模块边界 | 不同层提供不同抽象（Different Layer, Different Abstraction） | 每层是否把底层细节转换成上层可以直接使用的结果；是否存在纯透传层、按时序拆分或低收益模块 |
| 数据流与一致性 | 设计知识封装（Information Hiding）/ 一致性（Consistency） | 格式、版本、状态和统计口径是否集中维护；分层是否真正隔离变化 |
| 幂等与恢复 | Define Errors Out of Existence | 是否区分同一请求重试、新的重复业务和参数冲突；哪些目标状态操作可消除无价值异常；哪些金融关键错误必须显式保留 |
| 闭市与收尾 | 由最合适的责任模块集中处理复杂性（Pull Complexity Downwards） | 加工问题是否由责任模块提前解决；收尾节点是否只观察重要状态 |
| 监控与异常 | Make Important Things Obvious | 阻断状态、核心结果和责任方是否可直接定位，而非跨系统猜测 |
| 方案对比 | Complexity over Change Lists | 每个方案消除、封装或转嫁了什么复杂性；未来变更要理解和修改什么 |
| 改动与推进 | Strategic Programming | 最小闭环是否同时保护存量稳定和长期可维护性，而非机械追求最小 diff |

## 3. 从书中案例转成目标系统评审问题

书中案例用于帮助识别结构问题，不能作为“场景相似所以方案必然正确”的类比证明。先从案例提炼设计知识、接口成本或异常语义，再回到当前代码、数据和业务约束验证。

| 书中案例 | 可迁移的判断 | 目标系统架构评审问题 |
|---|---|---|
| HTTP 请求读取与解析共享协议知识 | 共享同一设计知识的步骤不应只因执行先后被拆开 | 采集、解析、标准化和校验是否被按时序分散，但每一层都重复理解同一文件格式、字段口径或状态语义？ |
| Unix 文件 I/O 与 Java I/O | 常见路径应由简单接口直接完成，罕见能力再单独暴露 | 服务 API 或公共组件是否要求调用方按顺序拼装批次查询、明细读取、异常判断和恢复步骤？ |
| “无选择”表示为空选择区 | 统一表示可以把特殊情况纳入正常路径 | 空批次、无匹配结果、重复回退等状态能否由正常数据模型和幂等语义表达，而不是新增一套旁路流程？ |
| Tcl `unset` 与 Unix 已打开文件删除 | 只有操作契约定义为“确保达到目标状态”时，目标已达到才可作为正常结果 | 清理、删除或回退是否适合定义成目标状态操作；同一请求重试、新的重复业务和参数冲突是否仍被分别处理；资金、订单、权限和核心状态失败是否保留信号？ |
| Decorator 与纯透传方法 | 新层必须提供不同抽象或真实能力 | Controller、Service、Client、独立服务之间是否只是原样转发相同参数、状态和错误，却新增部署、权限和故障边界？ |
| 透传变量与 context object | 无关中间层不应被迫理解低层参数 | 批次号、机构号、来源标记或恢复参数是否穿过大量不使用它们的节点；集中上下文后是否又形成可变的隐式总线？ |
| `block` 同时表示逻辑块与物理块 | 名称必须让不同语义的误用变得显眼 | “批次”“状态”“业务日期”“结果”等跨模块词汇是否对应唯一口径，还是同名字段在不同模块代表不同生命周期？ |
| 事件处理器和后台线程 | 隐式控制流必须提供可追踪入口和生命周期 | XXL-JOB、消息订阅、回调、Spring 扫描和后台任务的触发源、执行单元、重试及结束条件是否可以从设计和代码入口可靠找到？ |
| RAMCloud Buffer 优化 | 性能优化应先测量，并优先消除关键路径上的浅层调用和重复检查 | 闭市窗口或大批量链路的瓶颈是否有基线；方案是在责任模块内做根本修正，还是用缓存和并发把复杂性扩散到所有节点？ |

若案例暴露的问题与当前链路不一致，停止类比，按实际证据重新判断。完整案例和章节语境见 `software-design-philosophy/chapter-notes.md`。

## 4. 模块边界评审

### 4.1 简单接口封装大量能力（deep module，原书直译“深模块”）

模块或服务只有在隐藏的复杂性明显大于新增接口、部署、故障和一致性成本时，才形成有价值的边界。重点检查：

- 常见使用者需要理解多少概念、参数和调用步骤。
- 调用方是否仍需掌握内部表结构、状态映射、重试或补偿顺序。
- 新业务是否总要穿透边界修改模块内部。
- 模块是否提供安全、正确且自然高效的默认路径；默认值是否有技术规则、产品约定或权威上下文依据。

服务更小、接口更多不等于解耦。若只是把原有步骤搬到远端，反而可能增加跨系统复杂性。

默认行为用于封装调用方不应重复选择的知识，不是替产品决定业务结果。技术保护默认可由服务设置；如果会截断数据、改变用户看到的结果或影响业务时效，也要进入需求确认。业务日期、机构或范围由产品需求明确，只有来源唯一可追溯时才自动取得；否则显式输入或报错。权限始终以授权策略为边界。

### 4.2 设计知识封装（information hiding）与知识责任

先问“这项重要知识由谁唯一掌握”，再决定模块归属。适合集中隐藏的知识包括：

- 状态机和业务不变量。
- 账户、交易日、清算日、金额和匹配口径。
- 批次、版本、读标和恢复语义。
- 外部协议、数据格式、兼容和校验规则。
- 核心合约、事件、清算、资金和上场结果的定义。

若同一知识散落在多个模块，应比较三种路径：合并职责；统一跨模块输入、输出与错误含义；或保留重复但建立显式同步和验证机制。不要默认通过增加公共工具类解决，因为共享代码不一定消除知识所有权分散。

### 4.3 危险信号

| 信号 | 目标系统场景中的表现 | 调查方向 |
|---|---|---|
| 低收益模块（Shallow Module，原书直译“浅模块”） | 新服务只包装查询或转发，却引入部署、权限和故障边界 | 是否合并、提高接口层级或取消无价值边界 |
| 设计知识分散（Information Leakage） | 多个模块重复解释同一状态、字段或回退含义 | 指定一个模块统一解释，或统一各模块依赖的输入、输出与错误含义 |
| 按处理时序拆分（Temporal Decomposition） | 按采集、处理、校验顺序拆模块，但每层依赖相同业务规则 | 是否按知识和能力重组边界 |
| 纯透传层（Pass-Through Method） | 中间层原样传递参数、状态和错误 | 是否删除空层或赋予不同抽象 |
| 暴露过多内部细节（Overexposure） | 常见调用必须提供罕见配置或理解内部版本 | 对已确定的技术规则提供默认处理，业务默认值保留产品需求或权威来源依据，并隔离高级能力 |
| 通用机制与特定业务混杂（Special-General Mixture） | 通用同步或加工平台直接理解特定产品策略 | 分离稳定机制与业务策略 |
| 难以简洁说明（Hard to Describe） | 接口或状态必须用很长的前置条件才能说明 | 简化契约、状态模型或责任划分 |
| 重要事项被隐藏（Important Things Are Hidden） | 阻断条件、数据责任方或关键口径只存在于经验中 | 提升到接口、名称、监控和中心设计记录 |

危险信号用于触发调查，不是脱离业务约束直接判错的规则。

## 5. 方案比较方法

对每个候选方案同时回答：

1. 本方案消除了哪些复杂性。
2. 哪些复杂性无法消除，由哪个模块封装。
3. 哪些复杂性被转嫁给调用方、运维或其他团队。
4. 一个相邻需求变化时，需要修改多少位置。
5. 新接手者需要掌握哪些跨模块上下文。
6. 所有影响点是否能从接口、数据责任归属、监控和设计记录中找到。
7. 常见路径是否简单，罕见路径是否隔离。
8. 性能、兼容、权限、回退和金融正确性约束是否仍然满足。

`Design It Twice` 要求对重要决策比较实质不同的候选，但不要求为了模板制造多套完整方案。约束已经排除的路线，记录候选及排除理由即可。

评审收尾时再问：同一规则要改几处，调用者要理解多少内部信息，消费者、触发入口、状态、配置、权限和恢复路径能否全部找到。最终按主文形成五项结论：变更影响、规则所有权、行为契约、恢复闭环和演进验证；保留不变量、责任方、内部封装与验证证据。

## 6. 使用边界

- 最小闭环改动不等于最小 diff。不得借复杂性治理之名扩大成无关重构，也不能为了少改文件永久保留明显的多点修改（change amplification）和隐式依赖。
- 由底层责任模块集中处理复杂性（Pull Complexity Downwards）只适用于与模块核心职责相关、可以一次解决的问题，不能让底层模块理解所有业务。
- 消除异常不能吞掉资金、订单、权限、核心状态和数据一致性所需的信息。
- 适度通用不是预测未来需求；接口使用稳定基础概念，实现范围仍由当前需求约束。
- 架构原则不能替代性能测量、兼容验证、权限审查和业务确认。
- 存量性能优化以当前基线、主要瓶颈和同条件复测为依据；新架构或容量设计使用性能目标、容量假设、原型或压测计划和验收标准，不要求先证明一个尚不存在的真实瓶颈。
- TDD 导向架构可先用可观察行为示例评估候选契约，并通过 mock、内部状态准备和顺序负担识别职责泄露；明确模块边界、状态所有权、数据所有权和恢复责任后，再进入逐项实现验证。严格循环来自第三方 `test-driven-development` skill，不属于作者原话或目标系统既有规范。
