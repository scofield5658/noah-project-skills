# 目标系统架构设计检查清单

## 1. 范围与目标

- [ ] 是否说明本次设计解决的业务问题。
- [ ] 是否说明链路起点和终点。
- [ ] 是否明确本次只做架构设计，不做技术详细设计。
- [ ] 是否列出范围内和范围外事项。
- [ ] 是否说明文档面向团队评审、后续开发拆解还是知识库沉淀。
- [ ] 是否区分已确认事实、建议方案、代码支持的判断、合理推断和待确认，并避免把技能示例当作当前事实。
- [ ] 是否提炼了 3 到 5 个真正决定架构的核心问题，而不是把所有事实等量罗列。
- [ ] 是否明确本次要减少的多点修改（change amplification）、理解负担（cognitive load）或隐藏影响点（unknown unknowns）。
- [ ] 重要约束是否放在结论、边界、接口或中心设计记录中，能够被后续修改者发现。
- [ ] 涉及存量实现时，是否记录代码仓库、分支、提交号和核对日期。

## 2. 新增输入与共同规则

- [ ] 是否列出新增业务输入或新增业务场景。
- [ ] 是否区分业务来源和目标系统直接采集来源。
- [ ] 是否说明中转平台、到达时点、刷新频率、补采方式。
- [ ] 是否说明每类输入进入目标系统后的用途。
- [ ] 是否说明基础业务规则、匹配规则、账户口径、交易日/清算日口径。
- [ ] 是否标出生产样例落地前仍待验证的规则。
- [ ] 每项关键口径或规则是否有唯一维护者；消费者是否只依赖明确的结果、状态和错误，而不必理解内部处理步骤。
- [ ] 默认值是否注明技术规则、产品需求或权威上下文依据；会截断数据、改变业务结果或业务时效时，是否进入需求确认，并在来源不唯一时显式输入或报错。
- [ ] 权限范围是否始终服从授权策略，没有因参数缺失或产品默认而放宽。

## 3. 系统参与方

- [ ] 是否列出所有外部系统或平台。
- [ ] 是否按本次真实链路核对上游、客户端、管理端、同步与数据平台等相关方，未机械套用示例清单。
- [ ] 是否列出目标系统内部参与模块。
- [ ] 是否说明每个参与方是数据生产者、消费者、加工者、编排者、状态维护者还是展示/运营入口。
- [ ] 是否区分客户端系统入口和运营管理平台入口。
- [ ] 是否分别记录仓库、构建模块、代码包、启动/部署单元和业务责任方。
- [ ] 是否避免根据目录名、类名、`scanBasePackages`、`@ComponentScan` 或 Feign 扫描范围直接认定业务归属。
- [ ] 是否标出状态机、匹配口径、批次含义、回退规则和核心业务结果分别由谁维护。
- [ ] 同一知识若由多个模块掌握，是否识别设计知识分散（information leakage）风险并说明处理方式。

## 4. 主链路与流程图

- [ ] 是否画出端到端主链路。
- [ ] 流程图是否体现所属模块。
- [ ] 流程图是否体现整体时序。
- [ ] 复杂链路是否拆成主链路图、模块交互图、回退重跑图。
- [ ] 链路是否覆盖到实际业务收尾，例如闭市、上场、对账或 T+1 数据准备。
- [ ] 是否先评估是否真的存在多条合理技术路线，而不是为了套模板强行制造多方案。
- [ ] 如果存在多方案，是否每个方案都有独立架构图、节点输入输出表和架构设计解读。
- [ ] 如果只有单方案，是否说明没有展开多方案的原因。
- [ ] 是否在主链路中标出重复判断、隐式时序、多处状态维护和难以发现的影响点。
- [ ] 关键决策是否至少构思过两个实质不同的候选；快速排除时是否记录约束和原因。

## 5. 关键节点输入输出

- [ ] 每个关键节点是否写清输入。
- [ ] 每个关键节点是否写清输出。
- [ ] 每个关键节点是否写清责任模块或系统。
- [ ] 是否说明触发方式、触发时点或调度来源。
- [ ] 输入输出是否是具体数据对象，而不是“处理数据”等泛化表述。
- [ ] 是否说明现有目标系统参考链路或模块。
- [ ] 多方案下是否避免只写一个孤立总表，而是在各方案内分别写节点输入输出。
- [ ] 输出契约是否只暴露调用方正确决策所需的信息，并隐藏内部存储、状态映射和恢复步骤。
- [ ] 常见路径是否简单，罕见配置和高级控制是否被隔离。

## 6. 模块分工与边界

- [ ] 是否说明哪些逻辑留在核心模块。
- [ ] 是否说明哪些逻辑可以放到独立模块或前置加工模块。
- [ ] 是否以当前项目代码、配置和写入点核对实际模块边界。
- [ ] 涉及多个服务或仓库时，是否按仓库和构建证据区分独立服务与内部模块，而非凭名称判断。
- [ ] 是否避免把合约、事件、清算、资金等核心结果错误下放到前置加工模块。
- [ ] 是否通过页面和接口链路区分客户端操作与运营管理入口。
- [ ] 如果引入独立模块，是否说明输入同步、预处理结果同步、服务 API 查询/控制边界。
- [ ] 是否按容量、时效和恢复证据评估大批量明细传输方式，而非预设某种通道必然适用。
- [ ] 模块封装的能力是否明显大于新增接口、部署、故障和一致性成本，避免低收益模块（shallow module，常见直译“浅模块”）。
- [ ] 是否按知识所有权和稳定能力划分边界，而不是只按组织、技术层次或执行时序拆分。
- [ ] 不同层是否提供不同抽象，避免相同参数、模型和错误的机械透传。
- [ ] 危险信号是否只用于触发调查，没有脱离兼容性、性能和存量约束机械套用。

## 7. 数据流管理

- [ ] 是否说明数据源头是外部原始来源、平台同步结果，还是目标系统内部结果。
- [ ] 是否说明数据生产者和消费者。
- [ ] 是否说明数据落库、同步、查询和消费方式。
- [ ] 是否考虑数据库 schema 隔离。
- [ ] 大批量数据是否优先评估数据同步平台或批量同步，避免频繁跨模块查询。
- [ ] 是否设计批次、版本、来源记录号、交易日、清算日等追溯字段。
- [ ] 是否设计读标、消费状态、关联登记或统一统计口径。
- [ ] 是否说明加工结果、核心消费状态和核心业务结果分层管理。
- [ ] 是否说明同一批数据被多个核心节点读取时如何保证版本一致。
- [ ] 数据格式、批次语义、状态转换和统计口径是否集中到明确责任方，避免消费者复制实现。
- [ ] 数据分层是否真正隐藏了不稳定表示，而不是只增加层数和透传。

## 8. 幂等、回退、重跑

- [ ] 已发布或已消费的结果是否保留；重加工是否绑定输入版本、规则版本并产生关联的新结果版本。
- [ ] 是否先查明已消费范围及副作用，再由责任方选择可逆回退或不可逆场景的可审计补偿，最后从明确检查点重试并对账。
- [ ] 无法安全补偿时是否阻断并转人工，而非重放完整业务或假定回退成功。
- [ ] 迟到或补采是否记录来源标识、原业务时间、应到与实到时间、补采批次、去重及重开收尾条件。
- [ ] 是否说明重复采集如何处理。
- [ ] 是否说明重复加工如何处理。
- [ ] 是否说明重复消费如何避免重复业务结果。
- [ ] 是否区分同一请求重试、同一标识参数冲突和使用新标识产生的重复业务，并保证副作用只发生一次。
- [ ] 是否分别定义复用首次结果、返回处理中、提示“已经提交”和返回冲突的条件，而不是重复请求一律成功。
- [ ] 是否说明回退由哪个模块发起或维护状态。
- [ ] 是否说明回退后是否需要通知前置加工模块。
- [ ] 是否说明重跑使用原批次、修正批次还是新批次。
- [ ] 是否说明补采、补加工、人工修正后的恢复链路。
- [ ] 流程图是否体现关键回退和重跑路径。
- [ ] 是否说明核心侧回退与前置加工侧回退的先后关系。
- [ ] 是否确保资金、订单、权限、核心状态和数据一致性所需错误仍然显式可见。
- [ ] 只有操作契约定义为“确保达到目标状态”时，是否才把目标已达到作为正常结果；真正无法达到目标状态时是否仍返回错误。
- [ ] 恢复复杂性是否由最了解规则的模块集中承担，没有散落给所有调用方。

## 9. 收尾流程

- [ ] 如果涉及闭市、上场、对账或 T+1 数据准备，是否说明收尾起点、通过条件和输出内容。
- [ ] 是否说明闭市或调度节点只做状态接入，还是执行明细加工。
- [ ] 是否避免在闭市窗口内现场执行跨服务大批量明细加工。
- [ ] 是否说明哪些异常阻断收尾，哪些进入人工待办。
- [ ] 采集、加工和校验问题是否由最合适的责任模块集中处理（Pull Complexity Downwards），收尾节点只观察重要状态。
- [ ] 集中处理复杂性时是否仍保持职责边界，没有让底层模块吸收无关业务策略。

## 10. 监控与异常

- [ ] 是否列出采集缺失、字段缺失、匹配失败、金额不平、重复数据等监控项。
- [ ] 是否说明哪些异常阻断闭市、上场或核心处理。
- [ ] 是否说明哪些异常只进入待办或人工确认。
- [ ] 是否说明数据质量问题如何补采、重跑或回退。
- [ ] 监控项是否写清检查对象、检查口径和处理建议。
- [ ] 核心批次、阻断状态、业务结果和责任方是否能够直接定位。
- [ ] 是否避免必须跨多个系统拼接日志才能判断关键异常。

## 11. 方案对比与案例论证

- [ ] 如果存在多条路线，是否按同一维度对比。
- [ ] 每条合理方案是否都具备相对完备的架构图和设计解读，而不是只详写推荐方案。
- [ ] 是否说明数据加工位置、核心模块改动范围、上下游交互方式、回退重跑复杂度和扩展性。
- [ ] 是否识别需求中可借鉴的目标系统现有能力或机制。
- [ ] 是否分别论证复用、扩展和新建的代价。
- [ ] 是否避免默认复用现有链路。
- [ ] 当复用会影响模块边界、数据口径、闭市链路、性能、回退重跑或后续扩展时，是否要求和用户充分讨论并记录结论。
- [ ] 是否比较每个方案的多点修改（change amplification）、理解负担（cognitive load）、隐藏影响点（unknown unknowns）、设计知识封装（information hiding）和接口收益。
- [ ] 是否说明每个方案消除、封装、保留和转嫁了哪些复杂性。
- [ ] 是否避免只按改动文件数、服务数量或短期工期选择方案。
- [ ] 存量性能优化是否有当前基线、主要瓶颈、同条件复测和撤回条件；新架构或容量设计是否有性能目标、容量假设、验证计划和验收标准。
- [ ] 关键设计决定是否记录选择理由、快速排除的候选、必须保持的规则、规则维护者和事实依据。
- [ ] 跨模块约束是否只保留一份正式记录，并在相关模块或文档入口留下可发现的引用。

## 12. 关键改动与推进

- [ ] 是否按模块或系统列出关键改动点。
- [ ] 每个关键改动是否映射到要解决的架构问题或复杂性症状，而不是只有动作描述。
- [ ] 是否列出主要风险和待确认项。
- [ ] 是否给出建议推进顺序。
- [ ] 是否区分最小闭环改动与机械追求最小 diff，避免无关重构，也避免固化明显隐式依赖。
- [ ] 是否说明后续详细技术方案、Wiki 发布或实施文档由哪个技能承接。
- [ ] 是否形成变更影响、规则所有权、行为契约、恢复闭环和演进验证五项结论。
- [ ] 存量演进是否从真实近期变更选取最小切片，定义兼容期、唯一写入方、观测指标、切换及撤回条件。
- [ ] 是否用下一次真实相邻变更验证修改位置、理解负担与遗漏是否减少，再决定扩大范围；缺少历史证据时是否标记假设。
- [ ] 是否按需求风险选择检查项；新检查固化前是否先在真实需求中验证收益和维护成本。

## 13. 边界检查

- [ ] 是否没有进入类、方法、SQL、字段级详细设计。
- [ ] 是否没有把 Wiki 发布、代码实施、测试用例编写混入本技能输出。
- [ ] TDD 导向设计是否以调用者可观察行为评估候选契约，检查 mock、内部状态准备及顺序依赖是否暴露内部编排；是否避免按 mock 数量机械划界。
- [ ] 是否将行为示例反馈到边界取舍，明确状态、数据与恢复责任后再进入实现阶段；测试是否允许内部实现变化，不绑定私有调用顺序。
- [ ] 关键技术概念第一次出现时，是否同时保留英文原文和直白中文理解。
- [ ] 是否避免单独使用“未知的未知”“深模块”“复杂性下沉”等需要读者猜测含义的直译。
- [ ] 标题、表头和图中短标签脱离上下文后，是否仍能说明“谁做什么、影响谁”。
- [ ] 是否避免单独使用“知识收拢”“稳定语义”“证据边界”“理解成本外溢”等抽象短语，并改写为可检查的对象、动作和结果。
- [ ] 面向未读过原书的读者时，每个术语是否都能从当前句子直接理解，而不需要查阅术语表。
