# Software Complexity Design 四遍评审清单

按风险选择检查项。任何一遍发现关键证据缺失，都应把相关结论降级为推断或待确认。

## 第一遍：决定与证据

### 决定卡

- [ ] 目标结果是否可以用一句话说明？
- [ ] 链路起点、终点和范围外事项是否明确？
- [ ] 是否只保留 3–5 个会改变边界、正确性或长期成本的问题？
- [ ] 是否说明谁评审、谁实施、谁运营？

### 证据账本

- [ ] 是否分别记录仓库、构建模块、代码包、运行/部署单元和业务责任方？
- [ ] 是否记录分支、提交、工作区状态和核对日期？
- [ ] 职责判断是否有状态写入点、契约、数据模型、任务配置或调用方向支撑？
- [ ] 是否避免用目录名、依赖或扫描范围直接证明业务所有权？
- [ ] 是否区分事实、证据支持判断、推断和待确认？
- [ ] 证据冲突是否保留各自来源，而非静默选择一个版本？

## 第二遍：变化演练

- [ ] 是否同时演练当前需求和一个可能的相邻变化？
- [ ] 每次演练是否覆盖输入、规则解释、结果形成、消费者、收尾和恢复？
- [ ] 是否列出真实修改位置，而非只写受影响“模块”？
- [ ] 是否列出修改者必须额外理解的信息？
- [ ] 是否盘点后台任务、订阅、回调、人工入口和其他难发现触发源？
- [ ] 是否标出同一规则多处实现、相同状态多处维护和隐式时序？
- [ ] 变化传播与遗漏风险、决策信息负担、恢复确定性和演进摩擦是否都有具体证据？

## 第三遍：责任与契约

### 所有权

- [ ] 数据格式、版本、状态机、业务口径、恢复语义和核心结果是否各有维护者？
- [ ] 维护者是否对结果含义负责，而不只是执行一个步骤？
- [ ] 同一知识若分散，是否选择集中、统一契约或显式同步？
- [ ] 编排者是否只维护时序，没有复制领域规则？

### 契约

- [ ] 输入、输出、错误、版本、权限和触发方式是否明确？
- [ ] 输出是否有稳定含义，而不是暴露内部状态映射？
- [ ] 常见调用是否表达业务意图，而不是拼接内部步骤？
- [ ] 中间层是否提供新抽象，而非机械透传？
- [ ] 新边界隐藏的能力是否大于新增接口、部署和故障成本？
- [ ] 技术默认值是否会改变结果、范围、时效或权限？若会，是否进入确认？

## 第四遍：候选与证明

### 候选比较

- [ ] 关键决定是否构思至少两个实质候选？
- [ ] 快速排除的候选是否记录约束和原因？
- [ ] 候选是否按相同维度比较所有权、接口成本和恢复方式？
- [ ] 是否说明各候选消除、封装和转嫁的复杂性？
- [ ] 推荐方向是否写明成立前提？

### 幂等与恢复

- [ ] 是否区分同键同参重试、同键异参冲突和新键重复业务？
- [ ] 是否说明谁发起回退、谁维护状态和谁执行补偿？
- [ ] 重跑使用原批次、修正批次还是新版本是否明确？
- [ ] 迟到/缺失数据是否有应到/实到判断、补采批次、去重和收尾重开规则？
- [ ] 输入修正或规则变化是否通过重新加工生成新版本，而非覆盖已发布结果？
- [ ] 已消费结果是否明确选择回退或补偿，并说明最终对账？
- [ ] 是否保证先补采/重新加工、再处置已消费副作用、最后从明确检查点重跑？
- [ ] 权限、核心状态和一致性错误是否仍显式失败？

### 监控、收尾与性能

- [ ] 监控是否写清对象、口径、阻断条件、动作和责任方？
- [ ] 收尾是否有通过条件、人工待办和重新进入链路的入口？
- [ ] 核心批次、阻断状态、业务结果和责任方能否直接定位？
- [ ] 存量优化是否有基线、复测和撤回条件？
- [ ] 新架构是否有目标、容量假设和验收计划？

## 交付门

- [ ] 是否给出推荐结论、事实分层、所有权、稳定契约和验证证据？
- [ ] 是否列出风险、待确认项和推进顺序？
- [ ] 是否保持架构层级，没有进入类、字段或语句级详细设计？
- [ ] 是否没有为套模板制造多余方案、层次或文档？
