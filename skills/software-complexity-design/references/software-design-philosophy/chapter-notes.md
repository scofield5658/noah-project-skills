# 变更生命周期现场笔记

本文件使用独立的问题域和顺序组织软件复杂性经验，不复刻第三方著作的章节推进、原则清单或案例叙述。来源与采用边界见 [source-and-method.md](source-and-method.md)。

## 现场一：变更尚未开始

### 先问什么会变化

不要从现有目录或组织图开始。先选择一个具体变化：

- 新增一种输入或业务场景；
- 修改一个跨模块口径；
- 修正迟到数据；
- 替换一个外部依赖；
- 调整一个收尾条件。

列出变化必须穿过的代码、配置、契约、监控和操作入口。无法列全时，先解决可发现性，而不是直接选方案。

### 建立当前证据

涉及存量系统时记录：

- 仓库、分支、提交和工作区状态；
- 构建模块、代码包和运行单元；
- 状态写入点、数据模型和触发入口；
- 正式契约、配置和实际运行事实；
- 事实、判断、推断和待确认的边界。

名称和依赖只能帮助定位。真正的责任要从写入、解释和结果承担关系判断。

## 现场二：正在决定边界

### 绘制知识地图

把设计知识按问题域列出：

| 问题域 | 要找的维护者 |
|---|---|
| 输入格式和版本 | 谁接受变化并输出稳定表示 |
| 状态和不变量 | 谁允许或拒绝状态转换 |
| 业务口径 | 谁解释结果含义 |
| 恢复语义 | 谁决定回退、补偿和重跑 |
| 收尾条件 | 谁判断链路可以结束 |

同一知识被多处解释时，有三种选择：收拢责任、统一契约，或保留分散但建立明确同步和一致性验证。

### 计算边界收益

边界会新增接口、版本、部署、权限、监控和故障模式。它只有在减少调用者必须理解的信息时才产生收益。

检查：

- 调用者是在表达业务意图，还是组合内部步骤；
- 输出能否直接用于决策，还是暴露内部状态；
- 新场景是否总要穿透边界修改底层；
- 失败恢复是否集中在掌握规则的一方；
- 常见路径是否需要大量罕见选项。

## 现场三：用 TDD 形成契约

### 从行为示例开始

在实现前写出：

- 正常行为和可观察结果；
- 业务不变量；
- 参数冲突和权限错误；
- 处理中、失败和恢复后的状态；
- 重试与重复业务的区别。

这些示例用于比较契约候选，不直接决定模块归属。

### 让测试摩擦暴露设计问题

测试出现以下情况时回到边界评审：

- 一个场景必须编排许多低层调用；
- 需要 mock 多个模块的内部状态；
- 外部行为测试依赖内部调用顺序；
- 一个规则变化导致大量测试夹具一起修改；
- 错误断言只能检查技术异常，无法表达业务结果。

先判断摩擦是否来自真实业务复杂度。如果只是知识泄漏，调整契约后再继续红绿重构。

### 分层保留测试

- 外部行为测试固定稳定结果、不变量、错误和恢复；
- 契约测试验证跨边界协议；
- 内部测试允许跟随实现变化；
- 端到端测试只覆盖关键集成，不复制全部内部组合。

## 现场四：系统已经运行

### 把恢复当成正常设计对象

运行系统迟早会遇到迟到、缺失、重复和修正数据。恢复设计要区分：

- 补采：补齐原始输入，保留来源和业务时间；
- 重新加工：用明确输入版本和规则版本生成新结果；
- 回退：可逆副作用恢复到已知前态；
- 补偿：不可原地撤销时产生前向修正；
- 重跑：前置数据和副作用处理完毕后，从检查点重新执行。

顺序不明确时，重跑可能重复副作用或覆盖已消费结果。

### 让状态可以直接判断

监控不只统计成功率，还应回答：

- 当前批次使用哪个输入和规则版本；
- 哪个结果已发布、哪些消费者已处理；
- 阻断原因和责任方是谁；
- 是否允许重开收尾；
- 人工动作如何审计和去重。

如果这些问题只能跨系统拼日志回答，理解负担已经进入运行阶段。

## 现场五：大型项目持续演进

### 用变更历史选择切面

回看最近几次需求和缺陷：

1. 哪些位置反复一起修改；
2. 哪些知识在多个团队重复解释；
3. 哪些入口最容易遗漏；
4. 哪些兼容约束阻止一次性调整；
5. 哪个切面可以独立观测和撤回。

优先选择频繁变化、收益可测、失败可退的切面，不从最抽象的平台层开始。

### 双路径迁移

大型项目演进通常需要：

- 旧路径保持权威或可随时切回；
- 新路径影子计算或小流量运行；
- 差异可解释并有明确责任方；
- 状态和副作用避免无控制双写；
- 兼容期结束条件提前定义。

完成新实现不是成功标准。使用下一次真实变化验证：

- 修改位置是否减少；
- 新参与者需要理解的信息是否减少；
- 影响点是否更容易发现；
- 回退和恢复是否更直接；
- 新边界是否真的隐藏了复杂性。

## 现场六：决定如何留下

只记录未来修改需要的内容：

- 选择了什么以及适用前提；
- 哪些候选被排除，为什么；
- 不变量和责任方；
- 调用者契约与内部封装；
- 重新评估条件；
- 验证、观测和撤回证据。

不要用文档数量衡量设计质量。重要的是下一位修改者能否快速形成正确判断。
