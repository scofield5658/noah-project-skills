## 前言：软件设计是一种可训练的能力

### 核心命题

- 软件设计的中心任务是问题分解：把复杂问题拆成可以相对独立处理的部分。
- 设计能力并非只能依赖天赋。有效训练方式更接近写作课：实现、接受评审、重写，再把具体问题与设计原则对应起来。
- 全书是基于长期实践形成的一套观点和启发式规则，不是不可质疑的定律。判断标准始终是它是否真的降低复杂性。

### 书中案例

- 作者在 Stanford 的 CS 190 中让学生从零实现一套有一定规模的软件，再进行多轮 Code Review 和重写。这不是“讲完原则后考试”，而是像写作课一样，通过初稿、批评和改稿训练问题分解。
- 这些原则来自作者约 25 万行代码和多类系统的实践，包括三个操作系统、文件与存储系统、调试器、构建系统、GUI 工具包、脚本语言和交互式编辑器。前言据此提醒读者：全书是经验提炼，不是形式化定理。

### 对大型团队的启发

- 设计能力建设不能停留在规范宣贯，应建立“设计稿/代码—同行批评—重做—复盘”的训练闭环。
- 团队需要共享判断设计的词汇，否则评审容易退化成个人风格争论。
- 原则必须由真实代码和变更成本校验；若原则与降低复杂性的总目标冲突，应调整原则而非维护教条。

<a id="chapter-1"></a>
## 第 1 章 Introduction：一切围绕复杂性

### 核心命题

- 软件开发的主要瓶颈不是表达能力，而是人对不断增长系统的理解能力。
- 对抗复杂性有两条路径：直接消除复杂性，以及把不可避免的复杂性封装起来，让开发者一次只接触局部。
- 软件可塑，设计不是一次性阶段，而是贯穿生命周期的持续活动；增量开发必须同时意味着持续重设计。
- 本书原则适用于类、函数、子系统和网络服务，不限于面向对象代码。

### 危险信号

- 把设计冻结在项目早期，实施阶段只允许“绕开”设计问题。
- 看到问题后只追加补丁，不回到抽象和边界上修正。
- 把任何单一原则推到极端，而不比较它对整体复杂性的实际影响。

### 书中案例

- 瀑布模型把需求、设计、编码和测试切成顺序阶段，并在设计阶段结束后冻结总体结构。作者指出，大型软件的设计问题通常到实现中期才暴露；若原设计者已经转到别的项目，实施者只能绕着问题打补丁，复杂性随之激增。
- 增量开发是对照案例：先实现一小部分功能，利用实现反馈修正原设计，再扩展下一批能力。作者用“桥梁施工中途很难改变支撑塔数量”作比较，说明软件的可塑性使持续重设计成为可能。

### 对大型团队的启发

- 架构治理应覆盖系统全生命周期，不能仅设置立项评审或上线前评审。
- Code Review 是训练复杂性感知最有效的日常载体；评审应要求识别危险信号并比较替代设计，不能只检查正确性和格式。
- 技术方案需要明确哪些复杂性被消除、哪些被封装、由哪个边界承接。

## 第 2 章 The Nature of Complexity：复杂性的本质

### 核心命题

- 复杂性是任何使系统难以理解和修改的结构特征；规模大、功能多不必然等于复杂。
- 系统复杂性应按开发者实际接触频率加权。把复杂性隔离在极少触碰的位置，效果接近消除它。
- 三种外在症状：多点修改（change amplification，原书常译“变更放大”）、理解负担（cognitive load，原书常译“认知负担”）、隐藏影响点（unknown unknowns，常见直译“未知的未知”）。隐藏影响点最危险，因为开发者在修改前根本不知道还存在需要检查的地方。
- 两个根因：依赖与模糊性。依赖不可消灭，但可以减少，并替换为简单、显式、可由工具检查的依赖。
- 复杂性由大量微小问题渐进累积，因此必须对新增复杂性保持近乎零容忍。

### 危险信号

- 小变更要修改多个位置，且这些位置由隐含约定关联。
- 完成任务前需要掌握大量全局信息、调用顺序、资源责任或例外规则。
- 修改者无法可靠列出影响点，只能依赖全局搜索、个人经验，或等到问题在线上暴露。
- 以代码行数代替认知成本评估设计；更短的实现可能更难找到正确用法。
- 作者认为代码“很简单”，但其他维护者普遍难以理解。复杂性由读者体验决定，而非作者熟悉度决定。

### 书中案例

- 作者用网站背景色说明多点修改（change amplification）：旧网站在每个页面分别写背景色，换颜色必须修改所有页面；把颜色集中成 `bannerBg` 后，页面只依赖一个显式入口，编译器和搜索也能帮助发现引用。
- 同一案例还说明“依赖不能消失，只能被重组”：页面之间的隐式一致性依赖，被替换为所有页面对统一 API/变量的显式依赖。后者更容易查找、修改和校验。
- 书中另举状态码为例：增加新状态时还要同步更新消息表，但消息表的存在可能不为修改者所知。这正是隐藏影响点（unknown unknowns），问题不在于改动多，而在于修改者甚至不知道还要改哪里。

### 对大型团队的启发

- 技术设计评审可用三项症状做统一量尺：一次需求要改几处、参与者要理解多少信息、能否穷举影响点。
- 应优先治理高频变更路径上的复杂性，而不是平均用力追求全仓库形式整洁。
- 接口、编译检查、schema 和自动化校验的价值之一，是把隐式依赖转成显式依赖；但它们不能替代清晰设计。
- 隐藏影响点（unknown unknowns）应列为高风险：跨模块隐含约束、未记录的数据口径、散落的状态映射都应在评审中重点拦截。

## 第 3 章 Working Code Isn't Enough：能运行还不够

### 核心命题

- 战术式编程优先让当前任务尽快工作；每次妥协都很小，但会持续积累补丁和复杂性。
- 战略式编程把长期结构放在首位：目标是产出一个恰好也能正确运行的好设计，并持续为未来扩展降低成本。
- 投资既包括前置比较多个设计、预想未来变化、写文档，也包括发现问题后立即修正而非绕开。
- 作者建议持续投入约 10%–20% 的开发时间做设计投资，强调这是经验性量级，而非排期公式。
- 大规模前置设计仍然无效；理想设计通过许多连续的小投资逐渐显现。

### 危险信号

- 团队奖励“交付最快的人”，却不核算后续维护者的清理成本。
- 以当前 deadline 为由把结构问题推迟到“以后”，但没有可执行的偿还机制。
- 在已有设计问题上继续叠加绕行补丁，形成越乱越不敢改的反馈循环。
- 把增加人手视为清理意大利面代码的主要方案。

### 书中案例

- “战术龙卷风”（tactical tornado）是作者给出的团队人物画像：这类工程师交付功能很快，管理者容易把他视为英雄，但后续工程师要花大量时间清理其留下的结构问题，反而显得进度慢。
- Facebook 早期的 “Move fast and break things” 被作者用作战术式文化案例：新工程师很快提交生产代码，但代码缺少注释和测试、难以理解且不稳定。后来口号改为 “Move fast with solid infrastructure”，表明基础设施和设计投资已经成为约束条件。
- Google 和 VMware 是对照案例：二者同样处于高速成长阶段，却重视代码质量和设计，并借此形成能吸引优秀工程师的技术文化。作者的结论不是“慢就是好”，而是战略式投入可以与商业成功并存。

### 对大型团队的启发

- 绩效和项目度量不能只看功能吞吐，还应观察返工、多点修改（change amplification）、缺陷逃逸和他人维护成本。
- 设计投资应进入日常 Definition of Done，而不是独立的、永远排不到的“技术债项目”。
- 管理者需要保护持续的小额设计预算；这种文化也直接影响高级工程人才的吸引和留存。
- 紧急交付可以是例外，但例外必须显式记录其复杂性成本、偿还条件和责任人。

## 第 4 章 Modules Should Be Deep：用简单接口封装大量能力

### 核心命题

- 模块由接口和实现组成。使用者应理解本模块的接口，而无需理解其他模块的实现。
- 接口包括签名、类型和异常等形式信息，也包括行为、约束、调用前提等非形式信息；后者往往更多，只能靠清晰文档表达。
- 抽象是省略不重要细节后的简化视图。它既不能暴露无关细节，也不能遗漏使用者真正需要的信息；后者会形成“虚假抽象”。
- 高封装模块（deep module，原书直译“深模块”）用简单接口提供大量功能。接口是使用成本，封装的能力是收益；Unix 文件 I/O 和垃圾回收是书中的典型例子。
- 低收益模块（shallow module，原书直译“浅模块”）增加了新接口，却几乎没有封装复杂性。盲目追求小类、小方法会形成大量低收益接口，即作者所称的 classitis。
- 接口应让常见路径最简单，把少见选项隔离开；Unix I/O 的默认顺序访问优于要求每个用户显式组装缓冲能力的 Java I/O。

### 危险信号

- 模块的文档和调用成本不低于直接理解其实现。
- 一个包装方法只是换名转发，调用者仍需知道底层存储或行为细节。
- 仅以行数阈值拆类、拆方法，导致大量需要一起阅读和配置的组件。
- 常用能力必须通过多层对象或参数手工拼装，忘记其中一步就产生正确性或性能问题。
- 抽象看似简洁，却隐去了持久化时机、事务语义、资源所有权等调用者必须知道的信息。

### 书中案例

- Unix 文件 I/O 只用 `open/read/write/lseek/close` 五个基本系统调用，就隐藏了目录解析、权限、缓存、设备差异、调度等大量实现知识；数十年间实现发生巨大变化，核心接口仍保持稳定。这是高封装模块（deep module）的正例。
- Java 读取序列化对象时，调用者需要依次组装 `FileInputStream`、`BufferedInputStream` 和 `ObjectInputStream`。缓冲几乎总是需要，却必须显式选择；忘记包装不会报错，只会让 I/O 变慢。作者以此说明 classitis 会把常用机制拆成一串低收益模块（shallow modules）。
- 垃圾收集器是更极端的高封装模块：实现很复杂，却没有调用接口，还删除了手工释放对象的接口，使系统对开发者暴露的概念反而更少。

### 对大型团队的启发

- 服务、SDK、公共组件同样要评估“深度”：以少量稳定概念承接足够多的业务或技术复杂性。
- API 数量、参数数量、必读文档量和调用编排步骤都是接口成本，不应被“职责单一”口号遮蔽。
- 平台能力应默认覆盖主流正确用法，把罕见调优能力放到高级入口；避免让每个业务团队重复选择基础机制。
- 设计评审不能只问“职责是否拆开”，还要问拆分后是否减少了跨模块依赖和总体理解负担（cognitive load）。

## 第 5 章 Information Hiding (and Leakage)：集中封装设计知识，避免知识散落

### 核心命题

- 设计知识封装（information hiding，原书常译“信息隐藏”）不是把字段设为 `private`，而是让某个设计决策只被一个模块知道，并从外部接口中消失。getter/setter 仍可能把私有表示完整暴露出去。
- 封装设计知识既降低使用者的理解负担（cognitive load），也把未来变更限制在一个模块内；部分封装也有价值，例如让少数高级用法不干扰多数调用者。
- 设计知识分散（information leakage）是同一知识出现在多个模块。它可能出现在公开接口中，也可能表现为多个模块各自解释同一文件格式、协议或约定；这里不是安全意义上的数据泄漏。
- 按运行时间顺序拆模块容易形成按处理时序拆分（temporal decomposition）。模块应围绕“完成任务所需的知识”组织，而非围绕“先做 A 再做 B”的步骤组织。
- HTTP 示例表明：读取请求与解析请求共享协议知识，应合并；参数来自 URL 还是 body、采用何种编码，都应由 HTTP 模块隐藏。
- 返回内部 `Map` 等表示会造成浅接口；按调用者所需返回单值、类型化值更能隐藏表示和转换机制。
- 好的默认值是设计知识封装（information hiding）的一部分：模块应在常见场景自动处理已经确定的技术规则，只为少数例外提供独立覆盖入口；会改变业务结果的默认值仍需产品需求或唯一权威来源依据。

### 危险信号

- 多个模块都理解同一种数据格式、状态映射、序列化细节或业务口径。
- 代码按请求接收、转换、保存等时间步骤拆分，但各步骤重复使用相同领域知识。
- API 直接暴露内部集合、存储结构或可变对象，并要求调用者“不要乱改”。
- 常见功能迫使调用者理解罕见选项，即暴露过多内部细节（overexposure）。
- 模块通过大量配置项把本可自动判断的实现知识暴露给调用者或运维人员。

### 书中案例

- 在学生实现的 HTTP 服务中，一个类从 socket 读取请求字符串，另一个类再解析字符串。由于必须先读出 `Content-Length` 才知道 body 何时结束，“读取”本身已经要理解请求格式，结果两类重复协议知识；合并读取与解析后，协议知识只留在一处，调用者也只需一次调用。
- 学生正确隐藏了参数来自 URL 还是 body，并在 HTTP 模块内完成 URL decoding；但不少实现用 `getParams()` 直接返回内部 `Map`。作者建议改为 `getParameter(name)`、`getIntParameter(name)`，既隐藏存储表示，也把字符串转整数这类重复工作封装起来。
- 生成 HTTP 响应时，有团队要求调用者显式给出协议版本和 `Date`。协议版本其实可由请求推导，时间也可自动生成；把二者设为默认值后，常见调用不再接触这些知识，罕见覆盖需求再使用专门入口。

### 对大型团队的启发

- 服务边界应按“知识所有权”划分：协议语义、数据口径、状态机和校验规则应有唯一权威实现。
- 技术方案应列出关键设计知识及其责任方，检查是否在多服务、多端或多批任务中重复编码。
- SDK/中间件不要向业务方暴露内部传输对象和可变表示；应提供贴近使用意图但不绑定具体业务动作的接口。
- 技术默认值属于平台治理能力。常见的安全性、超时、重试、缓冲和协议版本选择应由平台承担，而不是让每个接入团队重新学习；业务日期、机构、查询范围和权限不能由平台静默猜测。

<a id="chapter-6"></a>
## 第 6 章 General-Purpose Modules are Deeper：适度通用的接口能封装更多能力

### 核心命题

- “适度通用”不是预测所有未来需求：实现能力只覆盖当前需要，但接口用基础概念表达，不绑定当前 UI、流程或单一场景。
- 通用接口的首要收益不是未来复用，而是现在就能减少方法数量、设计知识分散（information leakage）和跨类耦合，让简单接口封装更多能力。
- 文本编辑器的 `backspace`、`delete`、`deleteSelection` 都绑定 UI 动作；用基于位置范围的 `insert/delete` 可由少量基础操作组合出当前及未来能力。
- 通用不等于原子化到难用。只支持单字符操作虽然通用，却会把循环、范围处理和性能问题推给调用者。
- 判断问题包括：覆盖当前需求的最简单接口是什么、一个方法能服务多少场景、当前核心用例是否仍然直接易用。

### 第二版增补

- 作者进一步把过度专用化视为软件复杂性的主要来源之一，并将“消除特殊情况”纳入本章主线。
- 专用逻辑应与通用机制清晰分离：通常把专用策略推到上层；设备驱动等场景也可把硬件专用实现推到底层，中间保留通用接口。
- Undo 示例把能力拆成三层：通用的动作历史机制、每类动作的专用 undo/redo 实现、由上层决定动作分组的策略。三者各自只理解必要知识。
- 特殊情况应尽量通过正常表示消除。例如“无选择”可表示为空选择，使复制、删除等普通逻辑天然处理它，而无需状态分支。

### 危险信号

- 公共方法以一个具体页面、按键、工单类型或单一调用点命名。
- 新增一个上层功能就必须在底层模块新增一个对应方法。
- 为了看起来通用而堆积参数、策略接口和未被当前需求验证的能力。
- 同一基础动作存在多个只差少量条件的专用 API 或特殊分支。

### 书中案例

- GUI 文本编辑器的文本类最初为 UI 动作提供 `backspace`、`delete`、`deleteSelection`。每新增一个 UI 操作，底层文本类就要新增方法。作者将它改成 `insert(position, text)` 和 `delete(start, end)`：删除键、退格键和删除选区都由同一组范围操作表达，文本类不再了解按键和选区。
- 作者没有把“通用”推到单字符 API。若 `insert/delete` 一次只处理一个字符，上层必须写循环，批量编辑还会变慢；以字符范围为单位才同时满足通用性和当前编辑器的直接用法。
- 第二版增加“空选择”案例：不再用布尔状态表示“当前没有选区”，而是始终保留一个选择对象；无选区时起止位置相同。复制 0 字节、删除空范围都沿正常路径执行，从表示层消除了特殊分支。
- 第二版还用设备驱动说明专用代码不一定只向上推：操作系统核心保留 `read a block`、`write a block` 等通用接口，各设备的专用命令集下沉到驱动实现，中间层因而无需了解硬件差异。

### 对大型团队的启发

- 平台与领域核心 API 应围绕稳定的基础语义设计；具体渠道、页面和流程编排留在上层适配。
- 通用机制、专用动作、业务策略应明确分层，避免一个“万能服务”既管理基础机制又了解所有业务类型。
- 评审 API 时可统计“一次性方法”和“每个新场景新增方法”的比例，它们常提示接口过度专用。
- 对规则分支先问能否通过统一数据表示、空对象、默认行为或不变量纳入正常路径。

<a id="chapter-7"></a>
## 第 7 章 Different Layer, Different Abstraction：不同层应有不同抽象

### 核心命题

- 每增加一层、接口、参数或类都会增加认知成本；它必须隐藏或消除更多复杂性，才有净收益。
- 相邻层若提供几乎相同的抽象，常表现为纯透传层或方法（pass-through method）：只把相同参数转发到底层。这说明职责划分不清，并同时增加接口和依赖。
- 合理的相同签名包括 dispatcher 和同一接口的多种实现；它们提供了选择实现或替代实现的真实功能，且通常位于同一层。
- Decorator 容易为少量扩展制造大量透传方法。新增装饰器前应比较：并入底层、并入特定用例、合并现有装饰器或做成独立组件。
- 接口抽象应不同于内部表示。内部按行存文本，不代表 API 也应按行；按字符范围操作可隐藏拆行、并行的复杂性。
- 透传变量让无关中间层知道低层细节并造成多点修改（change amplification）。Context object 可集中实例级全局状态，但仍有全局变量式隐式依赖和线程安全风险，应优先不可变并保持克制。

### 危险信号

- Controller、Service、Manager、Client 多层方法签名一致，只做逐层转发。
- 包装类的大部分代码是 boilerplate，新增能力很少。
- 参数穿过长调用链，中间方法完全不使用它。
- 接口直接复刻数据库表、RPC DTO 或内部存储结构，没有提供更高层语义。
- Context 演变为任何代码都能写入的杂物袋。

### 书中案例

- 一个 GUI 编辑器的 `TextDocument` 类有 15 个公开方法，其中 13 个只是把相同参数转发给 `TextArea`。重分职责并把 `TextDocument`、`TextArea`、`TextDocumentListener` 三类收敛为两类后，透传方法消失，两个类的责任也更清楚。
- 文本内部按行存储并不意味着接口也应按行。作者让文本 API 按任意字符范围插入、删除，把拆行和合并留在文本类内部；上层不再到处复制跨行编辑逻辑，接口抽象与存储抽象由此分开。
- 数据中心服务把证书配置从 `main` 一路传到低层 socket 方法，中间方法完全不用它。作者比较共享对象、全局变量和 context object，最后选择每个系统实例一个 context，并尽量只在构造器上传递；同时提醒 context 仍可能成为隐式依赖杂物袋。

### 对大型团队的启发

- 分层规范不能以层数为目标；每层都应写清楚它新增的抽象、隐藏的知识和消除的复杂性。
- 对典型请求链统计纯透传层和 DTO 重复转换，可直接发现“组织结构映射成代码结构”的空层。
- 跨层统一对象可以减少参数扩散，但要建立字段准入、不可变性、生命周期和并发规则，避免变成隐形总线。
- 技术方案中的架构图应能回答“抽象在这一跳发生了什么变化”，否则该边界需要重新评估。

<a id="chapter-8"></a>
## 第 8 章 Pull Complexity Downwards：由最合适的责任模块集中处理复杂性

### 核心命题

- 不可避免且与模块职责相关的复杂性，通常应由模块实现者承担，而不是由所有调用者重复承担；简单接口比简单实现更重要。
- 抛异常、暴露配置项或要求调用者自行编排，常是在把难题向上推并放大到每个用户。
- 文本模块应内部承担拆行和并行，让上层直接按字符范围编辑；这会增加局部实现复杂性，却降低系统总体复杂性。
- 配置项是一种未完成的解决方案。只有上层确实掌握更多领域信息时才应暴露；否则应自动计算、动态适应并提供合理默认值。
- 集中处理也有边界：复杂性必须与模块职责紧密相关，能简化多个上层位置，并使接口更简单；否则会造成设计知识分散（information leakage）或巨型类。

### 危险信号

- 每个调用者都要捕获同一种可在模块内处理的异常。
- 运维配置数量持续增长，但大多数使用者不知道如何选择正确值。
- 低层模块为了实现简单，要求所有上层重复做格式转换、范围拆分、重试或兼容处理。
- 以“由底层模块集中处理复杂性”为由，让基础模块了解具体 UI、渠道或业务流程。

### 书中案例

- 文本类如果只提供整行操作，实现很简单，但 UI 每次插入字符、复制跨行选区都要拆行和合并。改为字符范围接口后，文本类内部更复杂，上层却全部变简单，说明复杂性被集中到真正拥有文本表示知识的模块。
- 网络协议的重试间隔不应直接变成配置项。协议层可以测量成功请求的响应时间，再用其倍数动态计算重试间隔；这既减少运维选择，也能随网络条件自动变化。
- 作者也给出反例：把 `backspace` 直接放入文本类看似把复杂性向下拉，实则让文本机制理解 UI 按键，既没显著简化上层又造成设计知识分散（information leakage）。

### 对大型团队的启发

- 平台团队应主动承接一次实现、全局受益的复杂性，包括兼容、容错、自适应和安全默认值。
- 配置治理不应只做集中展示，还应持续删除可计算、可推导、可默认的参数。
- 由责任模块集中处理复杂性（pull complexity downwards）的评审标准是系统整体复杂性，不是该模块增加了多少代码；局部实现变复杂可能是正确取舍。
- 模块责任方应替调用者解决与本模块核心机制相关的难题，而非只交付可拼装的原语。

<a id="chapter-9"></a>
## 第 9 章 Better Together or Better Apart：合并还是拆分

### 核心命题

- 拆分会新增组件数量、接口、管理代码、物理距离和潜在重复；小组件本身更简单，不代表系统整体更简单。
- 适合放在一起的信号包括：共享设计知识、总是双向共同使用、属于一个清晰的上位概念、理解一方必须阅读另一方。
- 合并在三种情况下尤其有价值：集中共享信息、消除中间接口并自动处理常见能力、消除重复。
- 通用机制与其专用用法应分开。低层通常保留通用机制，专用策略推向上层；但同一个领域模块可同时包含其他机制的专用实现。
- 重复不一定要抽成方法；短片段或与局部变量高度交互的片段，抽取后可能产生更复杂接口。也可通过重组控制流让逻辑只执行一次。
- 方法长度本身不是拆分标准。方法应做完整的一件事并提供简单接口；数百行但可顺序独立阅读的方法，可能比多个相互跳转的小方法更容易理解，也能封装更多完整能力。
- 好的子方法能独立理解，父方法也无需理解其内部；若读懂一个方法必须同时查看另一个方法的实现，说明方法相互依赖（conjoined methods），职责并未真正分开。
- 拆分面向调用者的一个方法，只在原方法混合无关职责且多数调用者只需其中一部分时成立；若调用者必须依次调用所有新方法，拆分通常更差。

### 第二版增补：与《Clean Code》的分歧

- Ousterhout 反对按行数机械拆方法。短方法通常较易读，但当进一步拆分破坏独立性、制造必须共同理解的接口时，系统级复杂性反而增加。
- 核心判断不是“函数是否足够短”，而是拆分后能否形成独立、深且易理解的抽象；不要用长度牺牲深度。

### 危险信号

- Repetition：相同或近似代码反复出现，说明尚未找到合适抽象。
- 通用机制与特定业务混杂（special-general mixture）：通用机制夹带特定场景策略，导致两者一起变化。
- 方法相互依赖（conjoined methods）：两个方法物理分开，但读懂其中一个时必须同时查看另一个方法的实现。
- 拆分后调用方要管理更多对象、传递中间状态或遵守新的顺序约束。
- 一个日志/校验辅助方法只有单一调用点、内容很短，却迫使读者来回跳转理解上下文。

### 书中案例

- “该合还是该拆”在本章有一组对照。HTTP 请求的读取与解析共享协议格式，应合并；编辑器中的插入光标和选区虽然经常一起变化，但上层仍把它们当成不同概念，合并对象反而要增加布尔状态和分支，因此应拆开。
- 一个学生项目把每种网络错误的单行日志抽成 `NetworkErrorLogger` 方法。每个方法只有一个调用点，注释比实现还长，读者必须在报错现场和日志方法之间来回跳转；作者建议把日志语句放回错误发生处。
- 编辑器 undo/redo 最初全部放在文本类里，导致文本类还要理解选区、光标和视图。重构后，`History` 只管理 `Action`、fence 和历史游标；文本、选区等模块各自实现专用 action，上层决定哪些 action 组成一次用户操作。
- 对长方法，作者给出两种有效拆法：抽出可独立理解的通用子任务，或把原本混合的两项独立能力拆成两个调用入口。若调用者仍要依次调用所有新方法并传递中间状态，就只是把一件事切碎。

### 对大型团队的启发

- 微服务、模块和方法拆分应使用同一复杂性标准，而不是以组织边界、代码行数或“职责单一”作机械依据。
- 对跨服务拆分，应量化新增接口、数据一致性、编排、观测和故障处理成本，再与独立演进收益比较。
- 通用能力平台化时，应把场景策略留给业务责任方，同时让平台接口真正封装机制，而不是把内部步骤远程化。
- Code Review 中对长方法的意见应指出具体抽象问题、共享状态或可独立子任务，不能只报行数。

<a id="chapter-10"></a>
## 第 10 章 Define Errors Out of Existence：通过定义消除错误

### 核心命题

- 异常是改变正常控制流的罕见条件，不限于语言的 `throw`；错误码和特殊返回值同样会增加复杂性。
- 异常处理要恢复半完成状态、处理恢复过程中的二次异常，而且难以稳定测试；异常本身是接口的一部分，传播越高影响面越大。
- 当操作契约适合定义为“确保达到目标状态”时，可以重新定义语义，使目标本来已达到不再是错误。例如删除不存在的临时变量可定义为“确保变量不存在”。这不适用于所有重复业务请求。
- Unix 延迟删除已打开文件，把“文件被占用”和后续进程访问失败都从语义上消除；容错语义可以同时减少多个参与方的异常。
- 对无法消除的异常有三种主要手段：低层 masking、在合适高层 aggregation、对罕见且无法合理恢复的内部故障明确失败并提供诊断。
- Masking 适合底层能比所有调用者更统一地恢复的情况，如 TCP 重传；但关键失败信息若是上层构建可靠性的必要输入，就不能吞掉。
- Aggregation 把同类请求失败集中到请求边界处理，既减少重复 handler，也让低层负责生成具体原因、高层负责统一协议响应。
- 可将多种罕见局部错误“提升”为已有的通用恢复机制，但要权衡恢复成本和发生频率。
- 特殊情况也可用统一表示消除，例如始终存在但可为空的 selection，让普通算法自然覆盖空场景。

### 危险信号

- 过度防御：遇到任何可疑输入都新增异常，却没有设计实际恢复责任。
- 每个调用点重复捕获同一异常，处理逻辑基本一致。
- 低层把不知道如何处理的问题直接抛给更不了解机制的上层。
- 吞掉网络、持久化等关键失败，导致上层误以为操作成功。
- 一个状态是否存在由额外 boolean 表示，使所有操作都出现对应分支。

### 书中案例

- Tcl 的 `unset` 原本在变量不存在时抛错。清理中间状态的调用者只好对每个可能存在的变量调用 `unset`，再捕获并忽略异常。作者后来认为应把语义定义成“确保变量不存在”：变量本来就不存在时，操作已经成功。
- Windows 不允许删除仍被进程打开的文件，用户常要寻找并终止占用进程；Unix 则先移除目录项，已有进程继续使用文件，最后一个引用关闭后再释放数据。延迟删除同时消除了“文件占用”和“正在使用的进程突然读写失败”两类异常。
- Java `String.substring` 对越界索引抛异常，调用者为取区间交集要先写多行边界修正。作者建议让方法自动截取字符串与请求区间的重叠部分；Python 切片返回空结果是类似语义。
- TCP 在内部重传丢包，让上层仍看到可靠字节流；NFS 在服务端暂时不可用时持续重试，使应用恢复后可继续执行。作者同时给出反例：学生网络模块把所有网络异常都吞掉，导致应用无法知道消息丢失或对端故障，可靠性反而无法建立。
- Web 服务的每个参数读取点若单独捕获 `NoSuchParameter`，会复制大量错误响应代码；让异常上浮到 dispatcher，由一个请求边界统一生成错误响应，是 exception aggregation 的具体例子。

### 对大型团队的启发

- API 评审必须同时评审错误语义：谁能恢复、在哪里恢复、是否可幂等化、是否可统一处理，而非只列错误码表。
- 业务幂等要额外区分同一请求重试、新的重复业务和参数冲突；`unset` 案例不能推导出重复提交一律成功。
- 请求级业务异常宜在统一网关/dispatcher 边界聚合，但错误原因应由最了解事实的模块产生，避免高层猜测。
- 重试、降级和屏蔽应由拥有机制知识的层实现，同时保留必要的可观测性和不可恢复信号。
- 对金融关键链路，作者的 “just crash” 不能机械套用；应按一致性、可恢复性、重复执行风险和业务连续性决定 fail-fast、隔离或恢复策略。
- 错误分支的测试价值高，应引入故障注入或状态模型验证，而不能因低频而放弃覆盖。

<a id="chapter-11"></a>
## 第 11 章 Design It Twice：至少设计两次

### 核心命题

- 重大设计决策不应直接实现第一直觉；至少构造两个明显不同的候选，并草拟关键接口即可，无需完整实现。
- 比较重点包括：上层使用成本、接口简单度、通用程度、实现复杂度和性能。
- 候选都不理想本身是一条证据：提取各方案共同暴露的问题，再形成新的组合或第三种方案。
- 该方法适用于接口、内部数据结构、模块分解和用户功能等不同层级；目标权重会随层级变化。
- 小模块的比较可能只需一两个小时，相对其数日或数周实现成本很低；持续比较也会训练长期设计判断力。

### 危险信号

- 技术方案只有一个实现路径，理由是“显而易见”或“以前一直这样”。
- 备选方案只在命名或局部实现上不同，没有触及抽象、边界或职责。
- 团队把一次想对当作能力证明，把推翻初稿视为失败。

### 书中案例

- 作者继续使用文本编辑器说明“至少设计两次”。文本 API 可按整行、单字符或任意字符范围设计：整行接口迫使上层拆行并行，单字符接口迫使上层写循环且效率差，范围接口最终吸收了前两种方案暴露的问题。
- 接口确定后，内部表示仍可再次比较：链表式行结构、固定大小字符块、gap buffer 都是不同候选。接口评估以调用者简单为主，内部实现评估则更看重实现简单度和性能，不能用同一套权重草率选择。

### 对大型团队的启发

- 方案评审应要求关键决策提供至少两个有实质差异的选项，并用统一复杂性指标对比，而非形式化罗列优缺点。
- 设计备选应优先覆盖最难逆转的决策：服务边界、数据模型、外部契约、一致性模型和扩展机制。
- 原型和 spike 的目标应是验证候选假设、暴露认知盲区，不是悄然演变为未经评审的正式实现。
- 评审文化要奖励可证伪的假设、主动推翻初稿和从候选比较中提炼的判断依据。

<a id="chapter-12"></a>
## 第 12 章 Why Write Comments?：为什么要写注释

### 核心命题

- 注释不只是帮助读代码，也是完整定义抽象、隐藏复杂性和辅助设计的组成部分；缺少文档会让好设计失去大部分价值。
- “好代码可以自解释”只覆盖局部语句。行为语义、边界条件、设计理由、调用前提和副作用无法由签名完整表达。
- 如果使用者必须读实现才能知道如何调用，就没有真正的抽象；为便于读实现而不断拆小方法，还会制造大量浅接口。
- 写注释是一项前置投资。作者估计其上界约占开发时间 10%，并认为维护收益会很快抵消成本；该数字应视作经验判断。
- 注释失效并非不可控：避免重复、靠近对应代码，并在 Code Review 中核对，可把维护成本限制在合理范围。
- 好注释保存设计者脑中但代码无法表达的信息，降低理解负担（cognitive load）并减少隐藏影响点（unknown unknowns），尤其对原作者数周后的再次维护同样重要。

### 第二版增补：与《Clean Code》的分歧

- Robert C. Martin 把注释视为代码表达失败的补偿；Ousterhout 认为代码与自然语言各自适合表达不同信息，优质注释不是失败。
- 用极长的方法名替代解释性注释，可能传递更少信息并诱导把相关代码拆成浅方法；注释的目的之一正是让使用者不必读实现。
- 团队不应营造“写注释说明代码差”的羞耻感，否则开发者会隐瞒真正的设计语义和依赖。

### 书中案例

- 作者用 `substring(start, end)` 的方法声明说明“自解释代码”的边界：只看签名无法知道 `end` 是否包含在结果中，也不知道 `start > end` 时如何处理。若使用者必须读实现才能确认这些规则，方法就没有形成可用抽象。
- 反对者常建议把代码继续拆成更短方法，让方法名代替注释。作者指出，这会把一个实现切成多个低收益方法（shallow methods）；调用者仍要阅读整条调用链，接口数量却增加了。
- 本章的四类常见借口也对应实际维护情境：延后写注释往往变成永远不写；数周后即使原作者回到代码，也已经忘记当时的设计理由，只能重新推导或猜测。

### 对大型团队的启发

- 公共 API、核心领域模型和跨团队组件必须把非形式契约视为接口的一部分，不能只发布 schema 或自动生成签名文档。
- 文档质量应进入设计和代码评审，而不是上线后的补录任务。
- 注释规范的目标应是保存决策与抽象，而不是提高注释行数或要求逐行解释。
- 对高流动团队，文档是在时间和人员之间传递设计上下文的基础设施，不是个人书写偏好。

<a id="chapter-13"></a>
## 第 13 章 Comments Should Describe Things That Aren't Obvious：注释描述代码不明显的信息

### 核心命题

- 好注释与代码处于不同抽象层级：要么补充更精确的低层契约，要么提供更高层的意图和直觉；与代码同层通常只是在复述。
- 团队应建立一致的注释分类和格式：接口、数据成员、实现、跨模块决策。接口和数据成员注释通常最重要。
- 判断复述的方法：不了解实现的人若只看相邻代码就能写出同样注释，该注释没有新增价值。
- 低层精度应覆盖单位、区间开闭、`null` 语义、资源释放责任、不变量和缺失值含义；变量注释应说明“它表示什么”，而非“哪些代码如何修改它”。
- 高层注释说明代码块总体要做什么、为什么这样做、在什么条件下走到这里，为细节提供判断框架。
- 类接口文档应描述整体抽象、实例代表什么、能力和限制；方法接口文档应描述调用者可见行为、参数/返回值、约束、依赖、副作用、异常和前置条件。
- 接口文档必须与实现文档分离。若接口文档不得不解释内部 RPC、数据结构或算法，可能是接口被实现污染或模块太浅。
- 实现注释重点写 what/why，而不是逐句 how；长方法可在主要代码块前给出抽象意图，复杂 workaround 应说明原因并链接问题记录。
- 跨模块决策不可避免且最易产生缺陷。优先在开发者必经的中心声明旁记录；无中心时可使用统一 design notes，并在每个相关代码点留下短链接。
- 集中记录与现场发现存在张力：设计决定只记录一次可以避免内容漂移，但距离代码较远，必须从相关代码反向链接并在评审中维护。

### 危险信号

- Comment repeats code：注释与标识符、语句使用相同词汇，没有补充语义。
- Implementation documentation contaminates interface：接口说明夹杂调用者无需知道的实现细节。
- 变量或方法缺少单位、边界、资源所有权、失败语义等精确契约。
- 跨模块约束只存在于某位资深开发者记忆、聊天记录或单个提交信息中。
- 评审者认为不明显，而作者以“代码已经很清楚”反驳；易理解性由首次阅读者判断。

### 书中案例

- `textHorizontalPadding` 原注释只是重复“每行的水平 padding”；改写后明确它是左右两侧留白、单位是像素。代码给出数值和名称，注释补充单位、作用范围和精确语义，二者处于不同信息层级。
- RAMCloud 的 `IndexLookup` 初版类注释写满内部 RPC、并发数量和私有常量，却没有清楚说明每个实例代表一次范围查询。重写后只保留调用者所需的查询模型和 `getNext()` 用法，服务端崩溃恢复等内部机制不再污染接口文档。
- RAMCloud 新增 `Status` 值时，需要同步消息表、异常类、C++/Java 映射等多处。作者把完整清单放在所有人必经的 `Status` 枚举末尾，让跨模块依赖在修改入口处可见。
- “僵尸服务器”处理跨越多个模块且没有天然中心。作者将完整设计放入 `designNotes` 的 `Zombies` 章节，再在每个相关代码点留下短引用；这样只有一个事实源，同时保留现场可发现性。

### 对大型团队的启发

- 技术设计文档和代码注释应形成两级索引：系统级决定只保留一份正式记录，相关模块在代码附近留下可以找到它的链接。
- 接口文档模板应强制覆盖契约维度，而非强制字数；对无异常、无副作用也可明确声明，减少猜测。
- 重大 bug 修复应留下“为什么需要这段非直观代码”和稳定问题编号，避免未来优化时重新引入问题。
- 可以把“接口说明能否简短而完整”作为模块深度的早期测试。

<a id="chapter-14"></a>
## 第 14 章 Choosing Names：选择名称

### 核心命题

- 名称是一种轻量抽象：用少量词让读者形成接近真实的心智图景，并同时知道对象不是什么。
- 好名称要求精确和一致。`block` 同时表示文件逻辑块与磁盘物理块，会让读者产生看似合理但错误的假设；`fileBlock`、`diskBlock` 可让误用显眼。
- 名称不能过泛，也不能绑定不成立的具体场景。代表任意范围的参数不应命名为 `selection`。
- 很难找到简短准确名称本身是设计警报，常说明一个变量承担多个含义或对象没有清晰职责。
- 一致性有三层：同一目的总用同一名称、该名称不用于其他目的、所定义的目的足够窄以保证相同行为。
- 短名只适合使用范围一眼可见的局部变量；声明与使用距离越远、影响范围越大，名称越应完整。
- 可读性最终由读者判断。语言社区风格可作为约定，但不能覆盖实际维护者的理解反馈。

### 危险信号

- Vague name：`data`、`result`、`count`、`block` 等可指代大量不同概念。
- 难以准确命名（Hard to Pick Name）：经过思考仍无法为对象找到清楚、不过长的名称。
- 同一个业务概念在不同模块使用不同词，或同一个词对应不同状态/口径。
- 名称表达的是当前 UI 或实现，而实体本身具有更通用语义。

### 书中案例

- Sprite 分布式操作系统曾偶发把文件数据块清零。作者和学生追查了六个月，最终发现变量 `block` 有时表示文件内逻辑块，有时表示磁盘物理块；某处把逻辑块号当成物理块号使用，覆盖了无关磁盘块。
- 错误代码此前被多人读过，但 `block` 这个“看似合理”的名字让阅读者自动假定类型正确。若一开始分别使用 `fileBlock` 和 `diskBlock`，误用会非常显眼。这是命名直接造成错误判断，而非单纯影响美观的案例。
- 书中还比较 `blinkStatus` 与 `cursorVisible`、`VOTED_FOR_SENTINEL_VALUE` 与 `NOT_YET_VOTED`：后者让布尔真值或哨兵值的业务含义直接出现在名称中，减少读者再查注释和实现的次数。

### 对大型团队的启发

- 建立领域词汇表的核心不是统一拼写，而是统一概念边界、数据口径和行为。
- 对跨团队 API、事件和数据库字段，命名歧义会被放大成数据错误和兼容成本，应作为契约风险评审。
- 命名讨论若长期僵持，应回到模型拆分和职责设计，而不是继续寻找更长的复合词。
- Code Review 可要求新名与既有领域术语一致，并检查是否误导未来读者，不能只检查命名格式。

<a id="chapter-15"></a>
## 第 15 章 Write the Comments First：先写注释

### 核心命题

- 把注释推迟到代码稳定后，通常导致不写、忘记设计理由，或只根据现成代码做低价值复述。
- 推荐顺序：先写类抽象，再写关键公开方法的接口说明和签名，迭代结构；然后写关键状态及其注释，最后实现方法体并补必要实现注释。
- 先写注释让设计者在实现细节干扰前定义抽象；注释随编码和测试一起被校验，完成代码时文档也同步完成。
- 注释是复杂性的“金丝雀”。完整说明一个接口若必须很长很绕，接口可能过于复杂；说明几乎覆盖全部实现，则模块可能太浅。
- 难以简洁说明（Hard to Describe）与难以准确命名（Hard to Pick Name）类似，都是可在编码前暴露坏抽象的反馈信号。
- 早写带来的少量修改成本可能由更稳定的抽象和更少的代码返工抵消。

### 书中案例

- 本章没有引入单独的生产事故，主要案例是作者自己的 comments-first 工作法：先写类接口注释，再写关键公开方法的注释和签名，方法体先留空；随后定义并注释关键状态，最后才填实现。
- 这个过程把注释当作设计探针。若一个方法的完整接口说明必须很长，说明调用前提、参数关系或异常过多；若接口说明几乎复述全部实现，方法可能是低收益模块（shallow module）。作者会在写代码前先调整抽象，而不是润色长注释来掩盖问题。

### 对大型团队的启发

- 技术设计不应等实现完成后补写。公共契约、领域对象和主要状态应在编码前以调用者视角说明。
- PR 可检查接口文档是否先于/同步于实现演进，并将“难以简明描述”升级为设计讨论，而非文字润色问题。
- 对外 API 可采用 contract-first，但需保留增量反馈，避免把早期契约冻结成无法修正的瀑布式设计。
- 先写注释的真正产物是可评审的抽象；团队应评审其完整性和简单性，而不是追求统一模板的填满率。

<a id="chapter-16"></a>
## 第 16 章 Modifying Existing Code：修改现有代码

### 核心命题

- 成熟系统的设计更多由历次变更塑造，而非由初始蓝图决定；每次修改都是设计活动。
- “只做最小代码改动”不总等于最小风险。局部补丁会不断新增特殊情况和依赖，使整体结构逐步恶化。
- 理想目标是：完成变更后，系统看起来像从一开始就考虑过该需求。必要时应调整原有抽象，而不是把新行为粘在边缘。
- 战略性修改仍受现实边界约束。若彻底重构代价和兼容影响过大，应寻找接近正确设计的中间路径，并显式安排后续治理。
- 文档应靠近所描述代码；距离越远，内容越应抽象。实现细节分散到最窄相关作用域，方法顶部只保留总体策略。
- 未来维护者需要的原因和约束必须进入代码或就近文档，不能只留在 commit message；日志不具备足够可发现性。
- 每个设计决定只保留一份正式记录，其他位置用短引用指向它；不要在调用方重复描述被调方法的接口约定。
- 提交前检查 diff，同时核对代码变更是否更新了对应注释；高层注释因不绑定细节，通常更稳定。

### 危险信号

- 变更目标被表述为“碰最少文件”，却没有评估新增特殊分支和长期影响。
- 关键兼容原因只存在于 commit、聊天或 Jira，代码附近没有线索。
- 同一规则在多个位置复制说明，内容已开始不一致。
- 独立文档详细描述易变实现，但没有代码侧引用或明确责任方。

### 书中案例

- 本章以“为现有系统补功能或修 bug”这一常见情境展开：两小时的局部补丁可能只碰一处，却新增特殊分支；三个月的彻底重构又可能超出进度和兼容边界。作者建议继续寻找几天内可完成、结构接近理想状态的中间方案，而不是把“最小 diff”当作唯一目标。
- C/C++ 常把接口注释放在头文件、实现放在源文件。作者认为维护者修改方法体时不容易看到头文件注释；在 Doxygen、IDE 能向使用者展示文档的前提下，注释应靠近实现，以提高同步更新概率。
- 某次 bug 修复若只在 commit message 解释“为什么这段非直观代码不能删”，未来维护者很可能看不到提交历史并撤销修复。作者要求把稳定原因写到代码附近，commit message 可以保留副本，但不能成为唯一事实源。
- 对跨模块设计，完整说明只写一次；其他位置写 `See ...` 短引用。若引用目标被移动，断链会暴露问题；若复制多份说明，其中一份过期却不一定有人察觉。

### 对大型团队的启发

- “最小闭环改动”应理解为满足需求、保持整体结构一致且风险可验证的最小方案，不是字符级最小 diff。
- 技术债治理应嵌入每次触达代码的演进预算，同时对大规模兼容性改造设置独立决策门槛。
- PR 模板可要求说明：这次变更是否让设计更接近理想状态、有哪些暂缓项、相关文档是否同步。
- 跨模块决定放在系统级记录，调用规则放在接口说明，局部原因放在代码注释，并用引用连接；这样既避免多处重复，又能从修改现场找到相关约束。

<a id="chapter-17"></a>
## 第 17 章 Consistency：一致性

### 核心命题

- 一致性产生认知杠杆：学会一处即可对相似位置做安全推断；不一致则要求逐点重新学习，并容易形成错误类比。
- 一致性可覆盖名称、编码风格、接口、多实现模式、设计模式和不变量；不变量尤其能消除特殊情况并简化推理。
- 维护一致性需要文档、自动化检查、Code Review 教育，以及开发者主动寻找仓库中的既有做法。
- 低层语法约定优先自动化拦截，不应长期占用人力评审注意力。
- “更好的新做法”不足以局部破坏约定。只有新增证据充分、收益足以承担全量迁移时才更新；迁移完成后不应残留双轨。
- 一致性不等于强行统一不同事物。只有“看起来像 X 就确实是 X”时，已有经验才可安全复用。

### 危险信号

- 新模块为同一概念创建另一套名称、错误结构、分页方式或状态定义。
- 新规范只改部分代码，旧用法长期共存并不断回流。
- 用统一模板抹平真实差异，使同名字段或接口在不同场景有不同语义。
- 本可工具化的格式和静态约束长期靠评审人工提醒。

### 书中案例

- 作者所在项目的开发者同时使用 Unix 和 Windows，编辑器有时把整个文件的 LF 换成 CRLF，导致一次小改动看起来像全文件变化。团队先约定只用 LF，但每位新人加入都会再次出现问题。
- 最终团队写了一个很短的 pre-commit 脚本：提交前检查所有改动文件，发现 carriage return 就拒绝提交，并可自动修复。问题随即消失，新人也会在第一次违反约定时得到即时反馈。这个案例说明低层一致性应由工具执行，而不是靠评审反复提醒。
- 文本行“始终以换行符结束”是本章的不变量示例。固定不变量让所有处理代码都能按同一假设推理，避免到处判断最后一行是否特殊。

### 对大型团队的启发

- 组织级规范要区分可自动执行的硬规则和需要判断的设计原则；前者交给工具，后者保留评审精力。
- 统一接口和领域约定会直接降低跨团队接手成本，但前提是语义一致，而非表面 JSON 结构一致。
- 规范升级应按迁移项目管理：证据、影响面、迁移计划、自动检查和去除旧约定缺一不可。
- 新成员 onboarding 应优先学习高杠杆约定和可运行示例，而不是阅读无优先级的规则全集。

<a id="chapter-18"></a>
## 第 18 章 Code Should Be Obvious：代码应当易理解

### 核心命题

- 易理解意味着首次阅读者无需大量推理，就能对行为和含义形成正确的第一判断；判断权在读者而非作者。
- 首选减少理解代码所需的信息量，例如更好的抽象和消除特殊情况；其次复用读者已有知识，例如一致约定；最后用命名和注释主动提供必要信息。
- 适当空白、代码块分隔和结构化格式能显式呈现层次，但不能替代设计。
- 事件驱动代码会隐藏控制流和实际回调目标，应在 handler 接口说明其触发条件与上下文。
- 通用 `Pair/Tuple` 方便作者，却用 `key/value` 等无语义名称增加所有读者成本；定义专用结果类型通常更清楚。
- 声明类型与实际分配类型差异若影响性能或线程安全，会误导读者；抽象声明并非无条件更好。
- 代码违反常规预期时必须主动说明，例如 `main` 返回后后台线程仍保持进程运行。

### 危险信号

- 难以直接理解的代码（Nonobvious Code）：快速阅读无法确认含义、控制流、生命周期或副作用。
- 回调、反射、隐式注册和框架魔法没有就近说明触发路径。
- 多返回值使用无语义容器，调用者只能通过位置或 `key/value` 猜含义。
- 作者以“写起来方便”选择结构，却把长期阅读成本转嫁给所有维护者。

### 书中案例

- Java 代码 `new Pair<Integer, Boolean>(currentTerm, false)` 写起来快，但调用者只能通过 `getKey()`、`getValue()` 取值，名称完全不说明“任期”和布尔状态。作者建议定义专用结果类型，让字段名和声明处文档直接表达语义。
- 事件处理器不会被业务代码直接调用，阅读者难以找到触发点。作者在 `Transport::RpcNotifier::failed()` 的接口注释中明确：它由 transport 在 dispatch 线程中、因底层错误导致 RPC 无法完成时调用。这类“何时、由谁调用”不能只靠方法体猜。
- `List<Message>` 实际分配成 `ArrayList<Message>` 时，读声明的人可能忽略具体实现的性能和线程安全属性；如果这些属性影响正确使用，作者主张声明类型与真实分配类型保持一致。
- `main` 中只创建一个 `RaftClient` 后就返回，通常让人以为进程会退出；实际上构造器启动了后台线程。除构造器接口文档外，作者建议在 `main` 末尾再留一条短注释，主动纠正读者最可能产生的错误判断。

### 对大型团队的启发

- 代码优化目标应从“减少作者输入”转为“减少团队总阅读和修改成本”。
- 评审者的困惑是设计数据，应记录是哪类信息缺失，再选择重构、命名、约定或注释中成本最低的补救方式。
- 事件驱动、消息驱动和依赖注入系统必须提供可追踪入口、注册关系和生命周期文档，否则隐藏影响点（unknown unknowns）会快速增加。
- 明确类型和领域对象虽增加少量代码，却能改善跨团队契约、静态检查和可观测信息，应按总认知成本取舍。

<a id="chapter-19"></a>
## 第 19 章 Software Trends：用复杂性检验流行实践

### 核心命题

- 语言机制、流程和模式本身不保证好设计；任何新范式都应回到“是否降低大型系统复杂性”检验。
- 接口继承通过复用同一抽象降低理解成本；多个真正不同的实现可以让同一接口封装更多能力（deep module）。
- 实现继承减少代码重复，却引入父子类之间的状态与行为依赖。优先比较 composition；无法避免时，应隔离父类状态并减少子类直接访问。
- 敏捷的增量反馈符合持续设计，但若只聚焦 feature 和尽快工作，会强化战术式编程。开发增量应是可完整设计的 abstraction，而不是零散功能补丁。
- 单元测试的设计价值在于重构后能发现被破坏的既有行为，让团队更有把握修复结构；系统测试不能完全替代细粒度覆盖。
- 作者不赞成把 TDD 作为所有新设计的默认过程，担心逐测试推进会把注意力锁在功能而非抽象；但修 bug 前先写能复现问题的测试非常有效。
- 设计模式是经过验证的候选，不是自动正确的答案；过度套用会把不适合的问题塞进既有结构。
- Getter/Setter 虽比公开字段多一层兼容空间，但通常仍暴露内部状态，接口浅且易被模式化滥用。

### 危险信号

- 以继承复用为默认，修改父类前必须理解所有子类。
- Sprint 持续交付 feature，却没有产生可复用、可独立理解的抽象。
- 为满足覆盖率或 TDD 节奏，把实现拆成测试方便但系统更浅的单元。
- 因为“这是标准模式”而不再比较设计知识封装（information hiding）、依赖和接口成本。
- 为每个字段机械生成 Getter/Setter，使领域对象退化为可变数据袋。

### 书中案例

- Tcl 解释器后来被字节码编译器替换，几乎触及核心引擎的每个部分。这种规模的重构若没有测试很难安全推进；现有单元测试在新引擎开发期发现了大量问题，alpha 发布后只出现一个遗漏 bug。作者以此说明测试能够发现重构引入的大多数缺陷。
- 接口继承的正例是同一 I/O 抽象可分别由磁盘文件和网络 socket 实现；学习一次接口即可使用多个实现。实现继承则可能让修改父类前必须检查所有子类，因此作者要求先比较 composition。
- Getter/Setter 是模式过度应用的反例：即使为未来校验或通知留了入口，它们通常仍直接暴露实例状态，而且每个方法只有一行。模式名称没有改变它们接口浅、设计知识分散的事实。
- 作者对 TDD 的观点有明确边界：新抽象不应被“让下一个测试通过”逐片塑造；修 bug 时则应先写一个能稳定复现问题的失败测试，再修复并确认测试转绿。

### 对大型团队的启发

- 流程指标要同时观察抽象质量和可演进性，避免 feature velocity 掩盖复杂性增长。
- 测试体系应优先保护契约、关键不变量和重构信心，而非仅追逐覆盖率数字。
- 关于 TDD 的观点应作为需要情境化验证的争议点：测试先行可用于明确行为，但仍需独立的抽象设计步骤，不能让单个测试驱动整体边界。
- 框架、DDD、微服务和设计模式都应作为候选工具，由问题适配性决定，而非成为团队身份或硬性配额。

<a id="chapter-20"></a>
## 第 20 章 Designing for Performance：面向性能设计

### 核心命题

- 不应优化每条语句，也不能完全忽略性能。日常设计应具备昂贵操作的基本常识，选择“天然高效且简单”的方案。
- 网络往返、持久化 I/O、动态内存分配和 cache miss 是典型高成本操作；具体数量会随硬件演进，方法上应靠 microbenchmark 建立本地事实。
- 若高效方案只增加少量且被模块隐藏的实现复杂性，可考虑提前采用；若污染接口或显著增加复杂性，应等待证据。
- 性能优化前必须测量：先定位少数高贡献点并建立基线，修改后复测；没有显著收益的复杂改动应撤回。
- 优先寻找 fundamental fix，如缓存、算法或体系结构变化。必须微调时，围绕 common-case critical path 重新设计。
- 先设想理想关键路径所需的最少代码和数据，再在尽量保留该路径的前提下恢复清晰抽象。
- 将所有特殊情况用一次前置判断移出关键路径，普通路径保持直线化；少见路径按易理解性组织。
- RAMCloud Buffer 案例通过消除浅层调用和重复检查，使常见操作约快 2 倍、代码量下降约 20%，说明简洁与性能常可同向。

### 危险信号

- 凭直觉优化，没有细分热点和前后基线。
- 保留测不出收益的复杂缓存、分支或手写优化。
- 关键路径跨越多个相同抽象的浅层方法，并反复检查同一条件。
- 以性能为由复杂化所有路径，而非只集中在有证据的少数热点。
- 只看 top-level latency，无法解释时间和资源消耗分布。

### 书中案例

- RAMCloud 用 `Buffer` 管理 RPC 的分段内存：小 header 放内部块，大对象直接引用外部内存，从根本上避免复制。随着每次 RPC 至少创建约四个 Buffer，团队测量后确认它已进入关键路径。
- 原 `Buffer::alloc` 的常见路径穿过三个签名几乎相同的方法，并对容量、分配状态等条件重复检查，共检查 6 个条件。重构后常见路径收进一个方法，用 `extraAppendBytes` 把多种特殊情况折叠为一次前置判断。
- 结果不是“用复杂代码换速度”：1 字节 append 从约 8.8 ns 降到 4.75 ns；创建 Buffer、追加小块再销毁从约 24 ns 降到 12 ns；类本身由 1886 行降到 1476 行，约减少 20%。
- RAMCloud 还在架构层提前选择绕过内核、直接使用网卡的网络方案。团队已有测量证明内核网络达不到延迟目标，因此愿意在一个关键位置承担额外复杂性，同时让系统其他部分继续以简单设计为主。

### 对大型团队的启发

- 性能方案必须带测量方法、当前基线、目标、关键路径和回退条件，避免不可证伪的“性能考虑”。
- 建立低成本 microbenchmark 与生产剖析能力，会提高整个团队对昂贵操作的共同直觉。
- 性能例外应由高封装模块（deep module）处理，并保证对外契约不因局部优化暴露内部表示。
- 架构级性能瓶颈应尽早识别；把一个高杠杆约束处理正确，常比到处微优化更能保持设计简单。

<a id="chapter-21-second-edition"></a>
## 第二版新增第 21 章 Decide What Matters：决定什么重要

### 核心命题

- 好设计的共同内核是区分重要与不重要：围绕重要因素组织系统，强调它们；把不重要因素的影响降到最低并尽量隐藏。
- 判断重要性可寻找 leverage：一个知识点或解决方案能解释、简化多少其他问题。通用接口和不变量因高杠杆而重要。
- 重大选择仍应 design it twice；经验不足时可把判断写成假设，按假设实现并在结果中寻找支持或反证，从反馈中提高“品味”。
- 尽量让更少的事情重要：减少不必要的必填参数、为已确定的技术规则提供默认值、缩小关键知识分布范围、低层完全处理可恢复异常、自动推导无歧义配置；业务结果和权限边界仍需明确依据。
- 已确定的重要事项应用三种方式强调：放在醒目位置、在必要位置有一致重复、置于系统中心使周围结构围绕它展开。
- 不重要事项则反向处理：隐藏、减少出现频率、避免影响系统结构。
- 两类错误：把太多事当重要会造成接口膨胀、低收益模块（shallow module）和理解负担（cognitive load）；忽视真正重要事项会造成隐藏依赖、重复实现和隐藏影响点（unknown unknowns）。
- 该原则同样适用于技术写作：先选少数核心概念，以它们组织全文；好的设计品味本质上包含区分轻重的能力。

### 书中案例

- 作者再次使用文本编辑器说明 leverage：按字符范围插入和删除的通用接口能解决退格、Delete、选区删除等多种问题；专用 `backspace` 只解决一个按键。对文本类来说，重要的是“哪段文本被删除”，并不重要的是这次删除由哪个 UI 动作触发。
- 设备驱动接口是 centrality 的例子：数百上千个驱动都围绕块读写等核心接口实现，因此这组接口必须处于系统中心、清楚可见且保持一致；具体设备命令则应隐藏在驱动内部。
- Java I/O 把 buffered 与 unbuffered 的区别暴露给几乎所有调用者，是“把太多事当重要”的反例。绝大多数调用者都需要缓冲，却要显式组装 `BufferedInputStream`，低收益模块和理解负担（cognitive load）随之增加。
- 对经验不足、暂时无法确定重点的设计者，作者给出可执行方法：把“我认为最重要的是 X”写成假设，按该假设实现，再从结果中寻找支持或反证。错误假设也要复盘当时遗漏了什么线索。

### 对大型团队的启发

- 技术方案不能平均展开所有细节，应明确三到五个决定系统结构的关键问题，并让接口、数据、验证和风险围绕它们组织。
- 架构治理应减少“全员必须知道”的事项数量；真正跨团队重要的约束则必须容易找到、统一命名并有明确责任方。
- 配置、错误码、字段和流程节点都可用“它是否真的需要对所有使用者重要”做删减检查。
- 资深设计判断应可训练：把“我认为最重要的是……”显式写成假设，通过上线反馈、变更成本和复盘持续校准。

<a id="conclusion"></a>
## 第一版第 21 章 / 第二版第 22 章 Conclusion：结论

### 核心命题

- 全书只有一个总目标：管理复杂性。依赖与模糊性是根因，各类危险信号帮助发现不必要复杂性；高封装模块（deep module）、通用接口、消除特殊情况和清晰文档是主要手段。
- 简单设计需要早期投入和训练成本，但收益会通过复用、低成本变更、可靠维护和更少缺陷较快回收。
- 设计是一种持续求解“怎样用最简单结构解决问题”的活动；能力成熟后，好设计与快速交付并非对立。

### 书中案例

- 结论章没有再引入独立工程案例，而是回扣全书的长期收益场景：项目初期定义清楚的模块会在后续反复复用；六个月前写下的接口和设计说明，会在开发者重返代码时直接节省重新推导的时间。
- 前文的 HTTP 解析、Tcl `unset`、Sprite 命名 bug 和 RAMCloud Buffer 分别展示了模块边界、错误语义、命名与性能设计如何影响复杂性。作者用这些案例收束到同一判断标准：是否让系统更容易被理解和修改。

### 对大型团队的启发

- 团队不应把本书变成另一套机械规范。每条原则都应服务于降低整体复杂性，并接受实际维护反馈校验。
- 设计质量最终应反映在系统能否被更多人安全理解、修改和扩展，而非文档数量、类数量或模式使用数量。
- 长期目标是让工程师把更多时间用于设计和创造，而不是在脆弱系统中追逐重复缺陷。
