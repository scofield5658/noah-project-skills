# 面向大型团队的软件复杂性设计

大型团队不需要更多抽象口号，而需要让设计决定能被不同角色复查。下面提供四种轻量工件，用于暴露复杂性并建立责任闭环。

## 1. 变化演练

选择一个可能出现的相邻需求，模拟它将如何穿过现有系统。

| 演练问题 | 记录内容 |
|---|---|
| 哪条规则会变化？ | 规则名称和当前维护位置 |
| 哪些位置必须修改？ | 代码、配置、契约、监控和操作流程 |
| 谁需要参与？ | 责任团队和审批边界 |
| 如何知道没有遗漏？ | 消费者清单、触发入口和验证证据 |
| 失败后如何恢复？ | 回退、重跑、补偿和人工入口 |

如果演练只能依靠某位成员的记忆完成，系统存在可发现性风险。如果一个规则变化需要多个团队分别重新解释，系统存在知识所有权风险。

## 2. 边界卡片

每个重要模块维护一张短卡片：

- **承诺**：对调用方稳定提供什么结果；
- **拥有**：独立解释哪些数据、状态和规则；
- **隐藏**：哪些存储、重试和恢复细节不要求调用方理解；
- **拒绝**：哪些责任明确不属于本模块；
- **证据**：状态写入点、契约、配置和运行监控在哪里。

边界卡片无法简洁填写时，不一定需要新增文档；更可能是职责本身尚未清楚。

## 3. 调用方成本账本

从调用方视角记录使用一项能力的成本：

| 成本 | 观察方式 |
|---|---|
| 概念数量 | 完成常见操作前必须理解多少状态和术语 |
| 调用步骤 | 是否必须按固定顺序组合多个低层接口 |
| 异常处理 | 是否由每个调用方重复解释和恢复 |
| 兼容负担 | 内部变化会迫使多少消费者同步升级 |
| 排障路径 | 是否需要跨多个系统拼接日志和状态 |

新增服务只有在显著减少这些成本时才形成有效边界。部署独立并不自动意味着职责独立。

## 4. 决定记录

只记录会影响边界、所有权、正确性或长期成本的决定：

- 选择了哪个候选；
- 其他候选为何被排除；
- 哪些不变量必须保持；
- 谁维护规则并对结果负责；
- 何种证据会触发重新评估；
- 兼容和撤回路径是什么。

普通实现细节不需要升级成架构决定。记录的价值在于让后续修改者理解“为什么”，而不是增加审批材料。

## 5. 把检查放进现有流程

- 需求评审使用变化演练，识别跨模块影响。
- 架构评审使用边界卡片和调用方成本账本。
- 实现评审检查契约是否符合已确认的责任划分。
- 验证阶段覆盖存量兼容、恢复入口和关键监控。
- 复盘使用真实修改位置、排障步骤和遗漏缺陷更新决定记录。

机械规则交给自动化；边界收益、错误语义和知识所有权保留人工判断。这样可以增加设计反馈，而不增加一套独立治理流程。

## 6. 使用限制

- 技术层可以封装稳定的重试、超时和资源保护，但不能静默决定业务范围或权限。
- 集中恢复逻辑不能让一个底层模块承担所有业务策略。
- 为未来复用预建复杂框架，需要当前需求或容量证据。
- 性能方案必须有目标、测量和撤回条件。
- 这些工件是通用评审辅助，不代表任何组织已经采用的强制规范。
