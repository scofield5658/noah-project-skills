## 版本边界

英文第一版完整版共 21 章，其中第 21 章为结论；书末另有 15 条设计原则和 14 个危险信号总结。第二版新增第 21 章 “Decide What Matters”，因此结论章在目录编号上顺延为第 22 章；第 6 章被重写和扩充，并在第 9、12 章加入与 Robert C. Martin《Clean Code》的观点比较。

Stanford 官方 PDF 是第二版的变更摘录，不是第二版全书。其实际内容为：完整重写后的第 6 章、第 9 章新增的 9.8 节、第 12 章新增的 12.6 节，以及新增的第 21 章。本次“全书覆盖”指完整覆盖英文第一版目录，并额外覆盖这份官方摘录公开的第二版实质变化；不声称已阅读第二版未包含在摘录中的完整正文。

## 本轮校正结论

- 英文第一版的前言、第 1–21 章、15 条设计原则和 14 个危险信号均已与现有笔记逐项复核，未发现需要推翻的核心理解。
- 第二版信息严格限定在 Stanford 官方变更说明和 20 页摘录的覆盖范围内，避免把新增内容误写为第一版原文。
- 中文学习译本只承担术语辅助作用；当中文表述与英文原文可能存在差异时，以英文原文为准。

## 研读方法

- 逐章阅读英文段落，不从中文译文反推英文含义。
- 中文主要用于统一术语，并检查英文理解是否遗漏语境。
- 每章记录四类信息：核心命题、关键推理、危险信号、团队/技术设计启发。
- 跨章节综合时区分三层：代码与方法、模块与 API、团队与研发机制。
- 对作者的经验性主张保留边界，不把启发式原则当作机械规则。
- 避免大段摘录原文；仅记录必要的英文术语和原创概括。

## 术语基线

| English original | 常见中文译法 | 本文采用的直白理解 | 使用说明 |
| --- | --- | --- | --- |
| complexity | 复杂性 | 妨碍理解和修改的结构 | 不等同于规模大或功能多 |
| change amplification | 变更放大 | 多点修改 | 一个简单决策导致多处代码、配置或流程一起修改 |
| cognitive load | 认知负担 | 理解负担 | 完成一次正确修改前必须同时掌握的信息量 |
| unknown unknowns | 未知的未知 | 隐藏影响点 | 修改前不知道某个依赖或影响点存在，因此不会主动检查 |
| dependency | 依赖 | 一处变化会影响另一处 | 某处无法被独立理解或修改 |
| obscurity | 模糊性 | 重要信息难以找到 | 关键信息不明显、不一致或没有记录 |
| deep module | 深模块 | 简单接口封装大量能力 | 接口使用成本明显小于它隐藏的实现复杂度 |
| shallow module | 浅模块 | 低收益模块 | 新增的接口、部署或理解成本接近甚至超过它封装的能力 |
| information hiding | 信息隐藏 | 设计知识封装 | 让一个设计决策只由一个模块掌握；调用方只需了解输入、输出和错误，不必理解内部实现 |
| information leakage | 设计知识分散 | 同一设计知识散落在多个模块 | 常见表现是多个模块各自解释同一格式、规则或状态语义；不是安全数据泄漏 |
| temporal decomposition | 时间分解 | 按处理时序拆分 | 按“先做 A、再做 B”拆模块，导致相同知识散落在多个阶段 |
| pass-through method | 透传方法 | 纯透传层或方法 | 只把相同参数和结果转给下一层，没有提供新的抽象 |
| overexposure | 过度暴露 | 暴露过多内部细节 | 常见调用也必须理解罕见配置或内部实现 |
| special-general mixture | 特殊与通用混合 | 通用机制与特定业务混杂 | 稳定机制直接依赖某个具体业务场景 |
| conjoined methods | 纠缠方法 | 方法相互依赖 | 读懂其中一个方法时，必须同时查看另一个方法的实现，说明职责并未真正分开 |
| nonobvious code | 不明显的代码 | 难以直接理解的代码 | 快速阅读无法确认含义、控制流、生命周期或副作用 |
| pull complexity downwards | 将复杂性下沉 | 由最合适的责任模块集中处理复杂性 | 只处理与该模块核心职责相关、能避免多个调用方重复承担的问题 |
| define errors out of existence | 从定义上消除错误 | 仅在操作契约允许时调整语义，让无价值异常不再发生 | 目标已达到可作为正常结果，但真正无法完成、业务冲突及上层实现正确性所需的错误仍要保留 |
| design it twice | 设计两次 | 至少比较两种实质不同的设计 | 关键决策先比较候选，再选择整体复杂性更低的方案 |
| decide what matters | 决定什么重要 | 先区分真正影响结果的事项 | 重要内容保持高可见，其余细节封装或延后 |
| tactical programming | 战术式编程 | 只求当前尽快完成 | 以短期可运行作为主要目标 |
| strategic programming | 战略式编程 | 持续投入长期可维护性 | 每次交付都做适量设计投资，避免复杂性累积 |
| obvious | 易理解、明显 | 阅读后容易形成正确判断 | 重要行为、约束和副作用不依赖猜测 |
