# 设计、实现与审查交接

本技能负责面向专业用户的界面设计和后续实现，以及同一类读者的文档版式。它不做代码审查，也不起草技术方案正文；这两件事由用户另外安排的审查或方案编写流程完成。本技能只说明交出去时要带哪些信息，不规定对方用什么工具、按什么规则。

## 分工

- **设计阶段**可以在还没有代码变更时开始。先弄清任务、项目约束和方案取舍。没有 diff 不是设计工作的停止条件。
- **已确认或已授权的范围内**，按现有技术栈指导或编写实现，包括在现有壳内做新布局，以及已授权的新页面或原型。不要把每个样式或文案细节都变成确认项，也不要只因为界面是新的就停下。哪些事要先确认，按 [SKILL.md](../SKILL.md) 方法第 5 步。
- **有了可读取的代码变更后**，交给代码审查。本技能不宣布审查通过，也不在本地拼一套审查规则来代替审查；用户没有安排审查时，如实说明代码尚未经过审查。
- 审查可以质疑实现，也可以质疑原方案里暴露出的问题。本技能不限制其质疑，也不以「已按设计方案实现」为由要求放行。

## 与技术方案、文档的关系

- **技术方案正文**（改动范围、字段契约、验收与回滚等）不由本技能起草或评审。用户需要时，把本技能的设计结论作为方案编写的输入交出去，并说明这部分不在本技能范围内。
- **Word 文档和 PPT** 按[文档与幻灯片](document-and-slides.md)处理，不走代码审查。已有的技术方案要做成文档或幻灯片时，正文内容以方案为准，本技能只负责结构呈现、版式和图表表达，不改动方案结论。

## 设计阶段应留下的信息

- 项目约束与依据，以及尚未核实的缺口
- 与改动深度相称的方案说明（深度按 [SKILL.md](../SKILL.md) 方法第 4 步），并说明默认方案如何复用现有能力
- 本次涉及的状态与交互，不要罗列未涉及的状态
- 实现范围：改什么、不改什么
- 验证预期与底线（按 [SKILL.md](../SKILL.md) 方法第 6 步），写明准备用项目里的哪些命令或手工路径检查

上下文不足时写明「依据有限」，不要编造项目约定、接口或禁令。

## 实现之后交给审查的信息

- 可读取的代码变更（diff、文件片段或 PR）
- 已确认的设计结论、范围、复用路径和仍然有效的约束
- 实际验证：已运行的项目命令和结果；若只做了静态查看，就如实说明
- 尚未确认或刻意不做的事项

## 可复制提示

提示要能单独发给另一个会话使用，所以把关键规则写全了。规则有变动时，以 [SKILL.md](../SKILL.md) 为准并同步这里。

界面：

```text
项目：【待填写】
任务：【待填写】
使用者：【岗位、使用频率、角色与权限范围】
授权范围 / 不在范围：【待填写】

请先阅读项目规范和周边已有实现，优先复用现有组件、模式和视觉变量。
在项目约束下，按「任务 → 原则 → 方案 → 实现 → 验证」推进。
已有页面的实质性改动，比较可行替代与保持现状；新页面给出至少两种可行且有差异的方案；局部微调按合适深度说明即可。
在授权范围内自主推进（含壳内新布局、已授权的新页面或原型）。只有放弃可复用能力另起一套、超出授权、实质新增依赖或改动业务规则时，才先确认。
输出要有实际依据，不编造接口或项目禁令；按适用范围验证键盘与焦点、非颜色唯一传达、减少动态，以及部分失败后的输入保留、成败明细与安全重试，并说明检查方法和未验证项。
代码变更产生后交给代码审查，不要预先宣布通过。
```

文档或幻灯片：

```text
文档类型与用途：【Word 供查阅 / PPT 现场讲解 / PPT 会后传阅】
读者：【岗位，读完要做什么决定或动作】
内容来源：【设计结论、方案或数据所在位置】
已有模板：【路径，或写「没有」】

请先确定样式来源：有组织模板就用模板；没有就从产品已有的视觉变量推导，并标明是建议。
结论和需要读者决定的事放在最前；幻灯片每页标题是一句判断，条件和来源写进讲稿备注。
多列表格只把支撑当页判断的行列放上幻灯片，完整表格放附录或随附文档。
数字带单位、口径和来源；没有来源的留空并标「待补」，不估算、不编造。
状态和风险不只靠颜色；内容不依赖动画。
默认交付 Markdown 大纲和样式约定；没有文档生成能力时，明说文件尚未生成，不安装工具。
```
