# 日志与注释补充原则

## Overview

这个 skill 用于指导我们在既有后端代码中补充**必要且克制**的日志与注释。

目标不是把代码写得“到处都在说话”，而是做到两件事：

1. **出问题时能定位**
2. **读代码时能理解作者意图**

本 skill 适用于 Java、Python、Go、Node.js（JavaScript / TypeScript）等后端代码，以及批处理、状态机、审批流、回调、异步任务、数据库写入链路等场景。

执行前先确认目标语言、版本、现有日志框架、文档风格和整改范围；按职责识别入口、业务处理、数据访问和边界模型，不要求项目使用分层类结构。多语言项目分别沿用各自约定。

涉及具体日志 API、异常处理、函数或字段文档时，先阅读[语言适配说明](references/language-adaptation.md)。本技能不要求更换框架、引入依赖或调整业务逻辑；文档语言沿用目标项目约定，中文项目保留中文字段语义要求。

核心原则来自两个来源：

- **Clean Code**：注释解释“为什么”，而不是复述“做了什么”；日志服务于诊断，而不是制造噪音
- **本技能的日志约定**：日志需便于生产检索，不泄露敏感信息，不大面积输出无价值明细

---

## 适用场景

在以下场景使用本 skill：

- 用户要求“补日志”“补注释”“增强可读性”“方便生产排障”
- 代码审查明确只关注日志与注释，而不改业务逻辑
- 新增了较长流程代码，但缺少关键节点可观测性
- 状态流转、批量处理、回调补偿、审批操作等链路很难从代码直接看懂

以下场景不要滥用本 skill：

- 仅做日志平台、采集与告警基础设施建设、运行日志根因调查或业务功能开发；没有代码日志与注释整改目标时不套用本技能

- 仅因为“文件空白很多”就机械加注释
- DTO / Entity / dataclass / struct / 数据映射 / 简单访问器这类结构性代码上堆无意义注释
- 为每个 if/for/赋值语句加“翻译型注释”
- 为每个方法入口都加一条重复、无上下文的 `info`

## 总体原则

### 0. 先判断当前是“克制模式”还是“全量注释模式”

本 skill 默认遵循“**必要且克制**”原则，但如果用户或审查意见**明确要求类型或模块级、方法或函数级都补充说明**，则应切换到“**全量注释模式**”：

- **克制模式**：优先补关键链路的日志、复杂分支的解释性注释，避免机械铺满
- **全量注释模式**：对本次整改范围内的后端代码，默认要求范围内的类型（类、接口、枚举、struct 等）或模块补齐**职责文档**，每个有业务语义或阅读门槛的方法或函数补齐**契约文档**

全量注释模式下也仍然要避免两类问题：

- 把每一行代码翻译成中文
- 为 getter / setter / 自动生成代码（如 Lombok）/ 明显的测试夹具函数硬塞无信息量注释

换句话说，**全量注释模式强调“覆盖面”，但不取消“信息增量”要求**。

### 1. 先补关键链路，不补表面热闹

优先补下面这些位置：

- Controller / Handler / 路由函数 / Facade 的请求入口与失败出口
- Service / 业务处理函数的关键状态变更点
- 批量处理的开始、结束、跳过、失败
- 回调 / 补偿 / 重试 / 幂等分支
- 状态机迁移与关键校验失败
- 外部依赖调用前后

不要优先补下面这些位置：

- 纯数据搬运、无判断的 DTO / dataclass / struct 组装
- 一眼能看懂的简单访问器或数据映射
- 高频循环中的逐行成功日志

### 2. 日志回答“发生了什么”，注释回答“为什么这样做”

- **日志**：描述运行时事实，便于定位问题
- **注释**：解释设计意图、业务约束、边界原因

如果一句话更像“运行时证据”，写日志。
如果一句话更像“阅读理解辅助”，写注释。

### 3. 优先记录上下文标识，不记录冗余大对象

日志优先记录：

- 业务主键、流水号、批次号、合同号、事件号
- 操作类型、状态值、数据来源、条数、日期
- 调用结果、失败原因、耗时、关键决策分支

日志避免记录：

- 整个大 DTO / Entity / dataclass / struct / 字典的全量 dump
- 敏感字段、过多名称类冗余信息
- 大集合完整明细

### 4. 注释必须有信息增量

可以写的注释：

- 为什么要做这个防御性判断
- 为什么这里必须新事务 / 延迟执行 / 回滚补偿
- 为什么按这个顺序处理
- 为什么某个状态不能修改
- 为什么这里选择某个 fallback / tolerance / mapping 规则

不要写的注释：

- `// 设置创建时间`
- `// 遍历列表`
- `// 如果为空则返回`
- 任何直接把代码翻译成中文的句子

### 5. 只补“足够定位问题”的日志，不补“证明我来过”的日志

日志是生产资产，不是代码存在感。

能帮助回答下面问题的日志值得加：

- 请求进来了没有
- 处理到哪一步了
- 为什么被拒绝/跳过
- 哪条记录失败了
- 状态从什么变成了什么
- 外部调用失败时输入上下文是什么

如果一条日志不能帮助定位问题，也不能帮助还原执行路径，就不要加。

## 日志原则

## 0. 复用项目日志入口，保留环境策略

- 各语言均优先通过项目已封装或注入的 logger、日志收集器或等价诊断入口，记录关键动作、关联标识、结果和必要错误信息；先核对其调用契约，不绕过它另建日志实例或仅用 `print` / `console` / 标准输出替代。
- 没有统一封装时，沿用项目现有日志方式；下文语言库示例仅用于适配，不要求新引入框架、收集器或依赖。
- 检查关键字段能否经过现有格式化、序列化和采集入口保留下来；仅有日志调用不代表信息可追踪。能验证时检查实际输出，资料或环境不足时明确缺口，不宣称部署后已可检索。
- 日志在测试、生产等环境是否启用，以及级别阈值、采样和输出去向，遵循用户明确要求与项目现状。未获相应授权，不擅自开启、关闭或调整这些策略，也不自行添加环境判断；发现诊断缺口时说明影响与可选方案，不以排障需要替用户决定。

## 1. 日志级别

以下为诊断语义；实际级别名和 API 沿用项目规范，不因迁移语言而改写已有告警口径。无级别的日志库不伪造 `warn` / `error` 方法，也不自动更换框架。

- `info`
  - 入口操作、批量任务开始/结束、关键状态变更、关键外部调用成功结果摘要
- `warn`
  - 可预期但值得关注的分支：跳过、幂等命中、数据缺失、状态不匹配、参数降级
- `error`
  - 操作失败、外部调用异常、关键落库失败、无法继续的分支
- `debug`
  - 仅当项目已有明确使用场景时补充；默认不要新增大量 debug

### 失败与跳过的口径

- 带有明确“失败”语义、且说明本次操作未完成或需要回滚/人工介入的日志，默认使用 `error`
- 带有“跳过 / 忽略 / 幂等未命中 / 锁拦截 / 校验拒绝”语义、且属于可预期保护分支的日志，默认使用 `warn`
- 不要把真正的失败写成 `warn`，否则生产检索时容易和正常保护性分支混在一起
- 也不要把正常跳过统一拔高成 `error`，避免把可预期流转误报成故障

判断时优先问两个问题：

1. 这次操作是不是失败了，结果需要调用方重试、回滚或人工处理？
2. 这条日志是“系统故障/业务失败证据”，还是“保护性拒绝/兼容性跳过说明”？

如果更接近前者，用 `error`；如果更接近后者，用 `warn`。

## 2. 日志内容模板

推荐模式：

- `动作 + 关键上下文 + 结果`
- `why skipped + context`
- `state change + old/new + key id`

以下日志示例均为虚构的文档处理场景，`{}` 仅展示上下文位置；Python logging、Go、Node.js 等 API 不直接套用该占位符：

- `开始审核待发布文档, ids={}, targetStatus={}`
- `跳过文档索引更新, documentId={}, reason={}`
- `文档发布回滚完成, batchId={}, documentId={}`
- `重新汇总文档处理结果失败, batchId={}, message={}`

避免：

- `进入方法xxx`
- `处理成功`
- `执行完毕`
- `参数为:{}`

这些表述缺少动作语义或上下文价值，生产上几乎不可用。

## 3. Controller / Handler / 入口函数日志

入口职责（Controller、Handler、路由函数或命令入口）只记三类：

- 请求入口摘要
- 业务异常/系统异常出口
- 批量任务受理结果

不要在入口与业务处理层同时重复记录同一份完整成功日志。
默认由业务处理代码记录关键业务过程，入口负责请求摘要和已有失败出口的记录；不为补日志新增异常捕获或改变错误传播。

## 4. Service / 业务处理函数日志

业务处理职责是本 skill 的重点，不要求通过 Service 类实现。

优先补在这些节点：

- 方法或函数开始，且这是一个批量/异步/状态流转入口
- 校验拒绝、状态不允许、数据缺失
- 写库前后的关键决策
- 调用外部系统前后
- 补偿、回滚、回调消费
- 批量汇总结果

### 批量场景

批量场景不要逐条记录成功明细；建议记录：

- 总条数
- 成功数
- 失败数
- 跳过数
- 失败样本的关键 id

### 循环场景

在循环中，只对以下情况单条打日志：

- 单条失败
- 单条被跳过且原因关键
- 单条触发特殊状态迁移

## 5. 异常日志

异常日志必须至少包含：

- 发生什么动作失败了
- 哪个关键业务 id 失败了
- 关键上下文参数
- 原始异常或错误对象；堆栈采集沿用项目机制，Go 的 `error` 不等同于自带堆栈的异常

推荐（Java / SLF4J 示例，其他语言按[语言适配说明](references/language-adaptation.md)使用对应 API）：

- `logger.error("审核文档失败, documentId={}, status={}", documentId, targetStatus, e);`

不推荐：

- `logger.error("失败", e);`

## 注释原则

## 0. 类型、模块与方法、函数文档的默认要求

当任务明确要求“补全注释”时，注释块默认按下面规则执行：

- **类型或模块文档**：说明它解决什么业务问题、承担什么职责、边界是什么
- **方法或函数文档**：说明它完成什么动作、关键参数各自代表什么、返回值、副作用及错误语义是什么
- **接口方法**：即使没有实现细节，也要说明对调用方的契约语义
- **覆盖范围**：请求入口、业务处理、回调、状态机、适配器、复杂数据模型，以及测试中的关键场景函数
- **默认豁免**：纯 getter / setter、自动生成代码、零业务语义的构造器、明显的测试夹具函数，除非它们承载了额外业务约束，否则不要补注释
- **默认豁免**：显而易见的 CRUD 方法、仅做日志后直通委派的 controller / facade 包装方法、mapper/interface 上一眼可读的增删改查声明，默认不补方法注释

按目标语言使用原生文档格式；Java 使用 Javadoc，Python 使用 docstring，Go 使用声明前的 doc comment，JavaScript 使用 JSDoc，TypeScript 沿用项目文档格式。公开 API 或文档检查有覆盖要求时，不适用上述简单方法豁免。以下保留 Java 示例；其他语言适配见[语言适配说明](references/language-adaptation.md)。

```java
/**
 * 处理待发布文档的保存与状态流转，负责协调校验、落库和后续回调依赖。
 */
public class DocumentSubmissionServiceImpl {

    /**
     * 批量保存待发布文档并在需要时补齐派生字段。
     *
     * @param saveDtoList 前端提交的待发布文档列表
     * @param operator 当前操作人
     * @return 保存后的文档主键集合
     */
    public List<Long> addDocuments(List<DocumentSubmissionDto> saveDtoList, String operator) {
        ...
    }
}
```

以下情况可以简化处理，但要谨慎：

- 明显的框架覆写方法，且类级注释已经把职责说清楚时，可只补一句方法用途
- 零业务逻辑的测试辅助方法，可只保留必要的命名和少量块注释
- 自动生成的数据载体若字段含义已足够清晰，可只补类级注释；若字段本身容易误解，再补字段说明
- 纯 getter / setter 默认直接不写注释，除非方法里除了读写字段之外还夹带了校验、转换、兼容或副作用
- 显而易见的 CRUD / 直通委派方法默认直接不写注释，除非方法里额外承载了状态约束、兼容逻辑、异常语义或副作用

以下做法仍然不推荐：

- `/** 查询列表 */`、`/** 保存数据 */` 这种没有业务语义的空洞注释
- 只写 `@param dto dto`、`@return list`
- 注释内容与当前实现不一致，或遗漏关键限制条件

## 1. 注释写在“读者最可能误解”的地方

优先补这些地方的注释：

- 非直觉的状态流转
- 多数据源兼容逻辑
- 手工录入与系统采集共存逻辑
- 回调匹配、身份比对、补偿清理
- 金额/数量/剩余值的容差判断
- 新旧模型并存、兼容旧字段/旧接口的原因

## 2. 注释解释意图和边界

优先使用下面几类注释：

- **意图注释**：这一段整体想解决什么问题
- **约束注释**：为什么这里必须遵守某个状态/顺序/锁
- **兼容注释**：为什么还要保留旧行为或旧字段
- **分支注释**：为什么这个分支和直觉不同

## 3. 注释粒度

推荐：

- 类型或模块级：说明职责、边界、适用业务对象
- 方法或函数级：说明用途、关键参数、返回值或副作用
- 代码块级：适用于长方法或函数中一段难懂逻辑前
- 代码块级：适用于多步推导、匹配、补偿、汇总
- 常量级：适用于特殊 magic value 的业务含义

不推荐：

- 每行注释
- 注释掉本来就能从方法名/变量名读懂的代码

## 4. 注释与命名的关系

如果靠重命名就能表达清楚，优先重命名而不是补注释。

但这次任务若明确限定“只补日志和注释”，则不要为了追求完美而扩大为重构；只在不改变行为的前提下补最必要的解释性注释。

## 5. 持久化模型字段注释

持久化模型（Java Entity、Python ORM model / dataclass、Go struct、JS/TS ORM 模型等）连接数据库字段与业务代码。字段名即使使用英文且命名规范，也不一定能准确表达数据库设计中的业务含义，因此按以下规则处理：

- 字段已有可直接识别的等价语义文档或元数据时，不重复添加；例如 Java `@Schema` 的描述、Python 模型字段描述、Go 字段 doc comment。只有类型、列名或 `json` tag 不算业务说明
- 没有上述说明时，逐字段补充业务含义；中文项目保留字段业务含义的中文说明和中文句号，其他项目沿用其文档语言
- Java 使用 Javadoc 块，Python 使用项目既有的属性文档或模型字段说明，Go 使用紧邻字段的 `// FieldName ...`，JS/TS 使用属性文档或已有模型字段描述；不跨语言强制套用 Javadoc、注解或字段空行规则
- 对状态、方向、类型、金额、比例、时间等容易误解的字段，应补充必要的口径、单位或取值范围
- 注释必须以实际表结构、DDL、数据映射、接口契约或业务代码为依据；含义不确定时先查证，不凭英文名称臆造

虚构案例：`DocumentCopyRecord.copiedDocumentId` 对应 DDL 列 `COPIED_DOCUMENT_ID`，DDL 中文注释为“副本文档ID”。Java 格式如下，列名通过映射核对，不重复写进注释：

```java
/**
 * 源文档ID。
 */
private Long sourceDocumentId;

/**
 * 副本文档ID。
 */
private Long copiedDocumentId;
```

不要扩写成 `COPIED_DOCUMENT_ID：副本文档ID`、`数据库字段：副本文档ID` 或自行添加未经 DDL/契约证实的说明。

对于带口径的字段，应记录契约已明确的单位和范围，例如“图片目标压缩比例，取值范围为 0 到 1。”；此范围仅为虚构示例，不从字段名推导。

这类字段说明属于持久化模型的必要语义，不视为“翻译型注释”或机械注释。其他语言的模型适配见[语言适配说明](references/language-adaptation.md)。

## 6. Integration DTO / Contract 字段注释

集成层模型定义本系统与外部系统之间的传输契约。它可能是 Java DTO / record、Python dataclass / 验证模型 / TypedDict、Go struct、JavaScript 普通对象 / typedef、TypeScript interface / type，或其他等价结构。即使字段名能够直译，仍需明确其在下游接口中的业务含义、口径和格式。

- 按职责识别外部边界，不依赖 `integration`、`client`、`adapter` 等目录名；请求与响应模型均需说明职责
- 字段已有等价语义文档或元数据时，不重复；没有时，按目标语言逐字段说明，参照上一节的格式规则
- 枚举值、单位、时间格式、分页口径、多值传参形式等不直观信息应一并说明；Java record component、Python 模型属性和 Go struct 字段同样适用
- 请求字段说明其传给下游的查询或操作语义；响应字段说明其由下游返回的业务口径，不把两者混写
- 以外部接口契约、客户端声明、下游模型、适配器映射或契约测试为依据；无法确认的字段先查证，不根据英文名称臆造

例如虚构的外部文档集合查询请求，其集合标识是否为列表、分隔字符串或重复参数，必须由下游契约确定，不能照搬示例。不同语言的模型文档示例见[语言适配说明](references/language-adaptation.md)。

这项规则只强制约束外部系统边界模型；普通内部数据载体仍按信息增量原则处理。

## 按文件类型的默认策略

### Controller / Handler / 路由或命令入口

- 补入口摘要日志
- 补异常日志
- 仅在请求参数转换、特殊兜底文案处补简短注释

### Service / Processor / Callback / StateMachine / 业务函数

- 重点补日志
- 对复杂决策块补注释
- 对状态迁移、幂等、补偿、兼容逻辑优先补充

### Mapper / XML / Repository / 查询与映射函数

- 默认不加日志
- 仅在 SQL 字段映射非常反直觉时考虑加 SQL 侧注释；通常不是本 skill 的重点

### DTO / Entity / Enum / dataclass / struct / 对象契约 / interface / type

- 默认不加日志
- 普通内部数据载体仅在字段含义明显反直觉、且会长期误导读者时考虑补字段/类注释
- 集成层模型按“Integration DTO / Contract 字段注释”规则处理：补充职责说明；没有等价文档的字段按目标语言格式逐一说明
- 持久化模型字段按“持久化模型字段注释”规则处理：没有等价语义元数据时，按目标语言格式逐字段说明

### Test

- 默认不为测试补日志；沿用测试框架的失败诊断
- 仅在测试场景名或准备数据极难理解时补注释

## 代码审查执行步骤

1. 先识别本次变更中的**关键业务路径**
2. 找出这些路径上当前**不可观测**或**难理解**的点
3. 只在这些点上补日志和注释
4. 自查是否出现以下问题：
   - 新增日志过密
   - 成功日志与失败日志重复
   - 注释翻译代码
   - 类型、模块 / 方法、函数文档缺失，或只有空洞套话
   - 输出了大对象或敏感信息
   - 注释与代码事实不一致
5. 最后再统一检查：是否仍然保持“少而有力”

## 自检清单

- 是否复用了项目 logger 或等价采集入口，并检查关键字段的实际输出或说明验证缺口？
- 是否遵循用户与项目的环境日志策略，没有擅自决定测试或生产是否启用？
- 是否能从日志还原关键执行链路？
- 出错时是否能快速定位到业务主键/批次/状态？
- 是否避免了逐条成功日志刷屏？
- 当前任务若要求补全注释，是否已按目标语言覆盖类型、模块与方法、函数文档？
- 持久化模型字段没有等价语义元数据时，是否已按目标语言逐字段补齐文档？
- 集成层模型是否已有职责说明，且没有等价文档的字段已逐一说明？
- 注释是否解释了意图、边界或兼容原因？
- 是否删除了“废话注释”的冲动，而只保留真正有信息量的注释？
- 是否没有借补日志/注释之名改动业务逻辑？

## 产出标准

一轮合格的“补日志和注释”整改，应满足：

- 新增日志主要落在入口、状态变更、关键分支、异常和回调补偿处
- 默认模式下，新增注释主要落在复杂代码块和非直觉规则处
- 若任务明确要求补全注释，整改范围内的类型、模块与方法、函数文档也应按对应语言完整补齐
- 读代码的人能更快理解流程
- 线上出问题时能更快缩小定位范围
- 改动不引入额外业务行为变化

## 本地环境依赖

无本地运行时依赖。本技能仅提供 Markdown 指令，不要求安装 CLI、MCP、第三方包，也不需要凭据或访问外部服务。

在实际代码中应用时，沿用目标项目已有的日志框架、源码、DDL 或接口契约及验证工具；资料不可用时说明证据缺口，不猜测字段含义，不自动连接外部系统。示例 API 的版本条件见[语言适配说明](references/language-adaptation.md)，不构成本技能的安装依赖。
