# Gitee Team 子任务拆分与关联缺陷

将子任务拆分视为一次受控的任务编排：先确认本地能力和主任务事实，再生成可编辑 Manifest，最后在用户确认后写入。业务上的子任务管理同时包含原生子任务和通过“缺陷关联”纳入的独立 Bug；查询、查重和结果展示均覆盖两者。不要从任务角色推断功能、人员、自测、SQL 或文档范围。

## 适用范围

- 仅为产品需求（`Product`）、技术任务（`Task`）、生产改进（`Improvement`）处理单条或批量子任务的查询、拆分草案、创建、人员登记、重复校验和创建后回查。按当前空间及父节点配置选择子类型；前端工作优先匹配目标空间中已核验的前端开发子类型；名称或 key 仅是匹配线索，不能代替层级校验。
- 创建或按授权维护缺陷（`Bug`），登记报告人、负责人、测试负责人，并以“缺陷关联”连接到用户指定的上述主任务，纳入对应主任务的子任务管理。平台上 Bug 独立创建并建立关联；不为 Bug 拆子任务。
- 只读查看主任务明确关联的 Wiki 页面，用于补充草案背景。
- 维护主任务的三个受控字段。不要处理 Jira 状态、工时、主任务创建，或创建/更新 Wiki。

## 本地运行时能力

本地拆分草案无运行时依赖。Gitee Team 读取和写入使用已安装的 `gitee-team-manager`，执行前读取其 SKILL.md，按其要求检查 Python、requests、`GITEE_ONE_TOKEN` 和租户配置；复用现有安装，不自动安装、升级或改配置。当前身份通过其调用 `GET /users/me` 核验；人员通过 OA 账号查询解析。Wiki 只读能力单独探测，缺失时继续草案。

| 运行时能力 | 可执行动作 | 缺失时行为 |
| --- | --- | --- |
| Jira 读取 | 查询父任务、子任务、远程链接 | 不查询；仅使用用户提供的清单生成本地草案。 |
| Jira 创建 | 创建已确认的子任务 | 不创建，并报告能力缺口。 |
| Jira 描述更新 | 更新主任务受控字段 | 不更新描述；不以整段替换或未授权接口降级。 |
| Wiki 只读 | 查看明确关联的页面 | 不读取、不搜索、不抓取页面，并报告关联文档未读取。 |

平台具体参数遵循 `gitee-team-manager` 当前公开说明，不复制另一套 API 客户端。工具、认证或必要元数据缺失时仅生成草案；不得猜测用户账号、回显凭据或用真实创建测试连通性。

## 工作流

1. 探测能力：分别记录 Jira 读取、人员/类型校验、创建、描述更新、回查和 Wiki 读取是否可用。
2. 获取目标主任务：读取并核验空间、类型、层级位置、标题、描述、所有负责人及所有状态的直接子任务和缺陷关联，拉全分页。主任务仅允许 Product/Task/Improvement；查询不完整不能证明无重复。否则仅接受用户提供的清单生成草案。
3. 读取 Wiki：仅按描述或远程链接中明确给出的 URL/pageId 读取。Wiki 不可用时继续生成 Jira 草案，并标记信息缺口。
4. 生成 Manifest：遵循 [Manifest 模型](references/manifest-schema.md)。普通子任务按 [子任务类型选择](references/subtask-types.md) 核对父子类型并应用约定映射；缺少可用子类型时询问用户。缺陷按独立 Bug 类型及“缺陷关联”校验，不要求主任务的原生子类型列表包含 Bug；生产改进未配置原生子类型也不阻止关联缺陷。按 [人员与缺陷规则](references/people-and-bugs.md) 登记报告人、用户指定的负责人，以及缺陷测试负责人和关联目标。无法可靠取得的工作内容或人员保持待补充。
5. 重复与字段预检：按 [能力矩阵](references/capability-matrix.md) 校验本次事项、人员及关联。需要维护主任务受控字段时，另按 [受控描述规则](references/managed-description.md) 生成补丁，性能风险由用户明确给出“是/否”；这项要求不作为独立创建/维护缺陷的前置条件。疑似重复或本次待写字段冲突未解决时，相关工作项不进入写入。
6. 预览：分组展示待创建、已存在、疑似重复、每条事项的报告人/负责人及其来源、缺陷测试负责人和关联目标、主任务描述补丁、Wiki 摘要、能力缺口和未决项。缺陷关联类型或方向未核实前，不创建依赖该关联的新缺陷。
7. 写入：仅在用户明确确认精确清单后，先创建已确认的非重复子任务，再更新已确认的主任务受控字段，最后回查并逐条报告结果。缺陷按人员与缺陷规则完成创建/更新及关联。所有写请求关闭自动重试，结果未知先回查；部分失败必须如实保留成功项和失败原因，不自动重试、回滚或重复创建。

## 任务拆分规则

- 每个子任务都是独立工作项，至少说明任务维度、主题、范围、模块、标题、类型和指派人。
- 支持 `frontend`、`backend`、`data`、`documentation` 及用户定义维度。工作维度与平台子类型分开记录：技术方案使用对应的技术方案子类型，普通文档使用文档撰写子类型；已约定的替代类型见 [子任务类型选择](references/subtask-types.md)。技术方案、详细设计、接口文档和测试说明的范围由用户明确给出。
- 标题使用 `{{角色前缀}}{{可选标签}}{{业务名称}}{{模块}}{{具体功能}}`。`【自测】`、`【SQL】`、文档前缀和完整标题覆盖均由单条工作项配置。
- 不限制同一父任务下同一维度的数量。完全匹配的已有任务不创建；主题或范围相近但无法确定的任务标为疑似重复并请用户决定。

## 人员与缺陷要求

- 所有新建子任务及缺陷都登记报告人和负责人。报告人使用顶层 `reporter` 单个用户 Pointer，负责人使用 `values.assignee` 用户数组；回查顶层报告人，不能以 `values.reporter` 有值作为成功依据。报告人默认当前认证用户，用户指定时使用指定人；负责人必须由用户指定，不默认当前用户、不继承父任务负责人。用户已明确的批量人员规则可复用。
- 缺陷另需测试负责人，未指定时询问用户；至少关联一个用户指定的 Product/Task/Improvement 事项。关系、字段和回查细节见 [人员与缺陷规则](references/people-and-bugs.md)。
- 当前用户默认值仅用于新建事项；维护已有事项时保留原报告人、负责人和测试负责人，除非用户授权修改或明确要求补齐缺失值。

## 输出与确认边界

以主任务分组展示管理清单，在每组内同时列出普通子任务与关联缺陷，分别标注“原生子任务”或“缺陷关联”以及实际平台类型。缺陷关联多个主任务时，可在各组展示同一 key，但创建清单和全局事项数量按 objectId/key 去重。普通子任务数量、关联缺陷数量分别注明；单个来源读取失败时标记该组不完整，不能把未取得的关联缺陷当成零条。

预览必须包含：任务清单、父任务映射、类型和人员校验状态、描述补丁、重复结论、Wiki 页面标题/pageId/version（若已读）以及能力缺口。用户的“创建”只授权预览中的精确工作项和描述补丁；新增、删除或改名后必须重新预览并确认。

任何未执行的检查必须显示为“未执行（原因）”，例如“重复校验：未执行（无 Jira 读取能力）”“关联 Wiki：未读取（无 Wiki 只读能力）”“描述补丁：未生成（性能风险未确认）”。不得将未执行项显示为通过、无重复或无关联文档。

## 常见错误

- 没有 Jira/Wiki 工具仍声称已查询、已创建或已读取。
- 把前端任务自动加 `【自测】`，或把数据任务自动定为菜单权限 SQL。
- 仅因同一父任务已有一个前端/后端任务，就阻止不同主题或范围的工作项。
- 将独立 Bug 排除在主任务的子任务清单之外，或因主任务未配置 Bug 子类型而拒绝缺陷关联。
- 维护主任务描述时重写原文、删除链接，或修改三个受控字段之外的文字。
- 因 Wiki 工具缺失改用浏览器、全局搜索或未授权接口。

## 完整使用示例

概述：按目标空间配置拆分子任务、管理关联缺陷并回查结果。

输入：空间 DEMO 的 `Task` 主任务 `DEMO-100`，为库存查询创建数据开发子任务，用户指定负责人 Alice。当前层级只有 `FE_Subtask`、`OT_Subtask`，没有已确认的类型替代规则，子任务分页尚未读取完整。

输出：产生 `dimension=data`、负责人 Alice 的 Manifest 草案，报告人使用已核验当前用户；列出类型待确认和重复校验不完整，暂不创建。用户确认当前空间使用 `OT_Subtask`、完整查重及人员/父节点核验通过后，再展示精确清单；确认后通过公共 `gitee-team-manager` 创建并回查，不沿用其他空间的配置。
