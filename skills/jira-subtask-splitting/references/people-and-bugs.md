# 人员登记与缺陷关联

## 人员来源

适用于每条新建业务子任务和缺陷。报告人与负责人使用不同的字段位置和数据结构。

| 角色 | 字段 key | 取值规则 |
| --- | --- | --- |
| 报告人 | 顶层 `reporter`（单个 `_User` Pointer） | 默认当前 Token 对应的认证用户；用户指定报告人时覆盖默认，预览注明来源 |
| 负责人（执行人） | `values.assignee`（用户数组） | 必须由用户指定；可以引用本会话已明确的人员或批量分配规则，不默认当前用户、不继承主任务 |
| 缺陷测试负责人 | `values.TestOwner`（用户数组） | 创建缺陷或用户要求补齐时必须明确；未指定则询问，不自动等同报告人、执行人或主任务测试负责人 |

用 `GET /users/me` 核验当前用户的 objectId、username、enabled/deleted；不能用本机登录名、Git 作者或查询账号当作当前用户。通过 OA username 精确查询 `_User`，校验账号有效；重名、账号缺失、停用或无法解析时保持待定。用户已授权的人员规则直接复用，不重复询问；“我负责”可以通过当前认证身份解析为用户指定。

创建或编辑时，报告人写入顶层字段，例如：

```json
{"reporter": {"__type": "Pointer", "className": "_User", "objectId": "<已解析的用户ID>"}}
```

负责人和测试负责人仍为 `values` 中的用户数组，元素按当前平台格式携带已解析的 objectId/value、username 等信息。不要把 OA 字符串当作 objectId，也不要提交未解析的 `currentUser` 占位符。

回读事项详情时，核对顶层 `reporter.objectId` / `reporter.username` 是否对应目标用户，同时分别核对 `values.assignee` 和 `values.TestOwner`。`values.reporter` 即使保存了用户数组，也不能证明业务报告人已设置；顶层为空时应判定报告人未完成。页面显示“未指定”与接口核验冲突时先排查字段位置，不直接归因于缓存。

`reporter` 是业务报告人，`createdBy` 是平台审计创建人，指定报告人不代表修改 createdBy。`assignee` 与 `DevelomentOwner` 是不同角色，不替换为开发负责人。维护已有事项时不套用新建默认值覆盖原人员；只有用户授权的字段才更新。

## 缺陷处理

缺陷在平台上是独立类型，在业务上通过“缺陷关联”纳入 Product/Task/Improvement 的子任务管理。用户要求查询某主任务的子任务、检查重复或整理拆分结果时，默认同时覆盖其原生子任务和关联缺陷；明确只查某一类时遵从用户范围。读取不到关联时报告不完整，不能因此将缺陷排除在管理范围之外。

1. 缺陷类型为 `Bug`，独立创建；不在 ancestors 中写入本次缺陷关联目标，也不把关联目标记为原生父事项。已有缺陷可能带迁移遗留 ancestors，不能据此判定本次关联关系，更不能顺手清空。
2. 用户指定至少一个关联目标（明确上下文中的目标也可），逐个读取并确认属于 Product、Task 或 Improvement。支持一条缺陷关联多个已明确目标，不能扩大到其他事项、子任务或任意普通关联对象；目标空间不明确时先核对，不自行跨空间关联。
3. 在任何写入前，读取已存在的“缺陷关联”关系类型，核对 objectId、方向和允许的类型；查询关联目标上现有缺陷并拉全分页，对已有关系去重。没有关系读取能力、关系定义无法核对、关联范围不完整或疑似重复未解决时，保留草案，不先创建一个无法完成关联的新缺陷。
4. 预览包含：缺陷标题、范围/复现与期望行为（按用户提供信息）、报告人、负责人、测试负责人、全部目标事项 key/类型、已有及待新增关联。确认精确清单后再写入。
5. 使用 `gitee-team-manager` 创建 Bug 或更新已授权字段，再通过其关联具体事项能力提交 `itemLinks`（source、destination、linkType 使用已解析 ID，方向以实际关系定义为准）。不创建新的 ItemLinkType，不用普通关联或原生层级替代“缺陷关联”。
6. 所有写调用关闭自动重试。创建成功但关联失败时分别记录结果及缺陷 key，不重复创建、不自动删除。结果未知先核对已有事项/关联；恢复操作只处理已授权且确认未完成的步骤。
7. 回读并核对 Bug 类型、报告人、负责人、测试负责人和每条缺陷关联目标。只有人员和全部约定关联均核验成功才报告完成；仅接口返回成功但不能回查时明确标为未独立验证。

## 查重与归组

- 已有 Bug 已关联目标主任务时复用，不重复创建或重复添加该关系。用户明确给出已有 Bug、只需补关联时，仅新增缺少且已授权的关系。
- 一个 Bug 可归入多个主任务组，Manifest 中只记录一次 Bug，以 related_main_keys 表达多个目标；不能按主任务组数重复创建。
- 查询范围内发现主题、现象或范围相近的 Bug 时先列为疑似重复，不凭标题相同断定同一缺陷。普通子任务描述了相似工作时也展示交叉提示，由用户判断是已有工作还是独立缺陷，不自动将两种类型合并。
- 无有效关联目标的 Bug 不伪装成某主任务的子任务；展示为待关联。关系完成后回读并更新会话中的对应主任务清单，标注“缺陷关联”，不声称 Dashboard 缓存或网页已同步。
