# 后端审查参考

当本次变更主要是后端代码时读取本文件。

## 重点

1. 单测是否覆盖改动行为。
2. 数据库字段是否必要，影响面是否清楚。
3. API 和字段契约是否冗余。
4. service 层写法是否符合项目习惯。

## 单测覆盖

- 改到业务逻辑、分支、校验器、helper 或 service 时，先看项目是否已有测试习惯，再判断是否应补单测。
- 如果项目通常要求测试而本次缺失，要指出。
- 如果被改区域平时很少写单测，判断要克制，先跟随本地约定。

## 数据库字段

- 新增或修改字段前，先看是否确实需要。
- 判断 schema 变更是否影响上游生产方、下游消费方、ETL、后台工具、报表或历史兼容。
- 不必要的字段扩展，或解释不清的 schema 变更，应作为强问题处理。

## API 和契约冗余

- 检查新增请求/响应字段是否和已有语义重复。
- 看下游调用方是否还能容易理解这个契约。
- 字段把接口撑宽但没有清楚业务价值时，要指出。

## Service 层一致性

- handler、service、repository、validator 要跟随项目已有的分层和职责边界。
- 除非用户明确要求重构，不要借审查推动大范围架构翻新。
