# 前端代码审查

## 定位

这是一套给前端工程组使用的代码审查标准。审查时先看项目一致性，再补充正确性、安全性和可维护性判断。

不要把普通审查变成大重构建议。除非用户明确说这是一次技术重构，否则只提和当前改动闭环相关的问题。

## 本地环境依赖

本 skill 本身是规则型 code review 标准，无固定本地运行时依赖，不要求安装特定 Node、Java、Python、Golang、lint 或测试工具。

| 依赖 | 必选 | 用途 | 检查方式 | 缺失时处理 |
| --- | --- | --- | --- | --- |
| 可读取的代码变更 | 是 | 明确本次审查对象 | 本地 diff、文件片段、PR 内容或用户粘贴内容 | 若无法读取，要求用户提供 diff、文件片段或 PR 内容 |
| 项目上下文 | 强烈建议 | 判断项目规范、复用路径、命名习惯和分层方式 | 读取相邻文件、项目文档、配置和既有实现 | 缺失时说明审查基于有限上下文，避免强推项目风格结论 |
| Git / diff | 可选 | 获取本地变更和上下文 | `git status`、`git diff` 或用户提供的补充 | 不可用时不阻塞，改用用户提供的变更内容 |
| 目标项目测试/构建/lint 命令 | 可选 | 验证高风险结论或复现问题 | 以目标项目 README、package scripts、Maven/Gradle、Makefile 等为准 | 未确认前不引入新工具链；无法执行时在审查中说明验证缺口 |

测试、构建、lint、类型检查只依赖目标项目已有命令。不要因为使用本 skill 而新增工具链要求，也不要在未确认项目约定前要求安装新的 npm、Java、Python 或 Golang 依赖。

## 审查立场

- 把本技能作为前端工程组代码审查的主口径。
- 项目有明确规范时，先按项目规范判断。
- 项目没有成文规范时，从相邻模块和重复写法里推断风格。
- 优先最小闭环修改，不鼓励为了“看起来更整齐”扩大改动。
- 与其他 review skill 重叠时，保留本技能的输出结构和判断阈值。

## 审查流程

### 1. 先建立项目基线

- 先看变更文件和周边实现，再判断风格或结构问题。
- 查项目里是否已有组件、工具函数、hook、service、wrapper 或同类模式可以复用。
- 判断本次变更主要是前端还是后端，按对应规则审查。

### 2. 先看五个主标准

审查时先按下面顺序看：

1. 是否符合项目约定。
2. 是否复用已有能力。
3. 命名是否清楚、和项目习惯一致。
4. 逻辑重量和实现成本是否合理。
5. 改动范围是否克制。

这些都看完后，再补充正确性、边界条件、安全性和可维护性问题。

### 3. 归类结果

只使用下面三个结果桶：

- `Blocking`：合并前必须处理。
- `Needs confirmation`：需要用户确认需求、范围或取舍后再判断。
- `Suggestion`：可以改进，但不阻塞合并。

### 4. 判断是否需要反哺 skill

如果用户在审查过程中提出了本技能没有覆盖的审查观点，先判断它是否适合沉淀成默认规则。

只有同时满足这些条件才提出 skill 演进建议：

- 当前 skill 或 reference 还没有实质覆盖。
- 能抽象成稳定的审查启发，而不是一次性意见。
- 能复用于同类项目，例如常见前端项目或常见后端项目。
- 不依赖某个项目的业务规则、临时绕法、组织流程或一次事故。
- 加进去后确实能提升后续类似审查的质量。

不要为这些内容建议演进 skill：

- 项目私有规则、业务语义或公司流程。
- 只适用于很窄技术栈的小怪癖。
- 依赖具体历史背景的一次性问题。
- 不够稳定的个人偏好。

如果确实值得沉淀：

- 先完成本次主审查，不要打断 findings。
- 一次最多提一两个高置信候选。
- 问用户是否要把规则抽象后加回本 skill。
- 简要说明规则内容、适用范围和可复用理由。

## 主审查标准

### 1. 项目约定

- 检查改动是否符合项目现有技术规范、编码风格和抽象方式。
- 有文档先看文档；没有文档就看周边模块。
- 不用个人偏好压过项目已经形成的写法。

### 2. 先复用，再新增

- 检查项目里是否已有组件、函数、工具、hook、service 或 wrapper 能解决同类问题。
- 已有能力能覆盖时，平行再写一套通常是严重问题，除非作者明确需要不同语义。
- 发现重复实现时，要指出可以复用的具体路径。

### 3. 命名清楚

- 检查变量、函数、方法、props、字段命名是否符合项目习惯。
- 不要求英文完美，但要求团队成员能快速理解。
- 如果命名会掩盖业务含义、反转语义或让下游使用变难，要作为问题指出。

### 4. 逻辑重量和实现成本

- 检查是否有明显过重的逻辑块。
- 留意重复调用、重复分支、重复转换，或者本来一步能说清却拆得很散的流程。
- 如果浪费明显且有实际影响，按 `Blocking` 处理。
- 如果只是可以简化，但当前写法仍可接受，优先归为 `Needs confirmation`，不要强推重写。

### 5. 改动范围克制

- 检查实现是否贴着需求闭环走。
- 普通任务里不要鼓励顺手清理、大范围重构或纯风格改写。
- 如果改动明显超过原需求，归为 `Needs confirmation`，因为需求也可能已经在开发过程中变化。

## 前端审查规则

前端项目不要机械要求大范围测试覆盖。重点看改动行为是否正确，是否能融入项目已有写法。

- 涉及工具函数、数据转换、交互逻辑时，要核对函数级行为。
- 检查组件用法是否符合项目已有组合方式。
- 检查 props 或属性注入方式，下游是否能安全使用。
- 检查 callback 参数、触发时机和返回值是否符合调用方预期。
- 检查是否新增了没有价值的 wrapper、状态、组件层级或间接层。
- 明显不符合组件约定、破坏 prop 契约、命名误导或有实际浪费的问题，都按正常结果桶输出。

更多细节读取 `references/frontend-review.md`。

## 后端审查规则

后端项目要更关注测试、持久化和接口契约。

- 改到业务逻辑、分支或可复用函数时，看单测是否覆盖了新增行为。
- 数据库字段变更要看是否必要，是否影响上下游。
- 接口字段要看是否冗余、过宽，是否和当前契约一致。
- schema、API、service 变更要跟随项目既有分层和命名，不要单独开一套风格。
- 不必要的数据库字段扩展、接口语义重复、高风险逻辑无测试，都应作为审查问题。

更多细节读取 `references/backend-review.md`。

## 结果归类

### Blocking

满足任一情况时归为 `Blocking`：

- 违反项目已形成的约定。
- 没有理由地重复实现已有能力。
- 命名误导到会影响代码或数据语义。
- 引入明显且有意义的性能或实现浪费。

### Needs confirmation

满足任一情况时归为 `Needs confirmation`：

- 改动可能超过原需求，但需求也可能已经变化。
- 代码有简化空间，但当前方案仍能工作。
- 要求更大改动前，需要用户确认范围或取舍。

### Suggestion

低风险、可读性或维护性改进，且不改变当前方案方向时，用 `Suggestion`。

## 输出结构

审查结果固定按这个顺序输出：

```markdown
## Conclusion
- Overall judgment: Blocking / Needs confirmation / Suggestion / Pass

## Findings
- [Blocking] ...
- [Needs confirmation] ...
- [Suggestion] ...

## Impact
- 说明影响到的模块、调用方、契约、复用路径或维护成本

## Risks
- 说明兼容性、性能、误用或回归风险

## Open Questions
- 列出需要用户确认的问题
```

没有发现问题时，要明确说检查了哪些内容，并说明哪些范围没有验证。

如果存在高置信的 skill 演进候选，在正常审查结果之后追加：

```markdown
## Skill Evolution Suggestion
- 这条审查意见目前没有被 `frontend-code-review` 充分覆盖，但看起来可以复用
- 建议抽象为：...
- 适用范围：frontend / backend / both
- 是否要我把它加入本 skill，作为后续默认审查规则？
```

这一节要短，只在候选规则确实稳定时使用。

## 默认边界

- 只用于支持栈的代码审查：Java、Python、Golang、Node.js，以及传统 Web、React、Vue、Next.js 等前端栈。
- 其他技术栈不触发本技能，交给更合适的 skill 或通用审查处理。
- 只审查具体代码变更，不扩展到方案设计、发布治理或产品设计。
- 没有具体代码审查对象时，不把本技能当成方案设计工具。
- 不因为风格一致性要求大重构。
- 先按本技能标准审完，再补充通用 code review 经验。
- 若旧版审查 skill 同时存在，本技能的标准和输出结构优先。

## Skill 维护规则

- 跨项目通用的审查启发放在主 `SKILL.md`。
- 仅前端或仅后端适用的规则放到对应 reference。
- 新规则要抽象、稳定、可复用；不要写进项目名、内部业务术语或一次性历史事故。
- 基于真实审查对话更新 skill 前，需要先得到用户确认。

## 完整使用示例

概述：按项目约定审查代码变更，报告风险和最小修复方向。

输入：用户提供 `function total(items) { return items.reduce((s, x) => s + x.price, 0); }`；调用者可能传入缺失的 `items`，没有可运行的项目环境。

输出：按 Conclusion / Findings / Impact / Risks / Open Questions 给出审查结果。指出缺失值将触发运行时错误，影响汇总展示；确认“缺失值”应按空集合还是错误响应处理后，再确定最小修复。明确只做静态分析，补验正常数组、空数组及缺失值，不声称已运行测试，不扩大为组件或状态管理重构。
