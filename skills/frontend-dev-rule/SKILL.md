# 前端开发规则

围绕用户目标形成从方案、实现到验证的最小闭环。先理解项目和行为，再判断结构与风格；不因使用本技能扩大任务范围。

## 选择当前模式

| 用户目标 | 读取资料 | 交付 |
| --- | --- | --- |
| 讨论、编写或评审前端技术方案 | [设计指南](references/design.md) | 可实施方案，或方案问题及待确认决策 |
| 开发页面、组件、交互或修复前端问题 | [实施指南](references/implementation.md) | 范围内的实现、相关验证及未验证项 |
| 审查具体前端代码或 diff | [评审指南](references/review.md) | 有证据的问题、影响和最小修复建议 |

只加载当前任务需要的指南。混合任务按实际阶段切换；审查或方案请求不自动授权修改代码，开发请求也不强制先产出完整方案文档。用户只要求方案评审时，不因为没有代码 diff 而拒绝。

任务复杂、涉及共享能力或多方契约时，可使用[完整方案参考](references/solution-template.md)组织材料。简单改动用简短说明即可，不以章节数量、固定顺序或工具登记代替工程判断。

## 共同判断原则

1. **建立事实基线。** 确认目标用户、功能入口、现有行为、预期变化和验收条件。已有项目读取相关代码、调用方、配置和约定；新项目根据明确需求确定基础结构，不虚构已有组件或规则。
2. **区分事实与假设。** 上下文能回答的问题先查证。影响数据含义、接口语义、权限、兼容性或修改范围的未知点必须明确提出；已授权且范围明确的操作不重复确认。普通局部实现细节可按项目惯例处理并说明重要选择。
3. **追踪改动和影响。** 区分直接修改对象与受影响对象，覆盖页面、组件、共享状态、工具、接口类型、配置、文档和验证；只展开实际相关项。共享能力变化须追踪消费方和回归点。
4. **先评估复用。** 给出已有能力的具体位置，核对语义、生命周期、依赖和演进方向。合理的独立实现不因外形相似就被判错；新增抽象须能解释当前收益。
5. **按职责分离。** 页面渲染、交互状态、请求调用和数据转换应有清楚边界，落点服从目标项目的实际结构。不要强制特定框架、表单库、目录名或三层架构。
6. **按风险验证。** 对有逻辑的转换、异步状态、表单联动、组件与接口契约加强验证；普通样式或文案改动不要求大范围测试套件。静态检查、模拟响应、单元测试、浏览器验收和真实联调的证据范围不同，不相互替代。
7. **保持范围克制。** 不顺手重构、升级框架、迁移公共层或统一无关风格。需求与现有约束冲突时说明冲突和最小可行路径，不静默更改行为。

## 触发边界

- 支持传统 Web 及组件框架项目，不依赖某个组织、仓库名称或路径。
- 前后端混合任务只覆盖前端行为和相关接口契约。后端内部实现、数据库设计、纯后端审查交给相应工程能力，不据此声称完成全栈验证。
- 页面视觉实现需要兼顾已有设计系统、响应式和可访问性；本技能不替代专门的品牌创作或视觉素材生成。
- 仅做产品方向讨论、绘制插画、安装技能、发布部署或修改后端 SQL 时，不自动触发前端工程流程。
- 不自动更新本技能、不自动发布文档、提交代码、合并或部署。执行这些操作需要用户请求及对应权限。

## 本地环境依赖

本技能是 Markdown 规则与参考资料，无本地运行时依赖。无需其他 skill、外部账号、指定 CLI、模型或 MCP 服务即可使用。

| 任务能力 | 依赖 | 缺失时处理 |
| --- | --- | --- |
| 阅读上下文 | 用户提供的需求、方案、代码片段或可读取的项目文件 | 说明缺失材料，只提出能由现有证据支持的结论 |
| 本地开发或读取 diff | 目标项目文件；Git 为可选取证工具 | 用已有片段评审或给出补丁建议，不假装已修改真实项目 |
| 测试、类型检查、构建、浏览器验收 | 目标项目声明的运行时、锁文件与已有命令；浏览器工具按环境选用 | 核对项目配置，不额外引入工具链；列出无法执行的验证和原因 |
| 独立复核 | 可用且已授权的人工或独立评审能力，可选 | 完成自检并标注未独立复核；项目明确要求评审门禁时保留未完成状态 |

先核对工具能力和实际版本，不假定子代理、浏览器或某个命令始终可用。评审工具或模型只记录可验证的信息，不编造名称或固定轮数。依赖安装、外部调用和写入仍受任务授权约束。

## 交付前检查

- 交付是否对应用户当前模式，范围和关键假设是否明确？
- 数据、交互、异常态及受影响调用方是否形成闭环？
- 验证结论是否能追溯到实际检查；未验证范围是否说明？
- 是否将项目偏好误当作缺陷，或将工具不可用误当作验证通过？

输出语言跟随用户及目标项目。
