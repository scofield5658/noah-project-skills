# 前端设计指南

用于前端技术方案的讨论、起草和评审。目标是让实施者能理解用户行为、修改边界和验证方式，不要求每次完整填写模板。

## 先还原用户流程

定位页面、路由、菜单、标签页、弹窗或嵌入入口。说明当前用户如何完成任务、本次改变哪一步以及成功的可观察结果。关注主路径、取消或返回、失败恢复和已有数据的再次编辑。

收集当前技术栈、相似实现、设计约定和接口资料。对多个入口分别确认状态是否共享、返回时是否恢复、刷新或深链接是否可用。不将未读到的接口、组件或业务规则补写成事实。

## 把变化落实到职责与契约

按实际涉及项描述：

- 页面布局与交互编排、专用组件、共享业务组件、基础组件和工具函数。
- 状态由谁持有，哪些值可以派生，哪些需要跨入口保存；避免同一事实存在多个互相同步的副本。
- 请求、转换与展示如何衔接；遵循已有分层，不为少量逻辑机械增加文件和包装层。
- 复用对象的路径、适配条件与新增实现边界。不能仅以“已有类似组件”为由复用不同语义。

字段变化需要区分来源值、展示值、编辑状态、请求值和响应值。记录相关类型、单位、空值与缺省值、枚举映射、提供方、消费方及兼容规则；这些规则没有依据时标为未知，不凭字段名猜测。

对表单联动说明驱动方向、清空时机、默认值、回填顺序、校验和禁用条件。异步获取选项或详情时，说明旧请求晚返回、重复提交、切换实体或离开页面后的处理，防止旧结果覆盖新状态。

## 检查交互与风险

按当前场景选择，不机械扩展无关功能：

| 场景 | 设计要回答的问题 |
| --- | --- |
| 加载、空态和错误 | 用户能否区分状态，能否恢复，是否保留已编辑数据？ |
| 提交与重试 | 重复点击是否受控，失败后是否允许重试，服务端结果不明确时如何避免误报成功？ |
| 权限与敏感信息 | 哪些内容可见，服务端拒绝如何反馈；前端隐藏不是访问控制依据。 |
| 响应式与可访问性 | 小屏、键盘、焦点、标签和错误提示是否支持主要操作？ |
| 共享组件或状态 | 哪些调用方会受影响，旧参数和默认行为如何保持兼容？ |

对会改变行为或影响范围的未决项，给出已知事实、可选路径、推荐理由和待确认问题。不要把普通排版偏好列成阻塞项。用户已有明确结论时沿用，不重复追问。

## 方案规模与交付

小任务可用一段或短列表说明“目标 → 修改对象 → 行为变化 → 验证”。涉及多入口、共享能力或复杂契约时再使用[完整方案参考](solution-template.md)。用户有模板时优先遵循其模板。

验收用例至少能定位前置条件、动作和可观察的预期结果；分别说明模拟、函数测试、浏览器检查和联调能证明什么。发布、观察与回滚仅在相关时设计，不据此实际执行发布。

方案评审检查需求、设计与用例是否一致，给出触发场景、缺口、影响和建议。没有实现代码时不虚构文件行号或已完成的验证。关键决策未确认则标为草案或待确认，不能宣称可直接实施。

独立复核按风险、项目约定及用户要求安排；工具不可用时标注“未独立复核”，完成可执行的自检。若项目把独立评审作为准入条件，不以自检替代该门禁。复核导致范围或契约变化时，回到相关决策确认，不无上限循环评审。
