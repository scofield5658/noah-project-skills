# 前端代码评审指南

只审查用户指定的具体代码变更及必要上下文。默认只读，不因发现问题而自动改代码、发布评论或执行审批。

## 建立评审基线

确认 diff 或文件范围、需求和原行为。读取改动周边与实际消费方，再检查项目约定、已有复用能力和测试。缺少基准版本时说明无法可靠区分新增与历史问题。

片段可以用于有限评审；缺少上下文不等于缺陷。没有代码但用户要评审方案时，切换到设计指南；用户确实要审代码却未提供对象时，指出需要的 diff 或文件，不虚构 findings。

## 检查顺序

1. **行为和契约。** 需求是否实现，字段和类型是否一致，props、callback 参数、调用时机和返回值是否符合消费方预期？
2. **状态与异常。** 检查过期闭包、异步竞争、加载与错误状态、空值、取消或返回、重复提交及监听器或计时器清理。
3. **安全与可用性。** 按实际代码检查不可信内容渲染、敏感信息、权限失败处理、键盘与焦点、响应式及关键交互；不能以按钮隐藏证明服务端权限已落实。
4. **项目一致性与成本。** 检查既有组件组合、命名、重复转换和不必要的状态或包装层；复用建议必须给出具体位置与语义适配依据。
5. **范围与验证。** 是否有无关改动、遗漏调用方、未验证的高风险分支？验证要求与实际风险相称，不因缺少大范围组件测试就阻塞普通 UI 改动。

允许项目已有约定和明确的业务差异。对于当前改动无关的历史问题标明边界，不包装成新增回归；不同模块独立维护公共逻辑本身不构成缺陷。

## 结果分类

| 分类 | 判断依据 |
| --- | --- |
| Blocking | 有证据的错误、回归、契约破坏、安全或显著性能风险；或明确违反项目强制验收要求。说明具体影响和成立条件。 |
| Needs confirmation | 需求、字段含义、范围或约束缺失，现有证据不足以判错；给出待确认问题。 |
| Suggestion | 不影响正确交付的可读性、命名、风格或维护性建议。不要因个人偏好提高严重程度。 |

违反一般风格、出现类似代码或可以进一步简化，不自动等同于 Blocking。明确的项目强制规则可作为依据，但需区分强制要求与从邻近代码推测的惯例。

## 输出与证据

先给整体结论，再按严重程度列出问题；每条包含：

- 分类及简短标题。
- 文件和准确行号（材料支持时），或片段位置。
- 触发条件、行为及实际影响。
- 最小修复方向；复用建议附可验证的具体路径。
- 验证依据、置信边界或需要补充的信息。

最后合并说明影响范围和未验证项。没有问题时说“在本次范围内未发现可确认问题”，并交代检查范围；不要把“未发现”写成无条件通过。用户或项目有输出格式时遵循其格式，保留上述证据要素即可。

不要自动反哺技能、重写方案或修改实现。用户要求整改后才切换实施模式，并保留此前已确定的范围。
